# Use type-aware linting for checks the compiler intentionally does not perform

## 1. Catalog record

- **Catalog identifier:** 10.2.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** For production TypeScript, consider a typescript-eslint type-checked preset rather than relying on `tsc` alone.

## 2. Example

### 2.1 Scenario

An order worker sends a receipt after payment and must not lose an email delivery failure.

### 2.2 Preferred form

```typescript
async function sendReceipt(orderId: string): Promise<void> {
  await Promise.resolve(`sent receipt for ${orderId}`);
}

async function processPaidOrder(orderId: string): Promise<void> {
  await sendReceipt(orderId);
}

void processPaidOrder("order-42");

// eslint.config.ts should enable a type-checked typescript-eslint preset,
// including a rule such as @typescript-eslint/no-floating-promises.
```

### 2.3 Hazardous form

```typescript
async function sendReceipt(orderId: string): Promise<void> {
  await Promise.resolve(`sent receipt for ${orderId}`);
}

function processPaidOrder(orderId: string): void {
  sendReceipt(orderId); // tsc permits this floating Promise.
}

processPaidOrder("order-42");
```

### 2.4 Why this difference matters

`tsc` intentionally permits several JavaScript patterns that are risky under a project policy. Type-aware linting can flag a floating Promise, unsafe `any`, an unbound method, or a non-exhaustive switch while still using the program's real types.

## 3. Boundaries and distinctions

Lint rules are policy tools, not replacements for TypeScript or runtime tests. Enable type-aware rules that fit the production codebase, then provide narrow, reviewed exceptions for intentional patterns.
