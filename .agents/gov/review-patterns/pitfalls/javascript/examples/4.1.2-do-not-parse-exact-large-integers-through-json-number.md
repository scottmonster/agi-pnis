# Do not parse exact large integers through JSON Number

## 1. Catalog record

- **Catalog identifier:** 4.1.2
- **Impact:** high
- **Consensus:** high
- **Definition:** If JSON contains integer identifiers or quantities outside JavaScript's safe integer range, do not rely on a normal `JSON.parse()` number followed by a reviver to recover the original value. Preserve such values as strings or another exact representation at the serialization boundary.

## 2. Example

### 2.1 Scenario

An API returns a database identifier that must remain exact when the client sends it back later.

### 2.2 Preferred form

```javascript
const responseBody = '{"invoiceId":"9007199254740993"}';
const payload = JSON.parse(responseBody);
const invoiceId = BigInt(payload.invoiceId);

console.log(invoiceId === 9007199254740993n);
```

### 2.3 Hazardous form

```javascript
const responseBody = '{"invoiceId":9007199254740993}';
const payload = JSON.parse(responseBody);
const invoiceId = BigInt(payload.invoiceId);

console.log(invoiceId);
```

### 2.4 Why this difference matters

The hazardous parse first converts the JSON number to an imprecise `Number`; converting it to `BigInt` afterward preserves the wrong value.

## 3. Boundaries and distinctions

Ordinary JSON numbers are suitable when the protocol guarantees safe integer values or accepts floating-point semantics. Exact large values need an exact representation at the protocol boundary.
