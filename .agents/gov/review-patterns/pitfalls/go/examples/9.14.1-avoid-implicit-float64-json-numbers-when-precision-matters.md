# Avoid implicit `float64` JSON numbers when precision matters

## 1. Catalog record

- **Catalog identifier:** 9.14.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Decode into concrete numeric fields or use `Decoder.UseNumber` when arbitrary JSON numbers must retain their textual or integer precision.

## 2. Example

### 2.1 Scenario

A service receives an arbitrary JSON account number that may exceed exact `float64` integer precision.

### 2.2 Preferred form

```go
package example

import (
	"encoding/json"
	"io"
)

func accountNumber(r io.Reader) (int64, error) {
	decoder := json.NewDecoder(r)
	decoder.UseNumber()
	var body map[string]json.Number
	if err := decoder.Decode(&body); err != nil { return 0, err }
	return body["account"].Int64()
}
```

### 2.3 Hazardous form

```go
package example

import (
	"encoding/json"
	"io"
)

func accountNumber(r io.Reader) int64 {
	var body map[string]any
	_ = json.NewDecoder(r).Decode(&body)
	return int64(body["account"].(float64)) // Large integers can already be rounded.
}
```

### 2.4 Why this difference matters

Decoding into `any` converts JSON numbers to `float64` by default, which cannot represent every large integer exactly. `json.Number` preserves the numeric text for deliberate conversion.

## 3. Boundaries and distinctions

Decode directly into an `int64`, decimal type, or schema struct when the field type is known. `UseNumber` is useful when the JSON shape or number kind is dynamic.
