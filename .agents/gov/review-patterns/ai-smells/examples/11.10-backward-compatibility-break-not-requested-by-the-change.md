# Backward-compatibility break not requested by the change

## 1. Catalog record

- **Catalog identifier:** 11.10
- **Evidence:** se
- **Definition:** Changes existing callers’ behavior, data, or configuration despite no requirement to do so.

## 2. Scenario

### 2.1 Context

A request adds a `verbose` response field to an internal command.

### 2.2 Safer approach

The agent preserves the command's existing defaults and adds the field in a compatible form covered by current tests.

### 2.3 Failure mode

The agent also changes the default output format from text to JSON because it seems cleaner.

### 2.4 Why this difference matters

Existing scripts and users break even though the requested behavior did not require changing them.

## 3. Boundaries and distinctions

An intentional compatibility break may be justified by an explicit requirement and migration plan; do not infer one from a nearby enhancement.
