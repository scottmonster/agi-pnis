# Prefer typed atomic wrappers over primitive operations where practical

## 1. Catalog record

- **Catalog identifier:** 12.21.1
- **Impact:** medium
- **Consensus:** medium
- **Definition:** `atomic.Bool`, `Int64`, `Pointer[T]`, and related wrappers often make atomic intent and alignment clearer than free functions on raw addresses.

## 2. Example

### 2.1 Scenario

A worker pool needs a race-safe flag that tells workers to stop accepting new jobs.

### 2.2 Preferred form

```go
package worker

import "sync/atomic"

type Pool struct {
	stopping atomic.Bool
}

func (p *Pool) Stop() {
	p.stopping.Store(true)
}

func (p *Pool) AcceptingJobs() bool {
	return !p.stopping.Load()
}
```

### 2.3 Hazardous form

```go
package worker

import "sync/atomic"

type Pool struct {
	stopping uint32
}

func (p *Pool) Stop() {
	atomic.StoreUint32(&p.stopping, 1)
}

func (p *Pool) AcceptingJobs() bool {
	return atomic.LoadUint32(&p.stopping) == 0
}
```

### 2.4 Why this difference matters

The wrapper documents that the field is atomic state, carries the intended type, and keeps its operations attached to the value. Raw integer fields invite accidental ordinary reads, writes, copies, or mismatched atomic operations.

## 3. Boundaries and distinctions

The free functions remain correct when used consistently and can be necessary for existing layouts or low-level interoperability. Do not copy either a typed atomic wrapper or a raw field after it has begun participating in synchronization.
