# Do not capture an `AddCleanup` target in its cleanup

## 1. Catalog record

- **Catalog identifier:** 12.7.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** A cleanup function must not retain the object it is attached to, directly through a closure or indirectly through its cleanup argument.

## 2. Example

### 2.1 Scenario

A cache entry owns a temporary file that should be removed after the entry becomes unreachable.

### 2.2 Preferred form

```go
package example

import (
	"os"
	"runtime"
)

type cacheEntry struct {
	path string
}

func newCacheEntry(path string) *cacheEntry {
	entry := &cacheEntry{path: path}
	runtime.AddCleanup(entry, func(path string) {
		_ = os.Remove(path)
	}, entry.path)
	return entry
}
```

### 2.3 Hazardous form

```go
package example

import (
	"os"
	"runtime"
)

type cacheEntry struct {
	path string
}

func newCacheEntry(path string) *cacheEntry {
	entry := &cacheEntry{path: path}
	runtime.AddCleanup(entry, func(struct{}) {
		_ = os.Remove(entry.path)
	}, struct{}{})
	return entry
}
```

### 2.4 Why this difference matters

The cleanup closure retains `entry`, which keeps the cleanup target reachable. Since it never becomes unreachable, the cleanup may never run and the temporary file can remain on disk.

## 3. Boundaries and distinctions

Use deterministic cleanup for resources that must be released promptly or reliably. `AddCleanup` is only a best-effort fallback for objects whose lifetime is governed by garbage collection.
