# Wildcard dependency versions

## 1. Catalog record

- **Catalog identifier:** 8.10
- **Evidence:** e
- **Definition:** `*`, `+`, `latest`, or similarly unstable selection where reproducibility matters.

## 2. Scenario

### 2.1 Context

A production command-line tool must produce the same build for developers and continuous integration.

### 2.2 Safer approach

Declare a bounded dependency range appropriate for the project's compatibility policy and commit the resolved lockfile.

```json
{
  "dependencies": {
    "acme-parser": "^2.7.1"
  }
}
```

### 2.3 Failure mode

The agent selects whatever parser release happens to be newest at installation time.

```json
{
  "dependencies": {
    "acme-parser": "latest"
  }
}
```

### 2.4 Why this difference matters

The same source can resolve differently on later installs, making regressions hard to reproduce and review.

## 3. Boundaries and distinctions

An intentionally floating version can be useful in a disposable experiment or a dedicated compatibility-testing job. This failure concerns unstable selection in work that needs repeatable installation or builds.
