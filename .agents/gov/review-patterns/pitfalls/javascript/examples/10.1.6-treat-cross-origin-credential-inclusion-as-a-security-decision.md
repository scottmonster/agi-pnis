# Treat cross-origin credential inclusion as a security decision

## 1. Catalog record

- **Catalog identifier:** 10.1.6
- **Impact:** medium
- **Consensus:** high
- **Definition:** Enable cross-origin credentials only when required by the CORS and CSRF security model.

## 2. Example

### 2.1 Scenario

A dashboard reads public product availability from a separate API origin.

### 2.2 Preferred form

```javascript
async function loadAvailability(sku) {
  const response = await fetch(
    `https://api.example/products/${encodeURIComponent(sku)}/availability`,
    { credentials: "omit" },
  );
  if (!response.ok) throw new Error(`Availability request failed: ${response.status}`);
  return response.json();
}

loadAvailability("AB-42").catch(console.error);
```

### 2.3 Hazardous form

```javascript
async function loadAvailability(sku) {
  return fetch(`https://api.example/products/${encodeURIComponent(sku)}/availability`, {
    credentials: "include",
  }).then((response) => response.json());
}

loadAvailability("AB-42").catch(console.error);
```

### 2.4 Why this difference matters

`credentials: "include"` sends eligible cross-origin cookies and requires a compatible CORS response, expanding the CSRF and data-exposure considerations for a request that did not need a session.

## 3. Boundaries and distinctions

Credentialed cross-origin requests can be correct for a deliberately designed CORS and CSRF flow. Configure the server for specific trusted origins and verify that the request genuinely needs credentials.
