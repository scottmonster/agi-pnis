# Escape URL components according to their context

## 1. Catalog record

- **Catalog identifier:** 12.11.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Use path-segment escaping for path components and query escaping for query values rather than applying one generic escaping rule everywhere.

## 2. Example

### 2.1 Scenario

An API client places a user-controlled account ID in a path segment and a search filter in the query string. Both values can contain spaces, slashes, and punctuation.

### 2.2 Preferred form

```go
package example

import "net/url"

func searchURL(base, accountID, filter string) (string, error) {
	u, err := url.Parse(base)
	if err != nil {
		return "", err
	}
	u = u.JoinPath("accounts", accountID, "search")
	u.RawQuery = url.Values{"filter": {filter}}.Encode()
	return u.String(), nil
}
```

### 2.3 Hazardous form

```go
package example

import (
	"net/url"
	"path"
)

func searchURL(base, accountID, filter string) (string, error) {
	u, err := url.Parse(base)
	if err != nil {
		return "", err
	}
	// QueryEscape encodes a space as '+', which is not path-segment escaping.
	u.Path = path.Join(u.Path, "accounts", url.QueryEscape(accountID), "search")
	u.RawQuery = "filter=" + url.QueryEscape(filter)
	return u.String(), nil
}
```

### 2.4 Why this difference matters

Path segments and query values have different reserved-character rules. Applying query escaping to a path can change a resource name or leave a slash with the wrong meaning, while URL helpers preserve each component's intended context.

## 3. Boundaries and distinctions

Do not escape an entire URL as one string. When a value belongs in a fragment, user-info field, or another URL component, use the corresponding `net/url` API or escaping rule for that component.
