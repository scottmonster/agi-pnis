# Avoid caller-selected return-only generics

## 1. Catalog record

- **Catalog identifier:** 5.5.1
- **Impact:** high
- **Consensus:** medium
- **Definition:** Avoid APIs such as `parse<T>(input): T` when `T` is not inferred from or validated against an input; return `unknown` or a validated schema-derived type instead.

## 2. Example

### 2.1 Scenario

A JSON parser must establish the shape of its returned value.

### 2.2 Preferred form

```typescript
function parseJson(text: string): unknown {
  return JSON.parse(text);
}

const raw = parseJson('{"id":"u1"}');
if (typeof raw === 'object' && raw !== null && 'id' in raw && typeof raw.id === 'string') {
  console.log(raw.id);
}
```

### 2.3 Hazardous form

```typescript
function parseJson<T>(text: string): T {
  return JSON.parse(text) as T;
}

const user = parseJson<{ id: string }>('{"wrong":true}');
console.log(user.id.toUpperCase());
```

### 2.4 Why this difference matters

A return-only generic often behaves like an assertion controlled by the caller and gives the appearance of type safety without evidence that the runtime value is `T`.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
