# Do not add explicit variance annotations as routine documentation

## 1. Catalog record

- **Catalog identifier:** 11.7.1
- **Impact:** low
- **Consensus:** high
- **Definition:** Even when variance is understood, avoid sprinkling `in` and `out` through normal APIs solely to document intent.

## 2. Example

### 2.1 Scenario

A library exposes a producer whose structural variance is already obvious from its output-only method.

### 2.2 Preferred form

```typescript
interface Producer<T> {
  produce(): T;
}

interface Animal {
  name: string;
}

interface Dog extends Animal {
  bark(): void;
}

const dogs: Producer<Dog> = { produce: () => ({ name: 'Pip', bark() {} }) };
const animals: Producer<Animal> = dogs;
```

### 2.3 Hazardous form

```typescript
// `out` repeats what TypeScript can already infer from `produce`.
interface Producer<out T> {
  produce(): T;
}

interface Animal {
  name: string;
}

interface Dog extends Animal {
  bark(): void;
}

const dogs: Producer<Dog> = { produce: () => ({ name: 'Pip', bark() {} }) };
const animals: Producer<Animal> = dogs;
```

### 2.4 Why this difference matters

TypeScript already derives variance structurally, and its documentation explicitly describes manual annotations as rarely necessary.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
