# Throw Error objects rather than strings or primitive values

## 1. Catalog record

- **Catalog identifier:** 7.1.5
- **Impact:** medium
- **Consensus:** high
- **Definition:** Throw `Error` instances or appropriate subclasses for operational failures instead of strings, numbers, or arbitrary primitives.

## 2. Example

### 2.1 Scenario

A parser rejects a configuration file that lacks a required port number.

### 2.2 Preferred form

```javascript
function readPort(config) {
  if (!Number.isInteger(config.port)) {
    throw new TypeError("config.port must be an integer");
  }
  return config.port;
}

try {
  readPort({});
} catch (error) {
  console.error(error.name, error.message);
}
```

### 2.3 Hazardous form

```javascript
function readPort(config) {
  if (!Number.isInteger(config.port)) {
    throw "config.port must be an integer";
  }
  return config.port;
}

try {
  readPort({});
} catch (error) {
  console.error(error.name, error.message);
}
```

### 2.4 Why this difference matters

The string lacks an error name, stack, cause, and reliable type identity, so diagnostics and selective handling are weaker.

## 3. Boundaries and distinctions

Only throw values intended to represent failures; error subclasses should communicate a meaningful failure category rather than merely adding names.
