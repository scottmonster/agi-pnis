# Make closed unions exhaustive

## 1. Catalog record

- **Catalog identifier:** 1.10.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Exhaustively handle discriminated unions and enums with `never`, an `assertNever` pattern, or `switch-exhaustiveness-check`.

## 2. Example

### 2.1 Scenario

A status formatter must be updated whenever a new job state is added.

### 2.2 Preferred form

```typescript
type Job =
  | { state: 'queued' }
  | { state: 'running'; percent: number }
  | { state: 'failed'; reason: string };

function assertNever(value: never): never {
  throw new Error(`Unexpected value: ${JSON.stringify(value)}`);
}

function formatJob(job: Job): string {
  switch (job.state) {
    case 'queued': return 'Queued';
    case 'running': return `${job.percent}% complete`;
    case 'failed': return `Failed: ${job.reason}`;
    default: return assertNever(job);
  }
}
```

### 2.3 Hazardous form

```typescript
type Job =
  | { state: 'queued' }
  | { state: 'running'; percent: number }
  | { state: 'failed'; reason: string };

function formatJob(job: Job): string {
  switch (job.state) {
    case 'queued': return 'Queued';
    case 'running': return `${job.percent}% complete`;
    default: return 'Done'; // A new state silently receives the wrong label.
  }
}
```

### 2.4 Why this difference matters

Adding a new variant otherwise leaves existing control flow silently incomplete.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
