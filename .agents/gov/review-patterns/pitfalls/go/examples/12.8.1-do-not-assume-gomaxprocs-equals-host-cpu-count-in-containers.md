# Do not assume `GOMAXPROCS` equals host CPU count in containers

## 1. Catalog record

- **Catalog identifier:** 12.8.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** On current Go, understand the container-aware default rather than hard-coding host CPU assumptions or overriding it reflexively. Also account for the module's Go version when relying on newer default behavior.

## 2. Example

### 2.1 Scenario

A service sizes an internal worker pool while running in a container with a CPU quota.

### 2.2 Preferred form

```go
package example

import "runtime"

func workerLimit() int {
	return runtime.GOMAXPROCS(0)
}
```

### 2.3 Hazardous form

```go
package example

import "runtime"

func workerLimit() int {
	runtime.GOMAXPROCS(runtime.NumCPU())
	return runtime.NumCPU()
}
```

### 2.4 Why this difference matters

`NumCPU` can describe host capacity rather than the container's CPU limit. Resetting `GOMAXPROCS` to that value can oversubscribe the quota, increasing contention and request latency.

## 3. Boundaries and distinctions

The container-aware default depends on the Go runtime and the module's declared Go version. Set `GOMAXPROCS` deliberately when a measured workload needs a different limit, and document that deployment choice.
