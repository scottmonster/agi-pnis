# `errexit` changes inside conditions and command substitutions

## 1. Catalog record

- **Catalog identifier:** 4.1.1
- **Impact:** high
- **Consensus:** medium
- **Definition:** Functions in conditions and command substitutions can have `errexit` exceptions, so handle essential failures explicitly.

## 2. Example

### 2.1 Scenario

A release script must stop when either manifest generation or upload fails, including when the release function is used as a condition.

### 2.2 Preferred form

```bash
#!/usr/bin/env bash
set -euo pipefail

generate_manifest() {
  return 1
}

upload_manifest() {
  return 0
}

publish_release() {
  local directory=$1
  generate_manifest "$directory" || return 1
  upload_manifest "$directory/manifest.json" || return 1
}

if ! publish_release "build"; then
  printf 'release publication failed\n' >&2
  exit 1
fi
```

### 2.3 Hazardous form

```bash
#!/usr/bin/env bash
set -e

generate_manifest() {
  return 1
}

upload_manifest() {
  return 0
}

publish_release() {
  generate_manifest "$1"
  upload_manifest "$1/manifest.json"
}

if publish_release "build"; then
  printf 'release published\n'
fi
```

### 2.4 Why this difference matters

Calling a function in a tested context can suppress `errexit` for failures inside it. Explicitly returning after essential failures keeps the function's result reliable after refactoring.

## 3. Boundaries and distinctions

`inherit_errexit` and POSIX mode can also change command-substitution behavior. Treat `set -e` as a guardrail, not the only failure-handling mechanism.
