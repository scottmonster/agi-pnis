# Do not silently discard meaningful errors

## 1. Catalog record

- **Catalog identifier:** 2.6.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Handle, propagate, or deliberately document ignored errors rather than routinely assigning them to `_`.

## 2. Example

### 2.1 Scenario

A service writes an audit record that must be durable before it reports a successful account deletion.

### 2.2 Preferred form

```go
package example

import (
	"fmt"
	"io"
)

func recordDeletion(audit io.Writer, accountID string) error {
	if _, err := fmt.Fprintf(audit, "deleted=%s\\n", accountID); err != nil {
		return fmt.Errorf("write deletion audit: %w", err)
	}
	return nil
}
```

### 2.3 Hazardous form

```go
package example

import (
	"fmt"
	"io"
)

func recordDeletion(audit io.Writer, accountID string) error {
	_, _ = fmt.Fprintf(audit, "deleted=%s\\n", accountID)
	return nil
}
```

### 2.4 Why this difference matters

Ignoring the write failure reports success even if the audit sink is full or disconnected. Propagating the error lets the caller retry, alert, or stop the operation according to its durability requirement.

## 3. Boundaries and distinctions

An ignored error can be acceptable only when failure is intentionally harmless and that decision is evident in context, such as a best-effort diagnostic write. Do not use `_` as a routine substitute for error handling.
