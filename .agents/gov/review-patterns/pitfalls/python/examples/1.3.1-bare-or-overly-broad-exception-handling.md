# Bare or overly broad exception handling

## 1. Catalog record

- **Catalog identifier:** 1.3.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Catch the narrowest exception types that the code can meaningfully handle. Avoid bare `except:` except for exceptional cases where `BaseException` subclasses such as `KeyboardInterrupt` and `SystemExit` truly need handling.

## 2. Example

### 2.1 Scenario

A configuration loader uses a default port only when the port text is malformed.

### 2.2 Preferred form

```python
def parse_port(text: str) -> int:
    try:
        return int(text)
    except ValueError:
        return 8000


print(parse_port("not-a-number"))
```

### 2.3 Hazardous form

```python
def parse_port(text: str) -> int:
    try:
        return int(text)
    except:
        return 8000


print(parse_port("not-a-number"))
```

### 2.4 Why this difference matters

A bare handler can hide interrupts, shutdown signals, and programming errors, making the process difficult to stop or diagnose.

## 3. Boundaries and distinctions

Handling `BaseException` can be justified in a top-level cleanup boundary, but it should normally re-raise termination-related exceptions.
