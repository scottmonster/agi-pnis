# Do not change the concrete type stored in `atomic.Value`

## 1. Catalog record

- **Catalog identifier:** 6.10.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** After the first store, all values placed in an `atomic.Value` must have the same concrete type, and storing nil is invalid.

## 2. Example

### 2.1 Scenario

A process publishes replaceable configuration snapshots.

### 2.2 Preferred form

```go
package main

import "sync/atomic"

type config struct{ enabled bool }
var current atomic.Value
func init() { current.Store(config{enabled: true}) }
func update(next config) { current.Store(next) }
func load() config { return current.Load().(config) }
```

### 2.3 Hazardous form

```go
package main

import "sync/atomic"

var current atomic.Value
func init() { current.Store("enabled") }
func disable() { current.Store(false) }
```

### 2.4 Why this difference matters

The second store panics because `bool` differs from the first stored `string`. Storing nil also panics.

## 3. Boundaries and distinctions

Store one stable wrapper type if the logical payload has variants. `atomic.Value` is for whole-value replacement, not shared in-place mutation.
