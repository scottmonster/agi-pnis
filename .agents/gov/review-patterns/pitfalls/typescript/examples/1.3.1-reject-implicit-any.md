# Reject implicit `any`

## 1. Catalog record

- **Catalog identifier:** 1.3.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Keep `noImplicitAny` enabled rather than allowing unresolved types to silently fall back to `any`.

## 2. Example

### 2.1 Scenario

A helper receives a percentage supplied by a form field.

### 2.2 Preferred form

```typescript
function parsePercentage(value: string): number {
  const parsed = Number(value);
  if (!Number.isFinite(parsed)) throw new Error('Invalid percentage');

  return parsed;
}
```

### 2.3 Hazardous form

```typescript
// With `noImplicitAny: false`, `value` silently becomes `any`.
function parsePercentage(value) {
  return value.trim() / 100;
}
```

### 2.4 Why this difference matters

An implicit `any` disables checking at precisely the locations where the compiler could not establish what a value is.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
