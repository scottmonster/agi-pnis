# Treating compound shared-state operations as atomic

## 1. Catalog record

- **Catalog identifier:** 2.22.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Use synchronization for shared invariants and read-modify-write sequences instead of assuming that individual list or dict operations make a larger operation atomic.

## 2. Example

### 2.1 Scenario

Several threads reserve units from one shared inventory count. A reservation must never make the count negative.

### 2.2 Preferred form

```python
from threading import Lock


class Inventory:
    def __init__(self, available: int) -> None:
        self.available = available
        self._lock = Lock()

    def reserve_one(self) -> bool:
        with self._lock:
            if self.available == 0:
                return False
            self.available -= 1
            return True
```

### 2.3 Hazardous form

```python
class Inventory:
    def __init__(self, available: int) -> None:
        self.available = available

    def reserve_one(self) -> bool:
        if self.available == 0:
            return False
        self.available -= 1
        return True
```

### 2.4 Why this difference matters

The check and decrement are one invariant, not one atomic operation. Interleaving threads can both pass the check and over-reserve the inventory.

## 3. Boundaries and distinctions

Single-threaded code does not need this lock. Concurrent designs can also protect the invariant through message passing or a database transaction rather than a Python lock.
