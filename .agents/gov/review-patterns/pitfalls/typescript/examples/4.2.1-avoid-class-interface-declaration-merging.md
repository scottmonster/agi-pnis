# Avoid class-interface declaration merging

## 1. Catalog record

- **Catalog identifier:** 4.2.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Do not merge a class and interface of the same name to add instance members unless the runtime actually initializes those members through a controlled mechanism.

## 2. Example

### 2.1 Scenario

A model needs data that is explicitly initialized by its constructor.

### 2.2 Preferred form

```typescript
class User {
  constructor(readonly id: string, readonly displayName: string) {}

  label(): string {
    return `${this.displayName} (${this.id})`;
  }
}

console.log(new User('u1', 'Ada').label());
```

### 2.3 Hazardous form

```typescript
class User {
  constructor(readonly id: string) {}
}

interface User {
  displayName: string;
}

const user = new User('u1');
console.log(user.displayName.toUpperCase()); // Runtime value is undefined.
```

### 2.4 Why this difference matters

TypeScript can believe merged members exist even though constructing the class leaves them undefined.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
