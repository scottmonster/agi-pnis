# Relying on `__del__` for important behavior

## 1. Catalog record

- **Catalog identifier:** 13.5.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Keep `__del__` minimal and avoid depending on it for correctness, lock acquisition, or deterministic resource release.

## 2. Example

### 2.1 Scenario

An export job needs a file handle to be closed before a follow-up process reads its output.

### 2.2 Preferred form

```python
from pathlib import Path


def write_export(path: Path) -> None:
    with path.open("w", encoding="utf-8") as output:
        output.write("complete\n")


write_export(Path("export.txt"))
```

### 2.3 Hazardous form

```python
from pathlib import Path


class ExportWriter:
    def __init__(self, path: Path) -> None:
        self.output = path.open("w", encoding="utf-8")

    def write(self) -> None:
        self.output.write("complete\n")

    def __del__(self) -> None:
        self.output.close()


writer = ExportWriter(Path("export.txt"))
writer.write()
```

### 2.4 Why this difference matters

Object finalization timing is not a deterministic resource-management contract. The file can remain open through the next operation, and shutdown or cyclic-reference conditions can make finalizers unreliable.

## 3. Boundaries and distinctions

`__del__` can support minimal best-effort cleanup, but it must not be the mechanism that preserves correctness. Use context managers or an explicit `close()` protocol for resources with required release timing.
