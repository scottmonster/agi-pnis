# Blocking the asyncio event loop

## 1. Catalog record

- **Catalog identifier:** 3.9.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Do not perform long blocking I/O or CPU-bound synchronous work directly inside event-loop callbacks and coroutines. Use asynchronous APIs, `to_thread()` for appropriate blocking I/O, or process/interpreter execution for CPU-heavy work.

## 2. Example

### 2.1 Scenario

An async API handler reads a legacy file through a blocking library. Other requests should remain responsive during the read.

### 2.2 Preferred form

```python
import asyncio
from pathlib import Path


def read_legacy_file(path: Path) -> str:
    return path.read_text(encoding="utf-8")


async def load_configuration(path: Path) -> str:
    return await asyncio.to_thread(read_legacy_file, path)


async def main() -> None:
    print(await load_configuration(Path("config.txt")))


asyncio.run(main())
```

### 2.3 Hazardous form

```python
import asyncio
import time


async def load_configuration() -> str:
    time.sleep(5)
    return "configured"


async def main() -> None:
    print(await load_configuration())


asyncio.run(main())
```

### 2.4 Why this difference matters

The blocking sleep prevents the event loop from running timers, I/O callbacks, and other coroutines. One slow operation can stall unrelated async work.

## 3. Boundaries and distinctions

Very short synchronous work may be acceptable. CPU-heavy work generally needs a process, interpreter, or native implementation rather than `to_thread()` on a GIL-enabled runtime.
