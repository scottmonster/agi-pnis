# Test a command by running it

## 1. Catalog record

- **Catalog identifier:** 5.2.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Prefer `if command; then ...` over running a command, inspecting `$?`, and then branching. Do not place a command name inside `[ ... ]` expecting it to be executed.

## 2. Example

### 2.1 Scenario

A release script must continue only after a package upload succeeds.

### 2.2 Preferred form

```bash
upload_package() {
  local package=$1
  [[ -s $package ]]
}

package_path=${1:?provide a package path}
if upload_package "$package_path"; then
  printf 'upload completed\n'
else
  printf 'upload failed\n' >&2
  exit 1
fi
```

### 2.3 Hazardous form

```bash
upload_package() {
  local package=$1
  [[ -s $package ]]
}

package_path=${1:?provide a package path}
upload_package "$package_path"
if [ $? -eq 0 ]; then
  printf 'upload completed\n'
else
  printf 'upload failed\n' >&2
  exit 1
fi
```

### 2.4 Why this difference matters

An `if` condition consumes the upload command's status directly. Separating execution from the status check creates an opportunity for future logging or cleanup to overwrite `$?` before it is tested.

## 3. Boundaries and distinctions

Saving `$?` is appropriate when the status must be used later or more than once, but it must be saved immediately after the relevant command.
