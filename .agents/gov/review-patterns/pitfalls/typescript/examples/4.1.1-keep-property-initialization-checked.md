# Keep property initialization checked

## 1. Catalog record

- **Catalog identifier:** 4.1.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Keep `strictPropertyInitialization` enabled and use definite-assignment assertions only when an external initialization mechanism genuinely guarantees assignment.

## 2. Example

### 2.1 Scenario

A service requires a configured endpoint before it can make requests.

### 2.2 Preferred form

```typescript
class Service {
  readonly endpoint: URL;

  constructor(endpoint: string) {
    this.endpoint = new URL(endpoint);
  }

  requestPath(path: string): string {
    return new URL(path, this.endpoint).toString();
  }
}

console.log(new Service('https://api.example/').requestPath('users'));
```

### 2.3 Hazardous form

```typescript
class Service {
  endpoint!: URL;

  requestPath(path: string): string {
    return new URL(path, this.endpoint).toString();
  }
}

const service = new Service();
console.log(service.requestPath('users'));
```

### 2.4 Why this difference matters

`property!: T` suppresses a real initialization check and can leave runtime properties undefined while their type claims otherwise.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
