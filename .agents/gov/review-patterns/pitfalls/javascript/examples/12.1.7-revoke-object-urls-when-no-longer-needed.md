# Revoke object URLs when no longer needed

## 1. Catalog record

- **Catalog identifier:** 12.1.7
- **Impact:** medium
- **Consensus:** high
- **Definition:** Revoke application-owned object URLs when their lifetime ends.

## 2. Example

### 2.1 Scenario

A file preview creates a temporary object URL for an image selected by the user.

### 2.2 Preferred form

```javascript
function showPreview(file, image) {
  const url = URL.createObjectURL(file);
  image.addEventListener("load", () => URL.revokeObjectURL(url), { once: true });
  image.addEventListener("error", () => URL.revokeObjectURL(url), { once: true });
  image.src = url;
}

const preview = document.querySelector("#preview");
const file = new File(["image bytes"], "avatar.png", { type: "image/png" });
showPreview(file, preview);
```

### 2.3 Hazardous form

```javascript
function showPreview(file, image) {
  image.src = URL.createObjectURL(file);
}

const preview = document.querySelector("#preview");
const file = new File(["image bytes"], "avatar.png", { type: "image/png" });
showPreview(file, preview);
```

### 2.4 Why this difference matters

Each object URL retains the referenced blob until it is revoked or the document unloads. Repeated previews can therefore retain substantial memory unnecessarily.

## 3. Boundaries and distinctions

Do not revoke an object URL before the consumer has finished reading it. The right lifetime differs for an image preview, a download, and a worker script.
