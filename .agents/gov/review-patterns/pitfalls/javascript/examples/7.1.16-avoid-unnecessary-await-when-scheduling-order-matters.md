# Avoid unnecessary await when scheduling order matters

## 1. Catalog record

- **Catalog identifier:** 7.1.16
- **Impact:** low
- **Consensus:** high
- **Definition:** Do not add `await` merely for stylistic consistency when the value does not need asynchronous unwrapping. Each actual suspension adds another asynchronous continuation.

## 2. Example

### 2.1 Scenario

A helper returns a value that has already been computed, and callers depend on predictable microtask ordering.

### 2.2 Preferred form

```javascript
async function formatStatus(status) {
  return status.toUpperCase();
}

formatStatus("ready").then(console.log, console.error);
console.log("scheduled");
```

### 2.3 Hazardous form

```javascript
async function formatStatus(status) {
  return await status.toUpperCase();
}

formatStatus("ready").then(console.log, console.error);
console.log("scheduled");
```

### 2.4 Why this difference matters

The unnecessary await adds a suspension and continuation, which can change interleaving with other queued work and adds overhead.

## 3. Boundaries and distinctions

Await is appropriate when a value must be unwrapped or sequencing and local error handling require it; omit it only when those effects are unnecessary.
