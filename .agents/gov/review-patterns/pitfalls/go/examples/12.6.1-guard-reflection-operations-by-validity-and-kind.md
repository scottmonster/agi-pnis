# Guard reflection operations by validity and kind

## 1. Catalog record

- **Catalog identifier:** 12.6.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Before calling kind-specific `reflect.Value` methods, establish that the value is valid and has the required kind and mutability properties.

## 2. Example

### 2.1 Scenario

A configuration helper accepts a value supplied by a plugin and sets its exported integer `Port` field.

### 2.2 Preferred form

```go
package example

import (
	"errors"
	"reflect"
)

func setPort(target any, port int64) error {
	v := reflect.ValueOf(target)
	if !v.IsValid() || v.Kind() != reflect.Pointer || v.IsNil() {
		return errors.New("target must be a non-nil pointer")
	}

	field := v.Elem().FieldByName("Port")
	if !field.IsValid() || field.Kind() != reflect.Int || !field.CanSet() {
		return errors.New("target must have a settable int Port field")
	}
	field.SetInt(port)
	return nil
}
```

### 2.3 Hazardous form

```go
package example

import "reflect"

func setPort(target any, port int64) {
	field := reflect.ValueOf(target).Elem().FieldByName("Port")
	field.SetInt(port)
}
```

### 2.4 Why this difference matters

The hazardous form panics for a nil value, a non-pointer, a missing field, a field of another kind, or an unsettable field. Validation turns unsupported plugin input into a normal error.

## 3. Boundaries and distinctions

Prefer a typed interface when the set of supported targets is known. Reflection is most useful when the helper must genuinely operate over types not known at compile time.
