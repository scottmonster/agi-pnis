# Do not treat `ERR` as a universal exception trap

## 1. Catalog record

- **Catalog identifier:** 4.3.1
- **Impact:** high
- **Consensus:** medium
- **Definition:** Do not rely on `ERR` as a catch-all because it skips several failure contexts.

## 2. Example

### 2.1 Scenario

A deployment must report and stop when its upload request fails.

### 2.2 Preferred form

```bash
#!/usr/bin/env bash

upload_artifact() {
  return 1
}

if ! upload_artifact; then
  printf 'upload failed\n' >&2
  exit 1
fi
```

### 2.3 Hazardous form

```bash
#!/usr/bin/env bash

trap 'printf "deployment failed\n" >&2' ERR

upload_artifact() {
  return 1
}

if upload_artifact; then
  printf 'upload succeeded\n'
fi
```

### 2.4 Why this difference matters

Failures in conditional contexts are among the cases where Bash does not run an `ERR` trap. The trap cannot replace explicit handling for operations that must succeed.

## 3. Boundaries and distinctions

An `ERR` trap can still add diagnostics for covered failures. It should complement direct checks, not serve as a universal catch mechanism.
