# Consider `isolatedDeclarations` for scalable library declaration generation

## 1. Catalog record

- **Catalog identifier:** 11.2.1
- **Impact:** low
- **Consensus:** high
- **Definition:** Library/tooling authors who need declaration generation without whole-program inference can use `isolatedDeclarations` and explicitly type the necessary exported surface.

## 2. Example

### 2.1 Scenario

A library needs declaration files to be generated independently for each source file.

### 2.2 Preferred form

```typescript
// tsconfig.json
// { "compilerOptions": { "declaration": true, "isolatedDeclarations": true } }

export interface User {
  id: string;
  name: string;
}

export function createUser(id: string, name: string): User {
  return { id, name };
}
```

### 2.3 Hazardous form

```typescript
// tsconfig.json
// { "compilerOptions": { "declaration": true, "isolatedDeclarations": true } }

export const createUser = (id: string, name: string) => ({ id, name });

// This exported inferred object shape is rejected by isolatedDeclarations.
```

### 2.4 Why this difference matters

It makes declaration emit locally derivable and enables more parallel or third-party declaration-generation workflows.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
