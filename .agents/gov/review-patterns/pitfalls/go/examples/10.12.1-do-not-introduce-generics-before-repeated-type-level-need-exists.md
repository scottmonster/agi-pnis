# Do not introduce generics before repeated type-level need exists

## 1. Catalog record

- **Catalog identifier:** 10.12.1
- **Impact:** medium
- **Consensus:** medium
- **Definition:** Prefer ordinary functions or interfaces until the same algorithm genuinely needs to operate over multiple types or type-preserving containers.

## 2. Example

### 2.1 Scenario

A package has one concrete user lookup and no second type with the same type-preserving lookup requirements.

### 2.2 Preferred form

```go
package example

type User struct {
	ID string
}

func findUser(users []User, id string) (User, bool) {
	for _, user := range users {
		if user.ID == id {
			return user, true
		}
	}
	return User{}, false
}
```

### 2.3 Hazardous form

```go
package example

type Identified interface {
	ID() string
}

func find[T Identified](items []T, id string) (T, bool) {
	for _, item := range items {
		if item.ID() == id {
			return item, true
		}
	}
	var zero T
	return zero, false
}
```

### 2.4 Why this difference matters

The generic helper introduces a constraint and a broader public abstraction before there is evidence of a second use. A direct function makes the actual `User` contract easier to read and evolve.

## 3. Boundaries and distinctions

Introduce generics when multiple types genuinely share an algorithm and callers benefit from retaining their type. Do not duplicate concrete functions once that repeated need is established.
