# Ignoring deprecation warnings in test suites

## 1. Catalog record

- **Catalog identifier:** 13.2.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Configure development and test runs to surface relevant `DeprecationWarning` and other normally hidden warnings.

## 2. Example

### 2.1 Scenario

A test suite exercises a legacy helper that will be removed in a future Python or dependency release.

### 2.2 Preferred form

```python
import warnings


def legacy_helper() -> None:
    warnings.warn("legacy_helper is deprecated", DeprecationWarning, stacklevel=2)


with warnings.catch_warnings():
    warnings.simplefilter("error", DeprecationWarning)
    try:
        legacy_helper()
    except DeprecationWarning:
        print("replace the legacy helper before release")
```

### 2.3 Hazardous form

```python
import warnings


def legacy_helper() -> None:
    warnings.warn("legacy_helper is deprecated", DeprecationWarning, stacklevel=2)


with warnings.catch_warnings():
    warnings.simplefilter("ignore", DeprecationWarning)
    legacy_helper()
print("tests continued without exposing the warning")
```

### 2.4 Why this difference matters

Many deprecation warnings are hidden by default outside development contexts. A suite that suppresses a relevant warning can remain green until an upgrade turns it into a broken API.

## 3. Boundaries and distinctions

Do not blindly make every third-party warning fatal without triage. Configure filters that surface relevant warnings and explicitly manage justified exceptions.
