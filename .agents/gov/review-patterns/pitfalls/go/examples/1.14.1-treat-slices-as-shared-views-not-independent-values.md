# Treat slices as shared views, not independent values

## 1. Catalog record

- **Catalog identifier:** 1.14.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Copying a slice copies its descriptor, not its elements. Sub-slices commonly share the same backing array, and `append` can modify data visible through another slice when capacity permits.

## 2. Example

### 2.1 Scenario

A helper derives a small list from a caller-owned buffer and appends a marker.

### 2.2 Preferred form

```go
package main

func withMarker(source []string) []string {
	copyOfSource := append([]string(nil), source...)
	return append(copyOfSource, "marker")
}
```

### 2.3 Hazardous form

```go
package main

func withMarker(source []string) []string {
	view := source[:len(source):cap(source)]
	return append(view, "marker")
}
```

### 2.4 Why this difference matters

If the source has spare capacity, the hazardous append writes into its backing array and can alter memory the caller still observes. Copying creates independent storage.

## 3. Boundaries and distinctions

Sharing a backing array is useful for read-only views and intentional in-place algorithms. Cap a sub-slice at its length when it must not grow into the original array.
