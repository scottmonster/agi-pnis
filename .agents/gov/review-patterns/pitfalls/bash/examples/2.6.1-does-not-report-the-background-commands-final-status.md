# `&` does not report the background command's final status

## 1. Catalog record

- **Catalog identifier:** 2.6.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Starting a command with `&` only reports successful asynchronous launch semantics. Save its PID and use `wait` when the eventual success or failure matters.

## 2. Example

### 2.1 Scenario

A script starts an asynchronous report generator and must not publish a completion message unless the report finishes successfully.

### 2.2 Preferred form

```bash
#!/usr/bin/env bash
set -euo pipefail

generate_report > report.json &
report_pid=$!

wait "$report_pid"
printf 'report completed\n'
```

### 2.3 Hazardous form

```bash
#!/usr/bin/env bash
set -euo pipefail

generate_report > report.json &
printf 'report completed\n'
```

### 2.4 Why this difference matters

The status after `&` only tells the shell that it launched the asynchronous list. It does not show whether `generate_report` later succeeded, so the hazardous form can report success after a failed job.

## 3. Boundaries and distinctions

No `wait` is needed when the task is intentionally fire-and-forget and its result is irrelevant. Save `$!` immediately whenever the job's status or later control matters.
