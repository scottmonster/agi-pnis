# Force module treatment when files should never be global scripts

## 1. Catalog record

- **Catalog identifier:** 7.6.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Use `moduleDetection: "force"` or explicit module syntax in projects where source files should not contribute declarations to the global scope.

## 2. Example

### 2.1 Scenario

A service keeps small maintenance scripts in `src/`, but those files are implementation modules and must not add declarations to the shared global script scope.

### 2.2 Preferred form

```typescript
// tsconfig.json: { "compilerOptions": { "moduleDetection": "force" } }

// src/rebuild-search.ts
const startedAt = new Date();

// src/rebuild-thumbnails.ts
const startedAt = new Date(); // Separate module-local binding.
```

### 2.3 Hazardous form

```typescript
// moduleDetection: "auto" and neither file has import or export syntax.

// src/rebuild-search.ts
const startedAt = new Date();

// src/rebuild-thumbnails.ts
const startedAt = new Date(); // Cannot redeclare block-scoped variable 'startedAt'.
```

### 2.4 Why this difference matters

Files treated as scripts share a global declaration scope. An innocent top-level helper or `const` can then collide with a declaration in an unrelated file, and script declarations can accidentally become visible to every source file. Forcing module treatment gives each source file module scope even when it has no imports or exports yet.

## 3. Boundaries and distinctions

Use explicit `import` or `export` syntax when it communicates the file's dependency or public surface. `moduleDetection: "force"` is most useful for application and package source trees that should contain no legacy global scripts. Do not force it for projects that intentionally rely on global script declarations without first moving those declarations into properly scoped `.d.ts` files or modules.
