# `QueryRow` defers its error until `Scan`

## 1. Catalog record

- **Catalog identifier:** 9.10.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Always check the error returned by `QueryRow(...).Scan(...)`; do not expect `QueryRow` itself to report query errors.

## 2. Example

### 2.1 Scenario

A repository fetches an account balance that may be absent or may fail to query.

### 2.2 Preferred form

```go
package example

import (
	"context"
	"database/sql"
)

func balance(ctx context.Context, db *sql.DB, id int64) (int64, error) {
	var cents int64
	err := db.QueryRowContext(ctx, "SELECT balance FROM accounts WHERE id = $1", id).Scan(&cents)
	if err != nil { return 0, err }
	return cents, nil
}
```

### 2.3 Hazardous form

```go
package example

import (
	"context"
	"database/sql"
)

func balance(ctx context.Context, db *sql.DB, id int64) int64 {
	var cents int64
	db.QueryRowContext(ctx, "SELECT balance FROM accounts WHERE id = $1", id).Scan(&cents)
	return cents // Query and no-row errors become a zero balance.
}
```

### 2.4 Why this difference matters

`QueryRowContext` reports query, no-row, and scan errors from `Scan`. Ignoring that error can turn failure into plausible data.

## 3. Boundaries and distinctions

Handle `sql.ErrNoRows` explicitly when absence is normal. The important point is that every `Scan` result must be inspected.
