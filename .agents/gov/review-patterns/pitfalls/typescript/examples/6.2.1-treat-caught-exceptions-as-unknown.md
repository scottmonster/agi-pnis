# Treat caught exceptions as `unknown`

## 1. Catalog record

- **Catalog identifier:** 6.2.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Keep `useUnknownInCatchVariables` behavior and narrow caught values before assuming they are `Error` objects.

## 2. Example

### 2.1 Scenario

A request can fail with an Error or a non-Error thrown value.

### 2.2 Preferred form

```typescript
function messageFor(action: () => void): string {
  try {
    action();
    return 'ok';
  } catch (error: unknown) {
    return error instanceof Error ? error.message : 'Unknown failure';
  }
}

```

### 2.3 Hazardous form

```typescript
function messageFor(action: () => void): string {
  try {
    action();
    return 'ok';
  } catch (error: any) {
    return error.message.toUpperCase(); // `throw 'offline'` crashes here.
  }
}
```

### 2.4 Why this difference matters

JavaScript permits throwing any value, not just `Error`.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
