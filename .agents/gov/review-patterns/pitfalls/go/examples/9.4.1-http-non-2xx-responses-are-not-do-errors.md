# HTTP non-2xx responses are not `Do` errors

## 1. Catalog record

- **Catalog identifier:** 9.4.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Inspect `resp.StatusCode`; do not interpret `err == nil` as application-level success.

## 2. Example

### 2.1 Scenario

A client creates a remote invoice and must distinguish a successful transport from a rejected application request.

### 2.2 Preferred form

```go
package example

import (
	"fmt"
	"net/http"
)

func createInvoice(client *http.Client, req *http.Request) error {
	resp, err := client.Do(req)
	if err != nil { return err }
	defer resp.Body.Close()
	if resp.StatusCode != http.StatusCreated {
		return fmt.Errorf("invoice service returned %s", resp.Status)
	}
	return nil
}
```

### 2.3 Hazardous form

```go
package example

import "net/http"

func createInvoice(client *http.Client, req *http.Request) error {
	resp, err := client.Do(req)
	if err != nil { return err }
	defer resp.Body.Close()
	return nil // A 400 or 500 response reaches here as apparent success.
}
```

### 2.4 Why this difference matters

`Do` reports transport and protocol failures, not whether the server accepted the application operation. Ignoring status codes can acknowledge failed work.

## 3. Boundaries and distinctions

Define accepted status codes for the specific endpoint. Some APIs intentionally use several 2xx codes or return useful structured error bodies that callers should parse.
