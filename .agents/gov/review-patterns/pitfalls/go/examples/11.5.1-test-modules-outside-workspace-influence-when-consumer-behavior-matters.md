# Test modules outside workspace influence when consumer behavior matters

## 1. Catalog record

- **Catalog identifier:** 11.5.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Use `GOWORK=off` when verifying that an individual module works using only its own `go.mod`, especially before publishing.

## 2. Example

### 2.1 Scenario

A library imports a dependency that is also present in the repository workspace. Release validation must mimic an external consumer.

### 2.2 Preferred form

```go
package example

import "os/exec"

func standaloneTest() error {
	cmd := exec.Command("go", "test", "./...")
	cmd.Env = append(cmd.Environ(), "GOWORK=off")
	return cmd.Run()
}
```

### 2.3 Hazardous form

```go
package example

import "os/exec"

func workspaceTest() error {
	// An automatically discovered go.work can replace local modules.
	return exec.Command("go", "test", "./...").Run()
}
```

### 2.4 Why this difference matters

An enclosing `go.work` can select local replacements and versions that an external consumer does not have, masking a broken standalone module.

## 3. Boundaries and distinctions

Workspace testing remains valuable for repository integration. Disable it specifically when the question is whether one module's own `go.mod` is sufficient.
