# Avoid cyclic module dependencies that require early binding access

## 1. Catalog record

- **Catalog identifier:** 8.1.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Do not access cyclic imported bindings before their initialization.

## 2. Example

### 2.1 Scenario

Two application modules share a display label while the application starts.

### 2.2 Preferred form

```javascript
// app.js
import { formatSettings } from "./settings.js";

export const applicationName = "Portal";

console.log(formatSettings());

// settings.js
import { applicationName } from "./app.js";

export function formatSettings() {
  return `${applicationName} settings`;
}
```

### 2.3 Hazardous form

```javascript
// app.js
import { settingsLabel } from "./settings.js";

export const applicationName = "Portal";

console.log(settingsLabel);

// settings.js
import { applicationName } from "./app.js";

export const settingsLabel = `${applicationName} settings`;
```

### 2.4 Why this difference matters

The hazardous cycle reads `applicationName` while that export is still uninitialized, so module evaluation throws a temporal-dead-zone error.

## 3. Boundaries and distinctions

Cycles are not always wrong. A cycle is safe only when neither module needs the other's uninitialized binding during evaluation.
