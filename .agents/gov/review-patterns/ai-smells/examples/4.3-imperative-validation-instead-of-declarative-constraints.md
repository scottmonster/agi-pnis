# Imperative validation instead of declarative constraints

## 1. Catalog record

- **Catalog identifier:** 4.3
- **Evidence:** se
- **Definition:** Application code manually enforces what a schema, database constraint, type system, or framework rule can guarantee.

## 2. Scenario

### 2.1 Context

An agent adds a `status` field to an order model, where only `pending`, `paid`, and `cancelled` are valid values.

### 2.2 Safer approach

It declares the allowed values in the model schema and type definition, so all writers and readers share the same enforced contract.

### 2.3 Failure mode

It adds repeated `if` statements in selected request handlers and background jobs, leaving imports and future write paths able to persist arbitrary strings.

### 2.4 Why this difference matters

Declarative constraints protect every applicable path, whereas duplicated imperative checks are easy to omit or make inconsistent.

## 3. Boundaries and distinctions

Imperative validation remains useful for contextual rules that cannot be represented declaratively. This failure concerns guarantees a schema, constraint, type system, or framework rule can already provide.
