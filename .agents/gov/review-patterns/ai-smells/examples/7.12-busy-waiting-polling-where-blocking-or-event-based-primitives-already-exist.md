# Busy waiting/polling where blocking or event-based primitives already exist

## 1. Catalog record

- **Catalog identifier:** 7.12
- **Evidence:** se
- **Definition:** Repeatedly checks for a condition instead of waiting for notification or a bounded blocking operation.

## 2. Scenario

### 2.1 Context

An agent waits for a worker to place a completed result onto a queue.

### 2.2 Safer approach

It uses the queue's blocking receive with a timeout, or an event notification provided by the runtime.

### 2.3 Failure mode

It loops continuously, checking the queue and immediately checking again when it is empty.

### 2.4 Why this difference matters

The idle loop wastes CPU and can contend with useful work.

## 3. Boundaries and distinctions

Polling may be necessary for an external interface without events, but it should use an appropriate interval or bounded wait when blocking or event-based primitives already exist.
