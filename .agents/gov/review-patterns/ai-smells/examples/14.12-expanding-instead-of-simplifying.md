# Expanding instead of simplifying

## 1. Catalog record

- **Catalog identifier:** 14.12
- **Evidence:** a
- **Definition:** When uncertainty appears, the model adds options, abstractions, fallbacks, or layers instead of reducing the solution to what is actually known to be necessary.

## 2. Scenario

### 2.1 Context

An agent is unsure whether a new endpoint will eventually need several response formats, but the request specifies only one JSON response.

### 2.2 Safer approach

It implements the specified JSON response with a clear, small code path and records any unresolved future requirement for later confirmation.

### 2.3 Failure mode

It adds format negotiation, plugin hooks, fallback serializers, a response strategy hierarchy, and configuration flags to cover imagined cases.

### 2.4 Why this difference matters

The extra layers turn uncertainty into unverified behavior, increase the bug surface, and make the known requirement harder to maintain.

## 3. Boundaries and distinctions

Some uncertainty is resolved by required compatibility, a documented extension point, or a real fallback need. Simplification means retaining only what current evidence makes necessary.
