# Check Fetch HTTP status explicitly

## 1. Catalog record

- **Catalog identifier:** 10.1.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Check response.ok or status when HTTP failure is a failure for the operation.

## 2. Example

### 2.1 Scenario

A browser loads an account profile and must report a missing account instead of treating the response as usable data.

### 2.2 Preferred form

```javascript
async function loadProfile(accountId) {
  const response = await fetch(`/api/accounts/${encodeURIComponent(accountId)}`);
  if (!response.ok) {
    throw new Error(`Profile request failed with ${response.status}`);
  }
  return response.json();
}

loadProfile("missing").catch(console.error);
```

### 2.3 Hazardous form

```javascript
async function loadProfile(accountId) {
  const response = await fetch(`/api/accounts/${encodeURIComponent(accountId)}`);
  return response.json();
}

loadProfile("missing").catch(console.error);
```

### 2.4 Why this difference matters

`fetch()` resolves for HTTP error statuses such as 404 and 500. Without a status check, an error body can be handled as though it were a valid profile.

## 3. Boundaries and distinctions

Some APIs intentionally use non-2xx statuses as normal control flow. In that case, branch explicitly on the documented statuses rather than assuming every resolved fetch succeeded.
