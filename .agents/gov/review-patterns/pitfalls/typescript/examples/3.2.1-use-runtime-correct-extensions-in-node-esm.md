# Use runtime-correct extensions in Node ESM

## 1. Catalog record

- **Catalog identifier:** 3.2.1
- **Impact:** high
- **Consensus:** high
- **Definition:** In Node ESM source, write relative specifiers that will be valid in emitted JavaScript, commonly `./file.js`, rather than assuming TypeScript will rewrite extensionless or `.ts` imports.

## 2. Example

### 2.1 Scenario

A Node ESM source file imports a sibling that compiles from `.ts` to `.js`.

### 2.2 Preferred form

```typescript
// src/main.ts, emitted as dist/main.js
import { format } from './format.js';

console.log(format('ok'));

// src/format.ts
export function format(value: string): string {
  return value.toUpperCase();
}
```

### 2.3 Hazardous form

```typescript
// src/main.ts, emitted as dist/main.js
import { format } from './format';

console.log(format('ok'));

// Node resolves dist/format.js, not an extensionless module name.
```

### 2.4 Why this difference matters

Node ESM requires runtime-resolvable extensions and TypeScript normally preserves the module specifier.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
