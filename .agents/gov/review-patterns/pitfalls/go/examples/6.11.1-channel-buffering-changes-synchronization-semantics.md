# Channel buffering changes synchronization semantics

## 1. Catalog record

- **Catalog identifier:** 6.11.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Do not assume buffered and unbuffered channels establish identical ordering. Design synchronization according to the memory model, not intuition about sends.

## 2. Example

### 2.1 Scenario

A worker reports completion after all work is done.

### 2.2 Preferred form

```go
package main

import "fmt"

func main() {
	done := make(chan struct{})
	go func() {
		result := "complete"
		fmt.Println(result)
		close(done)
	}()
	<-done
}
```

### 2.3 Hazardous form

```go
package main

import "fmt"

func main() {
	ready := make(chan struct{}, 1)
	go func() {
		ready <- struct{}{}
		fmt.Println("work completed after the send")
	}()
	<-ready
}
```

### 2.4 Why this difference matters

A buffered send can finish before a receiver waits, so receiving it does not imply that subsequent work is complete. Synchronize at the event whose completion is needed.

## 3. Boundaries and distinctions

Buffered channels are useful bounded queues, but their capacity is part of the synchronization design.
