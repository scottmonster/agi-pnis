# Prefer recursive setTimeout when interval work may overrun

## 1. Catalog record

- **Catalog identifier:** 12.1.4
- **Impact:** medium
- **Consensus:** high
- **Definition:** Use completion-based scheduling when recurring work must finish before the next run starts.

## 2. Example

### 2.1 Scenario

A dashboard polls an API every five seconds, but each request may take longer than five seconds to finish.

### 2.2 Preferred form

```javascript
async function refreshDashboard() {
  try {
    const response = await fetch("/api/dashboard");
    if (!response.ok) throw new Error(`Request failed: ${response.status}`);
    const data = await response.json();
    document.querySelector(".status").textContent = data.status;
  } catch (error) {
    console.error("Dashboard refresh failed", error);
  } finally {
    setTimeout(refreshDashboard, 5_000);
  }
}

void refreshDashboard();
```

### 2.3 Hazardous form

```javascript
setInterval(async () => {
  const response = await fetch("/api/dashboard");
  const data = await response.json();
  document.querySelector(".status").textContent = data.status;
}, 5_000);
```

### 2.4 Why this difference matters

With `setInterval()`, a slow request can still be in flight when the next callback starts, producing overlapping requests and potentially rendering stale responses last.

## 3. Boundaries and distinctions

Completion-based scheduling adds the work duration to the interval between starts. Use a fixed-rate scheduler only when overlap is safe or intentionally managed, such as through cancellation or a single-flight guard.
