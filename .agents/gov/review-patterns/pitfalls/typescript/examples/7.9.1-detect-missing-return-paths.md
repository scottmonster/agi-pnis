# Detect missing return paths

## 1. Catalog record

- **Catalog identifier:** 7.9.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Consider `noImplicitReturns` for functions whose control paths are expected to return consistently.

## 2. Example

### 2.1 Scenario

A function maps a recognized request status to a user-facing label and promises a string result for every supported input.

### 2.2 Preferred form

```typescript
type Status = 'queued' | 'running' | 'complete';

function statusLabel(status: Status): string {
  switch (status) {
    case 'queued':
      return 'Waiting';
    case 'running':
      return 'In progress';
    case 'complete':
      return 'Done';
  }
}
```

### 2.3 Hazardous form

```typescript
type Status = 'queued' | 'running' | 'complete';

function statusLabel(status: Status): string | undefined {
  if (status === 'complete') {
    return 'Done';
  }

  // queued and running fall through unexpectedly
}
```

### 2.4 Why this difference matters

With `noImplicitReturns`, TypeScript reports functions where some code paths return a value and others fall through. That turns an accidental `undefined` result into a compile-time repair rather than a later caller failure.

## 3. Boundaries and distinctions

Use this for functions whose branches are intended to produce a result consistently, especially selectors, formatters, and request handlers. A function that intentionally sometimes produces no value should express that contract with `void` or `undefined` and make the fallthrough deliberate. This option does not prove that all possible code paths are semantically correct.
