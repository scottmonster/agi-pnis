# Remember utility inference over overloads uses the last signature

## 1. Catalog record

- **Catalog identifier:** 10.10.1
- **Impact:** low
- **Consensus:** high
- **Definition:** Do not expect conditional inference or utilities such as `ReturnType` to perform overload resolution for a hypothetical call; overloaded types are generally inferred from their final signature.

## 2. Example

### 2.1 Scenario

A parser turns a user-supplied identifier into either a date or a numeric database id.

### 2.2 Preferred form

```typescript
type ParsedValue<Kind extends "date" | "id"> = Kind extends "date" ? Date : number;

function parse<Kind extends "date" | "id">(input: string, kind: Kind): ParsedValue<Kind> {
  return (kind === "date" ? new Date(input) : Number(input)) as ParsedValue<Kind>;
}

type ParsedDate = ParsedValue<"date">;
const date: ParsedDate = parse("2026-01-01", "date");
```

### 2.3 Hazardous form

```typescript
function parse(input: string, kind: "date"): Date;
function parse(input: string, kind: "id"): number;
function parse(input: string, kind: "date" | "id"): Date | number;
function parse(input: string, kind: "date" | "id"): Date | number {
  return kind === "date" ? new Date(input) : Number(input);
}

type ParsedValue = ReturnType<typeof parse>; // Date | number from the final signature
const value: ParsedValue = 42;
```

### 2.4 Why this difference matters

`ReturnType` cannot choose an overload for a hypothetical argument. It infers from the last signature, so a broad final overload produces a broad result even when individual calls resolve more precisely.

## 3. Boundaries and distinctions

Overloads remain useful for call-site ergonomics. Use a generic mapping, separate function types, or another explicit type-level representation when later type computation needs a result for a particular overload.
