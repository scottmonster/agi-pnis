# Do not expect pipeline loop mutations to survive

## 1. Catalog record

- **Catalog identifier:** 2.4.1
- **Impact:** high
- **Consensus:** high
- **Definition:** In normal Bash execution, pipeline components execute in subshell environments, so assignments inside constructs such as `producer | while read ...` generally do not modify the parent shell. Prefer redirection or carefully designed process substitution when parent-state mutation is needed.

## 2. Example

### 2.1 Scenario

A script counts active service names and needs the final count after the loop completes.

### 2.2 Preferred form

```bash
#!/usr/bin/env bash
set -euo pipefail

count=0
while IFS= read -r service; do
  printf 'checking %s\n' "$service"
  ((count += 1))
done < <(printf '%s\n' api worker scheduler)

printf 'count=%d\n' "$count"
```

### 2.3 Hazardous form

```bash
#!/usr/bin/env bash
set -euo pipefail

count=0
printf '%s\n' api worker scheduler | while IFS= read -r service; do
  printf 'checking %s\n' "$service"
  ((count += 1))
done

printf 'count=%d\n' "$count"
```

### 2.4 Why this difference matters

The `while` loop in the pipeline runs in a subshell, so its incremented `count` is discarded when the pipeline ends. The preferred form keeps the loop in the current shell.

## 3. Boundaries and distinctions

Subshell isolation is useful when state changes should not escape. Bash's `lastpipe` option can alter final pipeline behavior under specific job-control conditions, so do not depend on it accidentally.
