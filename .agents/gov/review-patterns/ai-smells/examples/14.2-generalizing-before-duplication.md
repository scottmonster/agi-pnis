# Generalizing before duplication

## 1. Catalog record

- **Catalog identifier:** 14.2
- **Evidence:** a
- **Definition:** An abstraction appears before two genuine, stable examples demonstrate what should be abstracted.

## 2. Scenario

### 2.1 Context

An agent adds one webhook provider to a service that currently has no other provider integrations.

### 2.2 Safer approach

It implements the provider directly behind the existing application boundary, documenting any provider-specific choices so a later second case can inform a shared design.

### 2.3 Failure mode

It creates a provider registry, base adapter hierarchy, factory, plugin protocol, and generic event model for the single integration.

### 2.4 Why this difference matters

The speculative abstraction hardens guesses about future variation and makes the one supported path harder to understand and change.

## 3. Boundaries and distinctions

A real stable contract, such as a framework-required interface, can justify an abstraction with one implementation. The failure is inventing generality before genuine examples establish it.
