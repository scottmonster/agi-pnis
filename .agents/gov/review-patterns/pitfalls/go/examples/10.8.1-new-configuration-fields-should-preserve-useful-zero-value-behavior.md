# New configuration fields should preserve useful zero-value behavior

## 1. Catalog record

- **Catalog identifier:** 10.8.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** When extending an exported configuration struct, design new fields so their zero values normally preserve prior behavior unless a deliberate breaking change is being made.

## 2. Example

### 2.1 Scenario

A server adds a limit to an exported configuration type used by existing callers with a zero-value literal.

### 2.2 Preferred form

```go
package example

type Config struct {
	MaxConnections int // zero means the historical unlimited behavior
}

func connectionLimit(config Config) int {
	if config.MaxConnections == 0 {
		return -1
	}
	return config.MaxConnections
}
```

### 2.3 Hazardous form

```go
package example

type Config struct {
	MaxConnections int
}

func connectionLimit(config Config) int {
	return config.MaxConnections // old Config{} callers now allow no connections
}
```

### 2.4 Why this difference matters

Existing callers construct `Config{}` without knowledge of the new field. Treating its zero value as a restrictive limit changes their behavior despite retaining source compatibility.

## 3. Boundaries and distinctions

A non-zero default is valid when the prior API already documented a required configuration step or when a breaking change is intentional. Use a pointer or explicit enum if zero must mean a separate value.
