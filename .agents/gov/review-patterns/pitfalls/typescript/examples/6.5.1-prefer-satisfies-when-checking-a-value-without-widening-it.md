# Prefer `satisfies` when checking a value without widening it

## 1. Catalog record

- **Catalog identifier:** 6.5.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** For configuration objects, lookup tables, and similar values, use `satisfies` when you want structural validation while retaining the expression's precise inferred type.

## 2. Example

### 2.1 Scenario

A request table must satisfy its contract while retaining each endpoint's literal method.

### 2.2 Preferred form

```typescript
type Endpoint = { method: 'GET' | 'POST'; path: `/${string}` };

const endpoints = {
  health: { method: 'GET', path: '/health' },
  createUser: { method: 'POST', path: '/users' },
} satisfies Record<string, Endpoint>;

function endpointKey<Method extends 'GET' | 'POST'>(method: Method): `request:${Method}` {
  return `request:${method}` as `request:${Method}`;
}

const healthKey = endpointKey(endpoints.health.method); // "request:GET"
```

### 2.3 Hazardous form

```typescript
type Endpoint = { method: 'GET' | 'POST'; path: `/${string}` };

const endpoints: Record<string, Endpoint> = {
  health: { method: 'GET', path: '/health' },
  createUser: { method: 'POST', path: '/users' },
};

function endpointKey<Method extends 'GET' | 'POST'>(method: Method): `request:${Method}` {
  return `request:${method}` as `request:${Method}`;
}

const healthKey = endpointKey(endpoints.health.method);
// `healthKey` is "request:GET" | "request:POST", not the known literal value.
```

### 2.4 Why this difference matters

A broad annotation can discard useful literal information, while an assertion can suppress validation.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
