# Treat declaration files as trusted claims, not runtime proof

## 1. Catalog record

- **Catalog identifier:** 3.5.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Investigate and correct inaccurate `.d.ts` declarations instead of assuming that successful type checking proves the dependency behaves as declared.

## 2. Example

### 2.1 Scenario

A dependency declaration says a parser returns an object, but its JavaScript may not agree.

### 2.2 Preferred form

```typescript
// vendor.d.ts
declare function parseSettings(text: string): { retries: number };

function loadRetries(text: string): number {
  const settings = parseSettings(text);
  if (!Number.isInteger(settings.retries)) throw new Error('Invalid retries');
  return settings.retries;
}
```

### 2.3 Hazardous form

```typescript
// vendor.d.ts claims `{ retries: number }`, but the runtime returns `null`.
declare function parseSettings(text: string): { retries: number };

function loadRetries(text: string): number {
  return parseSettings(text).retries; // Type checking cannot prove runtime behavior.
}
```

### 2.4 Why this difference matters

A declaration file can describe behavior the JavaScript implementation does not actually provide.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
