# Use `const` type parameters when an API needs literal-preserving inference

## 1. Catalog record

- **Catalog identifier:** 8.8.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** For APIs that routinely require callers to write `as const`, consider a `const` type parameter with an appropriate readonly constraint.

## 2. Example

### 2.1 Scenario

A route helper needs to retain each literal segment without requiring callers to add `as const`.

### 2.2 Preferred form

```typescript
function defineRoute<const T extends readonly string[]>(segments: T): T {
  return segments;
}

const route = defineRoute(['users', ':id']);
const parameter: ':id' = route[1];
```

### 2.3 Hazardous form

```typescript
function defineRoute<T extends readonly string[]>(segments: T): T {
  return segments;
}

const route = defineRoute(['users', ':id']);
const parameter: ':id' = route[1]; // Error: route elements widened to string
```

### 2.4 Why this difference matters

It moves literal-preserving inference into the API contract and avoids relying on every caller to remember a const assertion.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
