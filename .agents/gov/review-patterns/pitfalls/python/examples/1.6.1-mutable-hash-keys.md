# Mutable hash keys

## 1. Catalog record

- **Catalog identifier:** 1.6.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Objects whose equality-relevant state can change should normally not be hashable. In particular, do not implement a hash that changes while the object is stored in a dict or set.

## 2. Example

### 2.1 Scenario

An application tracks active user IDs in a set while account profiles remain editable.

### 2.2 Preferred form

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class UserKey:
    user_id: str


active_users = {UserKey("ada")}
print(UserKey("ada") in active_users)
```

### 2.3 Hazardous form

```python
from dataclasses import dataclass


@dataclass
class UserKey:
    user_id: str

    def __hash__(self) -> int:
        return hash(self.user_id)


key = UserKey("ada")
active_users = {key}
key.user_id = "grace"
print(key in active_users)
```

### 2.4 Why this difference matters

After mutation, the hazardous key hashes to a different location, so set membership and removal can fail unexpectedly.

## 3. Boundaries and distinctions

Mutable objects can be hashable only when equality and hash use stable identity rather than their changing value, but value-based mutable keys are usually a design error.
