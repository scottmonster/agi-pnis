# Prefer explicit type-only imports with predictable emit

## 1. Catalog record

- **Catalog identifier:** 7.3.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Use `import type` and `export type`, commonly with `verbatimModuleSyntax`, when an import exists only for the type system.

## 2. Example

### 2.1 Scenario

A Node ESM summary module needs an invoice shape but no invoice runtime value.

### 2.2 Preferred form

```typescript
// src/summary.ts
import type { Invoice } from './invoice.js';

export function formatSummary(invoice: Invoice): string {
  return `${invoice.id}: ${invoice.total}`;
}

// src/invoice.ts
export interface Invoice {
  id: string;
  total: number;
}
```

### 2.3 Hazardous form

```typescript
// src/summary.ts
import { Invoice } from './invoice.js';

export function formatSummary(invoice: Invoice): string {
  return `${invoice.id}: ${invoice.total}`;
}

// src/invoice.ts
export interface Invoice {
  id: string;
  total: number;
}

// Import elision depends on compiler settings. With `verbatimModuleSyntax`, this is rejected.
```

### 2.4 Why this difference matters

It makes the runtime/type boundary explicit and avoids relying on complex import-elision inference.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
