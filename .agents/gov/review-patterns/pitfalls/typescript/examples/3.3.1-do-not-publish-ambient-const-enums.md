# Do not publish ambient `const enum`s

## 1. Catalog record

- **Catalog identifier:** 3.3.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Prefer ordinary enums, literal objects, or de-constified declarations when publishing library APIs instead of exposing ambient `const enum` values to consumers.

## 2. Example

### 2.1 Scenario

A library exposes named status values to downstream TypeScript consumers.

### 2.2 Preferred form

```typescript
export const OrderState = {
  Pending: 'pending',
  Paid: 'paid',
} as const;

export type OrderState = typeof OrderState[keyof typeof OrderState];

function isPaid(state: OrderState): boolean {
  return state === OrderState.Paid;
}
```

### 2.3 Hazardous form

```typescript
// index.d.ts published by a library
export declare const enum OrderState {
  Pending = 'pending',
  Paid = 'paid',
}

// Consumer output inlines "paid" from the version it compiled against.
const state = OrderState.Paid;
```

### 2.4 Why this difference matters

Consumers can inline values from one library version and execute another, and some isolated transpilation workflows cannot safely consume ambient const enums.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
