# Do not use `paths` to fake monorepo packages

## 1. Catalog record

- **Catalog identifier:** 7.16.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Use package-manager workspaces or actual package resolution for sibling packages rather than pointing `paths` directly into another package.

## 2. Example

### 2.1 Scenario

An application consumes a sibling workspace package and must behave the same way in development, tests, and its published build.

### 2.2 Preferred form

```typescript
// packages/text/package.json
// { "name": "@acme/text", "exports": { ".": "./dist/index.js" } }

// packages/app/src/main.ts
import { format } from '@acme/text';

console.log(format('ready'));

// packages/text/src/index.ts
export function format(value: string): string {
  return value.toUpperCase();
}
```

### 2.3 Hazardous form

```typescript
// packages/app/tsconfig.json
// { "compilerOptions": {
//   "paths": { "@acme/text": ["../text/src/index.ts"] }
// } }

// packages/app/src/main.ts
import { format } from '@acme/text';

console.log(format('ready'));

// The emitted JavaScript still imports "@acme/text", but no installed
// package, exports map, or runtime alias is guaranteed to resolve it.
```

### 2.4 Why this difference matters

`paths` only teaches the TypeScript checker where to find a source file. It does not rewrite the emitted module specifier or validate the sibling package's published `exports`, declaration files, and dependency boundaries. A workspace dependency exercises the package contract that consumers will actually use.

## 3. Boundaries and distinctions

`paths` is appropriate for a real runtime alias that every relevant tool resolves consistently, such as a bundler-controlled application alias. It is not a substitute for declaring a workspace dependency and building or linking the package. Test package consumption against its built output before publishing.
