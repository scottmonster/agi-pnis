# Refactor and behavior change mixed together unnecessarily

## 1. Catalog record

- **Catalog identifier:** 11.2
- **Evidence:** se
- **Definition:** Combines structural cleanup with a semantic change so reviewers cannot readily isolate the behavior under review.

## 2. Scenario

### 2.1 Context

A checkout fix must reject expired promotional codes.

### 2.2 Safer approach

The agent adds the expiration check and a regression test in a focused change, leaving payment-service restructuring for a separate review.

### 2.3 Failure mode

The same patch converts the payment service to a new class hierarchy while adding the expiration check.

### 2.4 Why this difference matters

Reviewers must reason about two independent risks at once and cannot readily identify which change caused a regression.

## 3. Boundaries and distinctions

Refactoring is appropriate when it is required to make the behavior safely implementable; avoid mixing discretionary cleanup with the semantic change.
