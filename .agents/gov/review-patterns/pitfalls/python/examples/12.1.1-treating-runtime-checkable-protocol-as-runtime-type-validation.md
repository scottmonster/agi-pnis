# Treating `@runtime_checkable Protocol` as runtime type validation

## 1. Catalog record

- **Catalog identifier:** 12.1.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Use runtime-checkable protocols only for shallow structural presence checks, not validation of complete method signatures or annotated types.

## 2. Example

### 2.1 Scenario

A plugin boundary receives an object that must expose a `write` method with a safe callable contract.

### 2.2 Preferred form

```python
from typing import Protocol

class Writer(Protocol):
    def write(self, message: str) -> None: ...

def send_message(writer: Writer, message: str) -> None:
    writer.write(message)
```

### 2.3 Hazardous form

```python
from typing import Protocol, runtime_checkable

@runtime_checkable
class Writer(Protocol):
    def write(self, message: str) -> None: ...

class BrokenWriter:
    def write(self, count: int) -> None:
        print(count)

print(isinstance(BrokenWriter(), Writer))
```

### 2.4 Why this difference matters

The runtime protocol check can succeed because `BrokenWriter` has an attribute named `write`, even though its method contract does not match the annotated protocol.

## 3. Boundaries and distinctions

Runtime-checkable protocols are useful for shallow capability checks. Validate external data and method contracts explicitly when runtime enforcement is required.
