# Do not copy synchronization objects after first use

## 1. Catalog record

- **Catalog identifier:** 1.16.1
- **Impact:** high
- **Consensus:** high
- **Definition:** `Mutex`, `RWMutex`, `WaitGroup`, `Once`, `Pool`, `Cond`, `sync.Map`, atomic wrapper types, and other documented no-copy synchronization objects must not be copied after use.

## 2. Example

### 2.1 Scenario

A counter type protects its state with a mutex.

### 2.2 Preferred form

```go
package main

import "sync"

type Counter struct {
	mu sync.Mutex
	n  int
}

func (c *Counter) Increment() {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.n++
}
```

### 2.3 Hazardous form

```go
package main

import "sync"

type Counter struct {
	mu sync.Mutex
	n  int
}

func (c Counter) Increment() {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.n++
}
```

### 2.4 Why this difference matters

The value receiver copies the mutex and counter on each call. Copies no longer coordinate with one another, and copying a lock after first use is invalid.

## 3. Boundaries and distinctions

Create independent synchronization objects only before they have been used. Prefer pointer receivers for types that contain a mutex or other no-copy synchronization state.
