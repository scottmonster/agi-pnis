# Thin “swappability” wrapper

## 1. Catalog record

- **Catalog identifier:** 3.13
- **Evidence:** se
- **Definition:** Pass-through wrapper exists solely because a database, HTTP client, SDK, or library might theoretically be replaced someday.

## 2. Scenario

### 2.1 Context

One service uses the platform HTTP client for a single API integration.

### 2.2 Safer approach

Use the client directly behind the service operation and test the integration boundary appropriately.

### 2.3 Failure mode

Create a wrapper whose methods only forward every client argument because the client might later change.

### 2.4 Why this difference matters

The wrapper becomes another API to maintain while preserving no meaningful policy or isolation.

## 3. Boundaries and distinctions

A wrapper is justified when it adds a current boundary, translation, ownership, or test seam; theoretical replacement alone is insufficient.
