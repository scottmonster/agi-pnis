# Do not mistake excess-property checks for exact object types

## 1. Catalog record

- **Catalog identifier:** 6.6.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Treat TypeScript object types as open structural contracts; assigning an object literal directly gets special excess-property checking, but equivalent values can contain additional runtime keys.

## 2. Example

### 2.1 Scenario

An API accepts a user payload only when it contains the two documented fields.

### 2.2 Preferred form

```typescript
type UserPayload = { id: string; name: string };

function isUserPayload(value: unknown): value is UserPayload {
  if (typeof value !== 'object' || value === null) return false;

  const keys = Object.keys(value);
  return keys.length === 2
    && keys.every((key) => key === 'id' || key === 'name')
    && typeof (value as Record<string, unknown>).id === 'string'
    && typeof (value as Record<string, unknown>).name === 'string';
}

const payload: unknown = { id: 'u1', name: 'Ada' };
if (isUserPayload(payload)) {
  console.log(payload.name);
}
```

### 2.3 Hazardous form

```typescript
type UserPayload = { id: string; name: string };

const received = { id: 'u1', name: 'Ada', role: 'admin' };
const payload: UserPayload = received;

console.log(Object.keys(payload)); // Runtime value still contains `role`.
```

### 2.4 Why this difference matters

Intermediate variables and structurally compatible objects can carry properties not listed in the target type.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
