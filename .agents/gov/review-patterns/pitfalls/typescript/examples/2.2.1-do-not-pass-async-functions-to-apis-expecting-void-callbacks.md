# Do not pass async functions to APIs expecting `void` callbacks

## 1. Catalog record

- **Catalog identifier:** 2.2.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Avoid `async` callbacks in `forEach`, event APIs, or other `() => void` positions unless the returned Promise is deliberately handled. Use an awaited loop, `Promise.all`, or explicit rejection handling instead.

## 2. Example

### 2.1 Scenario

A batch job must send a receipt for every completed order.

### 2.2 Preferred form

```typescript
async function sendReceipt(orderId: string): Promise<void> {
  await Promise.resolve();
}

async function notifyAll(orderIds: readonly string[]): Promise<void> {
  await Promise.all(orderIds.map(sendReceipt));
}
```

### 2.3 Hazardous form

```typescript
async function sendReceipt(orderId: string): Promise<void> {
  await Promise.resolve();
}

function notifyAll(orderIds: readonly string[]): void {
  orderIds.forEach(async (orderId) => {
    await sendReceipt(orderId);
  }); // forEach discards every returned Promise.
}
```

### 2.4 Why this difference matters

TypeScript permits value-returning functions in void-returning positions, so the Promise can be silently ignored.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
