# Do not rely on your module's `replace` directives propagating to consumers

## 1. Catalog record

- **Catalog identifier:** 11.4.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Test published modules without depending on replacements defined only by the developing main module or workspace.

## 2. Example

### 2.1 Scenario

During local development, the application replaces a library dependency with a sibling checkout. The library itself must still work for an external consumer.

### 2.2 Preferred form

```go
package example

import "example.com/codec"

func preferred(input string) (string, error) {
	// The published module requires a real codec version in its own go.mod.
	return codec.Encode(input)
}
```

### 2.3 Hazardous form

```go
package example

import "example.com/codec"

func hazardous(input string) (string, error) {
	// This only works while the developer's main module has:
	// replace example.com/codec => ../codec
	return codec.EncodeExperimental(input)
}
```

### 2.4 Why this difference matters

`replace` directives apply to a main module or workspace, not downstream consumers. A consumer resolves the library's declared requirements instead.

## 3. Boundaries and distinctions

Local replacements are useful for development and integration testing. They are not a mechanism for publishing a dependency or changing a consumer's module graph.
