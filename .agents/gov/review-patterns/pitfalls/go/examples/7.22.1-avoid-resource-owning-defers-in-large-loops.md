# Avoid resource-owning defers in large loops

## 1. Catalog record

- **Catalog identifier:** 7.22.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** A `defer` runs when the surrounding function returns, not when a loop iteration ends. Put an iteration in a helper function or close explicitly when resources need to be released each iteration.

## 2. Example

### 2.1 Scenario

A batch importer opens one file per input path and may process thousands of paths.

### 2.2 Preferred form

```go
package batch

import "os"

func process(paths []string) error {
	for _, path := range paths {
		if err := processOne(path); err != nil { return err }
	}
	return nil
}

func processOne(path string) error {
	file, err := os.Open(path)
	if err != nil { return err }
	defer file.Close()
	return nil
}
```

### 2.3 Hazardous form

```go
package batch

import "os"

func process(paths []string) error {
	for _, path := range paths {
		file, err := os.Open(path)
		if err != nil { return err }
		defer file.Close() // All files remain open until process returns.
	}
	return nil
}
```

### 2.4 Why this difference matters

The hazardous loop accumulates open descriptors and can exhaust process resources before the function returns.

## 3. Boundaries and distinctions

Deferring in a small bounded loop is often clear and safe. The concern is resources retained across a materially large or unbounded number of iterations.
