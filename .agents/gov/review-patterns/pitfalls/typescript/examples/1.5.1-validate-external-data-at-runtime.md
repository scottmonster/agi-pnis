# Validate external data at runtime

## 1. Catalog record

- **Catalog identifier:** 1.5.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Parse and validate JSON, API responses, environment data, storage values, and other external inputs instead of asserting that they match TypeScript interfaces.

## 2. Example

### 2.1 Scenario

An HTTP response is parsed from JSON before being used as a user record.

### 2.2 Preferred form

```typescript
type User = { id: string; displayName: string };

function parseUser(value: unknown): User {
  if (
    typeof value === 'object' && value !== null &&
    'id' in value && typeof value.id === 'string' &&
    'displayName' in value && typeof value.displayName === 'string'
  ) {
    return { id: value.id, displayName: value.displayName };
  }
  throw new Error('Invalid user response');
}
```

### 2.3 Hazardous form

```typescript
type User = { id: string; displayName: string };

function parseUser(value: unknown): User {
  return value as User; // JSON can still be missing either field.
}
```

### 2.4 Why this difference matters

TypeScript types are erased and provide no runtime validation, so an asserted external value can violate its declared type without the checker knowing.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
