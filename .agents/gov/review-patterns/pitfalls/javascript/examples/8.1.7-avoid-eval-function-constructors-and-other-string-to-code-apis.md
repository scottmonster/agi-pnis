# Avoid eval, Function constructors, and other string-to-code APIs

## 1. Catalog record

- **Catalog identifier:** 8.1.7
- **Impact:** high
- **Consensus:** high
- **Definition:** Do not execute constructed code strings when ordinary functions or data can express the behavior.

## 2. Example

### 2.1 Scenario

A settings page lets a user choose one of a fixed set of display themes.

### 2.2 Preferred form

```javascript
const themes = {
  dark: () => "dark",
  light: () => "light",
};

function selectTheme(name) {
  const applyTheme = themes[name];
  if (!applyTheme) {
    throw new Error("Unknown theme");
  }
  return applyTheme();
}

console.log(selectTheme("dark"));
```

### 2.3 Hazardous form

```javascript
function selectTheme(name) {
  return eval(`apply${name}Theme()`);
}

function applydarkTheme() {
  return "dark";
}

console.log(selectTheme("dark"));
```

### 2.4 Why this difference matters

The hazardous version turns input into executable source. Malicious or malformed input can execute unintended code, and ordinary refactoring tools cannot safely follow the constructed call.

## 3. Boundaries and distinctions

Some tools deliberately compile source under a tightly controlled boundary, but application input should remain data and use explicit parsing or dispatch.
