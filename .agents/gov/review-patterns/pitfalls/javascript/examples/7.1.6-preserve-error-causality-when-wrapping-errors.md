# Preserve error causality when wrapping errors

## 1. Catalog record

- **Catalog identifier:** 7.1.6
- **Impact:** medium
- **Consensus:** high
- **Definition:** When converting a lower-level failure into a higher-level `Error`, preserve the original with the `cause` option when it provides useful diagnostic context.

## 2. Example

### 2.1 Scenario

A configuration loader adds application context to an error raised while reading a file.

### 2.2 Preferred form

```javascript
async function readFile() {
  throw new Error("permission denied");
}

async function loadConfig() {
  try {
    return await readFile();
  } catch (error) {
    throw new Error("could not load application config", { cause: error });
  }
}

loadConfig().catch((error) => console.error(error.message, error.cause.message));
```

### 2.3 Hazardous form

```javascript
async function readFile() {
  throw new Error("permission denied");
}

async function loadConfig() {
  try {
    return await readFile();
  } catch (error) {
    throw new Error("could not load application config");
  }
}

loadConfig().catch(console.error);
```

### 2.4 Why this difference matters

The hazardous wrapper hides the lower-level reason, making a production failure harder to trace to its source.

## 3. Boundaries and distinctions

Preserve a cause when it adds useful diagnostic context, while avoiding exposure of sensitive lower-level details to untrusted callers.
