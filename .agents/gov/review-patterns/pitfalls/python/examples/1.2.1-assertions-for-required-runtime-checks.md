# Assertions for required runtime checks

## 1. Catalog record

- **Catalog identifier:** 1.2.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Do not use `assert` for input validation, authorization, security checks, or other behavior required for correctness. Use explicit condition checks and raise an appropriate exception.

## 2. Example

### 2.1 Scenario

An API endpoint must reject a request that lacks an authenticated user.

### 2.2 Preferred form

```python
def delete_account(user_id: str | None) -> str:
    if user_id is None:
        raise PermissionError("authentication required")
    return f"deleted account for {user_id}"


print(delete_account("ada"))
```

### 2.3 Hazardous form

```python
def delete_account(user_id: str | None) -> str:
    assert user_id is not None, "authentication required"
    return f"deleted account for {user_id}"


print(delete_account("ada"))
```

### 2.4 Why this difference matters

Python can remove assertions with optimization, so the hazardous authorization check may disappear in production.

## 3. Boundaries and distinctions

Assertions remain useful for developer-facing invariants that need not be enforced when Python runs with optimizations.
