# Clear reused maps before JSON decoding when stale keys are invalid

## 1. Catalog record

- **Catalog identifier:** 10.1.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Decode into a new map, or clear an existing map first, when keys omitted by the new JSON document should disappear.

## 2. Example

### 2.1 Scenario

A configuration watcher reuses a map for successive full snapshots, where an omitted permission must be removed.

### 2.2 Preferred form

```go
package example

import "encoding/json"

func decodeSnapshot(data []byte, permissions map[string]bool) error {
	clear(permissions)
	return json.Unmarshal(data, &permissions)
}
```

### 2.3 Hazardous form

```go
package example

import "encoding/json"

func decodeSnapshot(data []byte, permissions map[string]bool) error {
	return json.Unmarshal(data, &permissions)
}

func example() (bool, error) {
	permissions := map[string]bool{"admin": true}
	err := decodeSnapshot([]byte(`{"reader":true}`), permissions)
	return permissions["admin"], err // stale admin key remains true
}
```

### 2.4 Why this difference matters

Unmarshaling into a non-nil map retains keys absent from the new document. The hazardous code can preserve revoked permissions from an old snapshot.

## 3. Boundaries and distinctions

Do not clear a map when each document is an intentional patch that inherits unspecified keys. Allocating a new map is equally suitable for replacement snapshots.
