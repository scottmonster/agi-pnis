# Assuming `final` is runtime enforcement

## 1. Catalog record

- **Catalog identifier:** 16.18.1
- **Impact:** low
- **Consensus:** high
- **Definition:** Treat `@final` primarily as a static type-checker contract rather than a runtime mechanism preventing inheritance or overriding.

## 2. Example

### 2.1 Scenario

A library marks a serialization method as final and wants downstream implementations to respect that API decision.

### 2.2 Preferred form

```python
from typing import final


class Message:
    @final
    def serialize(self) -> str:
        return "message"


class CustomMessage(Message):
    pass


print(CustomMessage().serialize())
```

### 2.3 Hazardous form

```python
from typing import final


class Message:
    @final
    def serialize(self) -> str:
        return "message"


class CustomMessage(Message):
    def serialize(self) -> str:
        return "custom"


print(CustomMessage().serialize())
```

### 2.4 Why this difference matters

Python still dispatches to the overriding method in the hazardous form. A type checker can flag the override, but the decorator itself does not block class construction or runtime dispatch.

## 3. Boundaries and distinctions

`@final` communicates a valuable static contract when projects run a compatible type checker. Use an explicit runtime design, such as composition or validation, when enforcement at runtime is required.
