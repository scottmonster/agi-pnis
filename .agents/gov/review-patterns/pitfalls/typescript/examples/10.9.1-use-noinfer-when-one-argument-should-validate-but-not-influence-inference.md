# Use `NoInfer` when one argument should validate but not influence inference

## 1. Catalog record

- **Catalog identifier:** 10.9.1
- **Impact:** low
- **Consensus:** high
- **Definition:** Use `NoInfer<T>` for secondary inputs such as defaults that must conform to a type inferred elsewhere but should not widen that inferred type.

## 2. Example

### 2.1 Scenario

A traffic-light factory accepts the allowed colors and an optional default that must be one of those colors.

### 2.2 Preferred form

```typescript
function createLight<Color extends string>(
  colors: readonly Color[],
  defaultColor?: NoInfer<Color>,
): { colors: readonly Color[]; defaultColor?: Color } {
  return { colors, defaultColor };
}

const light = createLight(["red", "yellow", "green"] as const, "red");
// @ts-expect-error "blue" cannot influence Color inference.
createLight(["red", "yellow", "green"] as const, "blue");
```

### 2.3 Hazardous form

```typescript
function createLight<Color extends string>(
  colors: readonly Color[],
  defaultColor?: Color,
): { colors: readonly Color[]; defaultColor?: Color } {
  return { colors, defaultColor };
}

const light = createLight(["red", "yellow", "green"] as const, "blue");
// Color widens to include "blue", even though blue is not an allowed color.
```

### 2.4 Why this difference matters

Without `NoInfer`, the default is another inference candidate. Its invalid value can widen the generic type enough to pass validation and create an object whose default is absent from its allowed values.

## 3. Boundaries and distinctions

Use `NoInfer` only when one argument is deliberately secondary to an inference source. If multiple arguments are meant to jointly determine the type, allow ordinary inference from all of them.
