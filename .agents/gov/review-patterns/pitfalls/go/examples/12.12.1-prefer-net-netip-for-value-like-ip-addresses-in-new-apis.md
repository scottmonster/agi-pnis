# Prefer `net/netip` for value-like IP addresses in new APIs

## 1. Catalog record

- **Catalog identifier:** 12.12.1
- **Impact:** medium
- **Consensus:** medium
- **Definition:** When compatibility constraints do not require `net.IP`, consider `netip.Addr` for application-level IP storage and comparison.

## 2. Example

### 2.1 Scenario

An access-control component stores client IP addresses in an allowlist. It needs stable value comparisons and should not let callers mutate stored addresses.

### 2.2 Preferred form

```go
package example

import "net/netip"

type Allowlist struct {
	addresses map[netip.Addr]struct{}
}

func (a *Allowlist) Add(raw string) error {
	addr, err := netip.ParseAddr(raw)
	if err != nil {
		return err
	}
	if a.addresses == nil {
		a.addresses = make(map[netip.Addr]struct{})
	}
	a.addresses[addr.Unmap()] = struct{}{}
	return nil
}

func (a *Allowlist) Contains(raw string) bool {
	addr, err := netip.ParseAddr(raw)
	if err != nil {
		return false
	}
	_, ok := a.addresses[addr.Unmap()]
	return ok
}
```

### 2.3 Hazardous form

```go
package example

import "net"

type LegacyAllowlist struct {
	addresses []net.IP
}

func (a *LegacyAllowlist) Add(addr net.IP) {
	// net.IP is a mutable byte slice, so the caller can change stored state.
	a.addresses = append(a.addresses, addr)
}
```

### 2.4 Why this difference matters

`netip.Addr` is a comparable, immutable value suitable for map keys and value-oriented APIs. `net.IP` is a byte slice, so it cannot be a map key and copied slices can still share mutable address bytes.

## 3. Boundaries and distinctions

Keep using `net.IP` where an existing public API, dependency, or wire-facing interface requires it. Convert at the boundary rather than forcing a broad compatibility-breaking migration.
