# Avoid `eval` for data-driven command construction

## 1. Catalog record

- **Catalog identifier:** 1.6.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Do not pass data, especially untrusted data, through `eval` merely to build commands, indirect assignments, or argument lists. Prefer arrays, associative arrays, namerefs where safe, or explicit dispatch.

## 2. Example

### 2.1 Scenario

A script selects one of a fixed set of maintenance actions from a command-line value.

### 2.2 Preferred form

```bash
#!/usr/bin/env bash

action=${1:-}

case $action in
  status)
    systemctl status my-service
    ;;
  restart)
    systemctl restart my-service
    ;;
  *)
    printf 'unknown action: %s\n' "$action" >&2
    exit 2
    ;;
esac
```

### 2.3 Hazardous form

```bash
#!/usr/bin/env bash

action=${1:-}
command="systemctl $action my-service"

eval "$command"
```

### 2.4 Why this difference matters

The explicit dispatch keeps the supplied value as data and permits only known actions. `eval` parses the constructed text again, so shell metacharacters in the value can become executable syntax.

## 3. Boundaries and distinctions

Indirect variable access can sometimes be needed inside controlled Bash code, but names must be constrained first. `eval` is not needed merely because a command, variable name, or argument list is chosen at runtime.
