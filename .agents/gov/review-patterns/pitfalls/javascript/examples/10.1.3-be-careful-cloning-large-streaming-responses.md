# Be careful cloning large streaming responses

## 1. Catalog record

- **Catalog identifier:** 10.1.3
- **Impact:** medium
- **Consensus:** high
- **Definition:** Avoid cloning large streaming bodies with uneven consumers when unbounded buffering is unacceptable.

## 2. Example

### 2.1 Scenario

A browser downloads a large export that the user saves immediately; diagnostic logging is optional.

### 2.2 Preferred form

```javascript
async function downloadExport() {
  const response = await fetch("/api/export");
  if (!response.ok) throw new Error(`Export failed: ${response.status}`);

  const file = await response.blob();
  console.log(`Downloaded ${file.size} bytes`);
  return file;
}

downloadExport().catch(console.error);
```

### 2.3 Hazardous form

```javascript
async function downloadExport() {
  const response = await fetch("/api/export");
  const auditCopy = response.clone();
  const file = await response.blob();
  const auditText = await auditCopy.text();
  console.log(auditText.length);
  return file;
}

downloadExport().catch(console.error);
```

### 2.4 Why this difference matters

Cloning tees the response stream. If one consumer falls behind or is unnecessary, the browser may need to buffer a large amount of data for it.

## 3. Boundaries and distinctions

Cloning is reasonable for small, bounded responses with two necessary consumers. For large exports, log metadata or have the server produce a separate audit artifact instead.
