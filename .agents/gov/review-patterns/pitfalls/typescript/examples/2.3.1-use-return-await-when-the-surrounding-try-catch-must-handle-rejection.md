# Use `return await` when the surrounding `try`/`catch` must handle rejection

## 1. Catalog record

- **Catalog identifier:** 2.3.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Inside an error-handling context, use `return await promise` when a rejection is supposed to be caught locally rather than directly returning the Promise.

## 2. Example

### 2.1 Scenario

A publishing operation should translate a remote rejection into a local fallback.

### 2.2 Preferred form

```typescript
type PublishResult = { url: string };

declare function publishRemotely(): Promise<PublishResult>;

async function publish(): Promise<PublishResult> {
  try {
    return await publishRemotely();
  } catch {
    return { url: '/drafts/pending' };
  }
}
```

### 2.3 Hazardous form

```typescript
type PublishResult = { url: string };

declare function publishRemotely(): Promise<PublishResult>;

async function publish(): Promise<PublishResult> {
  try {
    return publishRemotely();
  } catch {
    return { url: '/drafts/pending' };
  }
}
```

### 2.4 Why this difference matters

Returning the Promise without awaiting it lets its later rejection escape the surrounding `catch`.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
