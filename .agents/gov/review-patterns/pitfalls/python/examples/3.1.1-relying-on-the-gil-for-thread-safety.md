# Relying on the GIL for thread safety

## 1. Catalog record

- **Catalog identifier:** 3.1.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Do not design correctness around the assumption that CPython's GIL implicitly serializes shared mutable state. Use explicit synchronization or ownership boundaries.

## 2. Example

### 2.1 Scenario

Worker threads record completed jobs in a shared counter. The application needs a portable correctness guarantee.

### 2.2 Preferred form

```python
from threading import Lock


class JobCounter:
    def __init__(self) -> None:
        self._completed = 0
        self._lock = Lock()

    def record_completion(self) -> None:
        with self._lock:
            self._completed += 1

    def value(self) -> int:
        with self._lock:
            return self._completed
```

### 2.3 Hazardous form

```python
class JobCounter:
    def __init__(self) -> None:
        self.completed = 0

    def record_completion(self) -> None:
        self.completed += 1
```

### 2.4 Why this difference matters

The GIL is an implementation detail and does not make shared-state invariants a sound concurrency design. The unsynchronized increment can lose updates under interleaving or on runtimes with different execution behavior.

## 3. Boundaries and distinctions

The GIL can affect performance and some implementation details in CPython, but it is not a substitute for synchronization when correctness depends on coordinated access.
