# Avoid accidental switch fallthrough

## 1. Catalog record

- **Catalog identifier:** 1.1.18
- **Impact:** medium
- **Consensus:** high
- **Definition:** End a `case` with `break`, `return`, `throw`, or another explicit control transfer unless fallthrough is intentional and clear.

## 2. Example

### 2.1 Scenario

An order status determines one notification message.

### 2.2 Preferred form

```javascript
function notificationFor(status) {
  switch (status) {
    case "paid":
      return "receipt sent";
    case "shipped":
      return "tracking sent";
    default:
      return "no notification";
  }
}

console.log(notificationFor("paid"));
```

### 2.3 Hazardous form

```javascript
function notificationFor(status) {
  let message = "";

  switch (status) {
    case "paid":
      message = "receipt sent";
    case "shipped":
      message = "tracking sent";
      break;
    default:
      message = "no notification";
  }

  return message;
}

console.log(notificationFor("paid"));
```

### 2.4 Why this difference matters

Without a terminating control transfer, the `paid` case continues into `shipped` and overwrites the intended message.

## 3. Boundaries and distinctions

Fallthrough can be valid when multiple cases intentionally share behavior, but it should be explicit and readily visible.
