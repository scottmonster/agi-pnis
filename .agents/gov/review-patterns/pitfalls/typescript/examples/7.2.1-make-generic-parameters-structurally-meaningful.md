# Make generic parameters structurally meaningful

## 1. Catalog record

- **Catalog identifier:** 7.2.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Do not expect `Thing<A>` and `Thing<B>` to be distinct if `Thing<T>` never uses `T` in its structure.

## 2. Example

### 2.1 Scenario

A data access layer keeps user records separate from invoice records.

### 2.2 Preferred form

```typescript
type User = { id: string; email: string };
type Invoice = { id: string; total: number };

interface Repository<T> {
  find(id: string): T | undefined;
  save(value: T): void;
}

declare const users: Repository<User>;
const user = users.find('user_1');
if (user) console.log(user.email);
```

### 2.3 Hazardous form

```typescript
type User = { id: string; email: string };
type Invoice = { id: string; total: number };

interface Repository<T> {
  find(id: string): unknown;
}

declare const users: Repository<User>;
const invoices: Repository<Invoice> = users;
// `T` is absent from the structure, so both repository types are identical.
```

### 2.4 Why this difference matters

TypeScript is structural, so an unused phantom type parameter has no effect on assignability unless represented by a member or brand.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
