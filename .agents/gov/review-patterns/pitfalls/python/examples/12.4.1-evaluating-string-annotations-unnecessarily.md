# Evaluating string annotations unnecessarily

## 1. Catalog record

- **Catalog identifier:** 12.4.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Avoid enabling annotation string evaluation unless actual Python values are required. Prefer string or forward-reference formats for introspection where possible.

## 2. Example

### 2.1 Scenario

A documentation generator displays the parameter type for a function with a forward reference.

### 2.2 Preferred form

```python
from annotationlib import Format, get_annotations


def connect(client: "RemoteClient") -> None:
    print(client)


annotations = get_annotations(connect, format=Format.STRING)
print(annotations["client"])
```

### 2.3 Hazardous form

```python
from annotationlib import Format, get_annotations


def connect(client: "RemoteClient") -> None:
    print(client)


annotations = get_annotations(connect, format=Format.VALUE)
print(annotations["client"])
```

### 2.4 Why this difference matters

Resolving annotations can import names, fail because a forward reference is unavailable, and evaluate expressions that a documentation-only consumer did not need.

## 3. Boundaries and distinctions

Choose value format when the consumer genuinely requires runtime type objects, such as a validator that deliberately resolves them. Keep string or forward-reference forms for display and deferred analysis.
