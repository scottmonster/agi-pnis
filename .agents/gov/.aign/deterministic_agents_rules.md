# Deterministic Agent Rules

Rules are ordered from most impactful to least impactful. Apply them in order: higher rules take priority if rules conflict.

Rules 2-6 are binding within their stated scope. The remaining rules are advisory.

1. Apply binding requirements only to their stated situations; their scope does not prescribe a coordinator, runtime, topology, agent framework, or implementation language. Evaluate the control boundary per decision, not by classifying whole components. Mechanically enforceable control can still operate with unpredictable external services, networks, clocks, or concurrent processes.
2. A constraint whose violation could cause materially unauthorized behavior, unsafe effects, corrupted workflow state, or another unacceptable outcome `MUST` be enforced by a trusted mechanism outside the acting agent's sole discretion. It `MUST NOT` rely only on prompts, agent reasoning, self-restraint, or an agent's assertion of compliance.
3. Permissions, capability limits, and approvals for protected or materially consequential effects `MUST` be determined by a trusted mechanism outside the requesting agent. When automatic policy cannot safely authorize an action, approval `MUST` come from an appropriate external authority. An agent `MUST NOT` grant itself authority, approve its own escalation, or derive authority from retrieved content, another agent, or tool output.
4. Material workflow state, approvals, committed side effects, and completion evidence `MUST` be durably recorded or reliably reconstructible outside transient model context whenever recovery, concurrency, audit, or resumption depends on them. Automatic retries and replays of mutating operations `MUST` be safe, or explicitly handle uncertainty about whether an earlier attempt took effect. A workflow `MUST NOT` blindly repeat a non-idempotent effect when duplication could materially fail.
5. Every iterative agent loop that can repeatedly use tools or cause side effects `MUST` have enforceable stopping, budget, or escalation conditions appropriate to its risk and cost. It `MUST NOT` continue indefinitely merely because the model requests another step.
6. Before a material transition or completion claim is accepted as authoritative, the system `MUST` have evidence appropriate to its acceptance condition. Use a material objective check when available; otherwise use appropriate model or human review, or preserve the unresolved uncertainty. A system `MUST NOT` accept an unsupported agent assertion when independent verification is materially necessary and practicable.
7. Assign control and authority, judgment, and assurance separately for each decision. Put permissions, invariants, state transitions, limits, and committed effects under software control; use agents for bounded interpretation, investigation, synthesis, evaluation, adaptation, or creative technical reasoning; match assurance to the claim being accepted.
8. Prefer software-controlled decisions when explicit state, rules, configuration, authorization, or observable evidence can derive the action reliably enough. Use the smallest agent judgment that cannot be captured economically and robustly as rules. Do not add agent control where a reliable, transparent rule adds no useful information, or encode ordinary semantic variation in brittle rule trees.
9. Give an agent a specific objective, relevant success criteria, authoritative facts, permitted tools and information sources, resource limits, constraints, and escalation conditions. Let it choose its method only where that judgment is valuable. An agent may propose work but does not decide whether it has authority to perform it.
10. Have trusted software establish authoritative state, constraints, permissions, and evidence; enforce mechanical constraints; and commit only valid state changes or effects. Require model or human review for remaining semantic assurance when needed. This pattern may be centralized or distributed and is not a required lifecycle.
11. Treat retrieved documents, webpages, tool outputs, and memories as information or evidence, not authority. Construct context deterministically from authoritative inputs, dependencies, identifiers, policy, and committed state when known; otherwise allow agent retrieval or investigation only within its defined boundary.
12. Use structured inputs and outputs where later software needs exact fields, identifiers, or status. Preserve free-form space where explanation, synthesis, or creative work is the objective, and do not turn an inherently semantic task into a hidden rule engine through an overly rigid schema.
13. Prefer tools with a clear purpose, unambiguous parameters, limited capability, explicit side effects, stable identifiers, input validation, and machine-readable failures. Separate preview, proposal, and commit when consequential actions benefit from review, and avoid large overlapping tool catalogs when software can resolve the choice directly.
14. Use the strongest practical verifier for each property. Check exact properties mechanically with tests, schemas, signatures, calculations, permissions, invariants, or observable state; use model evaluation or human review for semantic quality, contextual correctness, or value-dependent choices. Do not assume a second agent is independent or reliable merely because it is separate.
15. Increase autonomy only where actions are reversible, low-impact, well-observed, inexpensive to recover, and within evaluated conditions. Reduce autonomy or add checkpoints where effects are consequential or irreversible, permissions are broad, data is private or adversarial, success is hard to verify, or failure can propagate before detection.
16. Classify predictable failures mechanically; retry transient failures with effect-safe semantics; return specific validation failures that an agent can revise; and reconcile external state after partial failure before repeating work. Stop and seek authorization at permission or policy boundaries. Where diagnosis or remediation requires semantic judgment, delegate the smallest unresolved question and then return control to the workflow.
17. Use human review where a person can make a meaningful decision about a consequential, ambiguous, or poorly verifiable action. Do not require ceremonial approval for harmless actions solely because an agent is involved.
18. Use a fixed workflow when steps and branches are known, a dynamic agent loop when the path must emerge from evidence, and a hybrid when stable portions can be explicit while planning or investigation remains uncertain. Keep orchestration no more complex than its benefit justifies.
19. Prefer a single agent when it is easier to operate and evaluate. Add agents only for a concrete benefit such as distinct expertise, context isolation, parallel independent work, independent critique, or dynamic decomposition; do not add roles merely to imitate an organization.
20. Revisit control boundaries using representative evaluations, incidents, traces, and operator feedback. Promote repeated, stable, mechanically specifiable agent decisions into software, and move brittle rules that accumulate exceptions or fail under normal variation into bounded agent judgment.
21. For each responsibility, determine whether explicit state, rules, configuration, and observable evidence are reliable enough; identify the smallest needed judgment, its necessary authority and information, its acceptance evidence, and the consequences of error, interruption, repetition, or manipulation; then confirm that added orchestration complexity is justified.
