# Losing references to background asyncio tasks

## 1. Catalog record

- **Catalog identifier:** 3.12.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Keep strong references to independently scheduled tasks, or preferably use `TaskGroup` when tasks belong to one operation.

## 2. Example

### 2.1 Scenario

An async request launches notification tasks that belong to one batch. The request must wait for the batch and surface any failures.

### 2.2 Preferred form

```python
import asyncio


async def notify(address: str) -> None:
    await asyncio.sleep(0)
    print(f"notified {address}")


async def notify_all(addresses: list[str]) -> None:
    async with asyncio.TaskGroup() as group:
        for address in addresses:
            group.create_task(notify(address))


asyncio.run(notify_all(["a@example.com", "b@example.com"]))
```

### 2.3 Hazardous form

```python
import asyncio


async def notify(address: str) -> None:
    await asyncio.sleep(0)
    print(f"notified {address}")


async def notify_all(addresses: list[str]) -> None:
    for address in addresses:
        asyncio.create_task(notify(address))


asyncio.run(notify_all(["a@example.com", "b@example.com"]))
```

### 2.4 Why this difference matters

The hazardous function drops every task reference and returns before the tasks are guaranteed to run. At event-loop shutdown, notifications can be cancelled and their failures are not supervised.

## 3. Boundaries and distinctions

For deliberately independent background work, retain tasks in a managed collection and observe completion. Use `TaskGroup` when the tasks are part of one operation and should share failure and cancellation semantics.
