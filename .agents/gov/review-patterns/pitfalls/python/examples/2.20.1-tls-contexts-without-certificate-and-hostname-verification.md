# TLS contexts without certificate and hostname verification

## 1. Catalog record

- **Catalog identifier:** 2.20.1
- **Impact:** high
- **Consensus:** high
- **Definition:** For ordinary TLS clients, prefer `ssl.create_default_context()` or `PROTOCOL_TLS_CLIENT` rather than manually constructing a context that leaves certificate or hostname verification disabled.

## 2. Example

### 2.1 Scenario

A client fetches an account service over HTTPS. It must verify both the service certificate and its hostname.

### 2.2 Preferred form

```python
import ssl
from urllib.request import urlopen


def fetch_account(account_id: str) -> bytes:
    context = ssl.create_default_context()
    url = f"https://accounts.example.com/{account_id}"
    with urlopen(url, context=context) as response:
        return response.read()
```

### 2.3 Hazardous form

```python
import ssl
from urllib.request import urlopen


def fetch_account(account_id: str) -> bytes:
    context = ssl.SSLContext(ssl.PROTOCOL_TLS_CLIENT)
    context.check_hostname = False
    context.verify_mode = ssl.CERT_NONE
    url = f"https://accounts.example.com/{account_id}"
    with urlopen(url, context=context) as response:
        return response.read()
```

### 2.4 Why this difference matters

The hazardous client accepts an impostor certificate, allowing a network attacker to impersonate the service and read or alter traffic.

## 3. Boundaries and distinctions

Private PKI deployments may need a custom trust store, but the custom context should still verify certificates and hostnames for the intended service.
