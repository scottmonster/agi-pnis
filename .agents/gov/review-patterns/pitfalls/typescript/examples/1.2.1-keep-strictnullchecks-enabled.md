# Keep `strictNullChecks` enabled

## 1. Catalog record

- **Catalog identifier:** 1.2.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Treat `null` and `undefined` as distinct types instead of allowing them to flow through ordinary values.

## 2. Example

### 2.1 Scenario

A customer record can contain a null display name.

### 2.2 Preferred form

```typescript
type Customer = { displayName: string | null };

function label(customer: Customer): string {
  return customer.displayName?.toUpperCase() ?? 'ANONYMOUS';
}
```

### 2.3 Hazardous form

```typescript
// With `strictNullChecks: false`, this unchecked dereference compiles.
type Customer = { displayName: string | null };

function label(customer: Customer): string {
  return customer.displayName.toUpperCase();
}
```

### 2.4 Why this difference matters

Without it, APIs such as `find` can be treated as returning a value even when they can actually return `undefined`, directly enabling runtime failures.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
