# Treat `%w` as an API commitment

## 1. Catalog record

- **Catalog identifier:** 2.4.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Wrap an underlying error with `%w` only when callers should be able to depend on that error identity or type. Use `%v` when the underlying implementation detail should remain hidden.

## 2. Example

### 2.1 Scenario

A package exposes a stable service-level error while its current implementation happens to use a database driver error internally.

### 2.2 Preferred form

```go
package example

import (
	"errors"
	"fmt"
)

var ErrUnavailable = errors.New("profile service unavailable")

func fetchProfile(driverErr error) error {
	if driverErr != nil {
		return fmt.Errorf("fetch profile: %w (%v)", ErrUnavailable, driverErr)
	}
	return nil
}
```

### 2.3 Hazardous form

```go
package example

import (
	"errors"
	"fmt"
)

var ErrUnavailable = errors.New("profile service unavailable")

func fetchProfile(driverErr error) error {
	if driverErr != nil {
		return fmt.Errorf("fetch profile: %w", driverErr)
	}
	return nil
}
```

### 2.4 Why this difference matters

Using `%w` lets callers inspect and branch on the driver error, making that internal dependency part of the package's observable contract. The preferred form commits only to `ErrUnavailable` and retains the driver detail with `%v`.

## 3. Boundaries and distinctions

Use `%w` when callers genuinely need a documented sentinel or typed cause. Hiding an error must not remove information the caller needs to recover safely.
