# Accept `readonly` arrays when mutation is not required

## 1. Catalog record

- **Catalog identifier:** 5.2.1
- **Impact:** high
- **Consensus:** medium
- **Definition:** Type non-mutating array inputs as `readonly T[]` or `ReadonlyArray<T>` instead of mutable arrays.

## 2. Example

### 2.1 Scenario

A formatter reads tags but does not modify them.

### 2.2 Preferred form

```typescript
function formatTags(tags: readonly string[]): string {
  return tags.join(', ');
}

const labels = ['urgent', 'customer'] as const;
console.log(formatTags(labels));
```

### 2.3 Hazardous form

```typescript
function formatTags(tags: string[]): string {
  tags.push('formatted'); // A read-only helper needlessly permits mutation.
  return tags.join(', ');
}

const labels = ['urgent', 'customer'] as const;
console.log(formatTags(labels)); // Cannot accept readonly data.
```

### 2.4 Why this difference matters

Mutable array covariance can create an unsound write path, while readonly inputs prevent the callee from exploiting that mutation hole.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
