# Swallowing `CancelledError`

## 1. Catalog record

- **Catalog identifier:** 3.11.1
- **Impact:** high
- **Consensus:** high
- **Definition:** If cleanup code catches `asyncio.CancelledError`, normally re-raise it when cleanup finishes unless cancellation is intentionally and completely suppressed.

## 2. Example

### 2.1 Scenario

A task holds a resource while awaiting an operation. On cancellation, it must clean up and let its caller observe the cancellation.

### 2.2 Preferred form

```python
import asyncio


async def release_resource() -> None:
    await asyncio.sleep(0)


async def process_job() -> None:
    try:
        await asyncio.sleep(60)
    except asyncio.CancelledError:
        await release_resource()
        raise
```

### 2.3 Hazardous form

```python
import asyncio


async def release_resource() -> None:
    await asyncio.sleep(0)


async def process_job() -> None:
    try:
        await asyncio.sleep(60)
    except asyncio.CancelledError:
        await release_resource()
        return
```

### 2.4 Why this difference matters

Returning after catching `CancelledError` makes the task appear to have completed normally. Supervisors and structured-concurrency code can then make incorrect lifecycle decisions.

## 3. Boundaries and distinctions

An API may intentionally convert cancellation into a completed result, but it must do so deliberately and fully define the resulting task state and caller contract.
