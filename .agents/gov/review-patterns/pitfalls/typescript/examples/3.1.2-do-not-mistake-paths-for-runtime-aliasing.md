# Do not mistake `paths` for runtime aliasing

## 1. Catalog record

- **Catalog identifier:** 3.1.2
- **Impact:** high
- **Consensus:** high
- **Definition:** Use `paths` only when the runtime or bundler implements the same mapping, and do not publish libraries whose emitted imports depend on private `paths` aliases.

## 2. Example

### 2.1 Scenario

A web application uses a source alias that its bundler resolves in development and production.

### 2.2 Preferred form

```typescript
// tsconfig.json and the bundler both map "@/*" to "src/*".
import { format } from '@/format';

console.log(format('ok'));

// src/format.ts
export function format(value: string): string {
  return value.toUpperCase();
}
```

### 2.3 Hazardous form

```typescript
// tsconfig.json: { "compilerOptions": { "paths": { "@/*": ["src/*"] } } }
// The emitted JavaScript still contains this private specifier.
import { format } from '@/format';

console.log(format('ok'));

// Publishing this file without an alias-aware runtime fails at import time.
```

### 2.4 Why this difference matters

`paths` changes TypeScript resolution but does not rewrite emitted module specifiers.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
