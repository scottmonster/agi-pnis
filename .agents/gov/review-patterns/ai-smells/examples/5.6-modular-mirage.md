# “Modular mirage.”

## 1. Catalog record

- **Catalog identifier:** 5.6
- **Evidence:** e
- **Definition:** Many files/classes give the appearance of modularity while remaining tightly coupled semantically.

## 2. Scenario

### 2.1 Context

An import feature has separate parser, validator, mapper, and coordinator files, but each reads and mutates the same shared context dictionary using undocumented keys.

### 2.2 Safer approach

Define explicit inputs, outputs, and ownership boundaries so each component can be understood without hidden shared state.

### 2.3 Failure mode

Create another small class that reads the same context keys and call it a separate module.

### 2.4 Why this difference matters

File count disguises semantic coupling, so changes still require understanding the whole feature.

## 3. Boundaries and distinctions

Multiple files are not inherently false modularity. The issue is when nominal components cannot vary or be understood independently.
