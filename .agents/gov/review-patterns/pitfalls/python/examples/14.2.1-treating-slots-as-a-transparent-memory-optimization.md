# Treating `__slots__` as a transparent memory optimization

## 1. Catalog record

- **Catalog identifier:** 14.2.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Use `__slots__` only after accounting for inheritance, weak references, instance dictionaries, class defaults, and layout restrictions.

## 2. Example

### 2.1 Scenario

A performance-sensitive coordinate type is designed with a fixed, carefully reviewed instance layout.

### 2.2 Preferred form

```python
import weakref


class Coordinate:
    __slots__ = ("x", "y", "__weakref__")

    def __init__(self, x: int, y: int) -> None:
        self.x = x
        self.y = y


point = Coordinate(2, 3)
reference = weakref.ref(point)
print(reference().x)
```

### 2.3 Hazardous form

```python
class Coordinate:
    __slots__ = ("x", "y")
    x = 0

    def __init__(self, x: int, y: int) -> None:
        self.x = x
        self.y = y
```

### 2.4 Why this difference matters

Slots participate in class layout rather than merely turning on a transparent memory option. The hazardous definition conflicts with a class default for a slotted name and fails at class creation.

## 3. Boundaries and distinctions

Slots can be useful for measured memory or attribute-control needs. Review inheritance, pickling, weak references, dynamic attributes, and defaults before adopting them, especially in public base classes.
