# Using EAFP as an unconditional rule

## 1. Catalog record

- **Catalog identifier:** 16.20.1
- **Impact:** low
- **Consensus:** medium
- **Definition:** Python commonly favors EAFP, especially where a check-then-act sequence would introduce races, but do not mechanically replace every precondition check with exceptions. Choose based on API semantics, readability, cost, and concurrency requirements.

## 2. Example

### 2.1 Scenario

A command handler accepts an optional `--limit` argument. Absence is part of the normal request contract, while malformed values are errors.

### 2.2 Preferred form

```python
def parse_limit(options: dict[str, str]) -> int | None:
    raw_limit = options.get("limit")
    if raw_limit is None:
        return None
    return int(raw_limit)


print(parse_limit({"limit": "25"}))
```

### 2.3 Hazardous form

```python
def parse_limit(options: dict[str, str]) -> int | None:
    try:
        return int(options["limit"])
    except (KeyError, ValueError):
        return None


print(parse_limit({"limit": "not-a-number"}))
```

### 2.4 Why this difference matters

The hazardous form treats a malformed supplied value as though the option were absent, masking invalid input. The preferred form uses an explicit check because presence is part of this API's semantics.

## 3. Boundaries and distinctions

EAFP is often safer for operations where checking first would race with the operation, such as opening a file. Choose it or LBYL according to the API contract, clarity, cost, and concurrency risk.
