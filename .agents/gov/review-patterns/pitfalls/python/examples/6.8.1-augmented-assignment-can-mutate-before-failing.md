# Augmented assignment can mutate before failing

## 1. Catalog record

- **Catalog identifier:** 6.8.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Be cautious with expressions such as `tuple_obj[index] += mutable_value`. Separate mutation and assignment when the target is immutable or behavior matters.

## 2. Example

### 2.1 Scenario

A workflow stores a mutable list inside an immutable tuple and must add a completed status without leaving state half changed.

### 2.2 Preferred form

```python
statuses = (["queued"],)
updated_statuses = statuses[0].copy()
updated_statuses.append("sent")
statuses = (updated_statuses,)

assert statuses == (["queued", "sent"],)
```

### 2.3 Hazardous form

```python
statuses = (["queued"],)

try:
    statuses[0] += ["sent"]
except TypeError:
    pass

assert statuses == (["queued", "sent"],)
```

### 2.4 Why this difference matters

The list mutation occurs before Python attempts to assign the result back through the tuple index. That assignment fails because the tuple is immutable, but the nested list has already changed.

## 3. Boundaries and distinctions

Augmented assignment is safe when the target can accept the resulting assignment and partial mutation is acceptable. Separate the steps when immutable containers or transactional state make ordering important.
