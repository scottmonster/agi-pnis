# Use separate TypeScript projects for genuinely different environments

## 1. Catalog record

- **Catalog identifier:** 4.4.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Use separate tsconfigs or project references when code is checked against materially different runtimes such as Node, DOM, workers, tests, or separately published packages.

## 2. Example

### 2.1 Scenario

A monorepo has browser code and server code with incompatible global APIs.

### 2.2 Preferred form

```typescript
// tsconfig.browser.json: { "compilerOptions": { "lib": ["ES2022", "DOM"] } }
// tsconfig.server.json: { "compilerOptions": { "lib": ["ES2022"], "types": ["node"] } }
export function renderTitle(title: string): void {
  document.title = title;
}

```

### 2.3 Hazardous form

```typescript
// One config includes both DOM and Node types, so server code can accidentally use `document`.
export function renderTitle(title: string): void {
  document.title = title;
}
```

### 2.4 Why this difference matters

A single compilation can accidentally expose globals or resolution behavior that is unavailable in one of the actual execution environments.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
