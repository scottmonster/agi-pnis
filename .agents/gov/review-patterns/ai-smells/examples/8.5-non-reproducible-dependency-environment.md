# Non-reproducible dependency environment

## 1. Catalog record

- **Catalog identifier:** 8.5
- **Evidence:** e
- **Definition:** Builds or runs only with an undocumented, machine-specific set of package versions or tools.

## 2. Scenario

### 2.1 Context

An agent updates a frontend build and confirms success using the exact versions of Node, package-manager plugins, and packages already present on its workstation.

### 2.2 Safer approach

It records the supported runtime and tool versions, commits or updates the dependency lockfile, and builds from a clean checkout using the documented setup. The result is verified in CI with the same declared constraints.

### 2.3 Failure mode

It commits source changes without recording the local tool versions or resolved package set. Teammates install newer packages and receive different build output or a build failure that cannot be recreated on the author's machine.

### 2.4 Why this difference matters

Undocumented environment state prevents reliable debugging, onboarding, CI validation, and release reproduction.

## 3. Boundaries and distinctions

Some projects deliberately support a compatible version range rather than one exact environment. They still need documented constraints and repeatable resolution; this failure is reliance on unrecorded machine-specific state, not flexibility itself.
