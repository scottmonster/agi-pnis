# Treating `ast.literal_eval()` as safe for hostile input

## 1. Catalog record

- **Catalog identifier:** 2.3.1
- **Impact:** high
- **Consensus:** high
- **Definition:** `ast.literal_eval()` avoids arbitrary code execution but should still not be used indiscriminately on hostile input without resource controls.

## 2. Example

### 2.1 Scenario

A public API accepts a small list of numeric filters.

### 2.2 Preferred form

```python
import json


def parse_filters(payload: bytes) -> list[int]:
    if len(payload) > 1_000:
        raise ValueError("payload too large")
    values = json.loads(payload)
    if not isinstance(values, list) or not all(isinstance(value, int) for value in values):
        raise ValueError("filters must be integers")
    return values


print(parse_filters(b"[10, 20]"))
```

### 2.3 Hazardous form

```python
import ast


def parse_filters(text: str) -> object:
    return ast.literal_eval(text)


print(parse_filters("[10, 20]"))
```

### 2.4 Why this difference matters

Literal evaluation does not execute arbitrary code, but deeply nested or huge hostile input can still consume excessive CPU or memory.

## 3. Boundaries and distinctions

`literal_eval` is useful for trusted Python-literal data. At a hostile boundary, enforce size, depth, type, and resource limits.
