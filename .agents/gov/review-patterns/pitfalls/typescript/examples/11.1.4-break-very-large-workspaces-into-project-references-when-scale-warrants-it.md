# Break very large workspaces into project references when scale warrants it

## 1. Catalog record

- **Catalog identifier:** 11.1.4
- **Impact:** low
- **Consensus:** high
- **Definition:** Use project references when a workspace becomes large enough that build or editor scale is itself a demonstrated problem.

## 2. Example

### 2.1 Scenario

A monorepo has measured slow builds and editor updates because every package is checked as one program.

### 2.2 Preferred form

```typescript
// tsconfig.json
// {
//   "files": [],
//   "references": [{ "path": "./packages/core" }, { "path": "./packages/web" }]
// }
// packages/core/tsconfig.json
// { "compilerOptions": { "composite": true, "declaration": true } }
// packages/web/tsconfig.json
// { "compilerOptions": { "composite": true }, "references": [{ "path": "../core" }] }

// `tsc --build` can reuse the output for unchanged referenced projects.
```

### 2.3 Hazardous form

```typescript
// tsconfig.json
// {
//   "include": ["packages/*/src/**/*.ts"],
//   "compilerOptions": { "declaration": true }
// }

// Every change requires the compiler and editor to reason about all packages
// as one large program, even when most package boundaries are stable.
```

### 2.4 Why this difference matters

References divide the program into independently understandable units and can materially improve build and editor interaction at scale.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
