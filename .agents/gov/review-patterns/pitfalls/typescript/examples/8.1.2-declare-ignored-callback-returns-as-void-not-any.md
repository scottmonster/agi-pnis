# Declare ignored callback returns as `void`, not `any`

## 1. Catalog record

- **Catalog identifier:** 8.1.2
- **Impact:** medium
- **Consensus:** high
- **Definition:** When an API ignores a callback's return value, declare the callback as returning `void` rather than `any`.

## 2. Example

### 2.1 Scenario

A notification API invokes subscribers for their side effects and must not depend on a subscriber return value.

### 2.2 Preferred form

```typescript
function notify(subscribers: readonly ((message: string) => void)[], message: string): void {
  for (const subscriber of subscribers) {
    subscriber(message);
  }
}

notify([message => console.log(message)], 'deployment complete');
```

### 2.3 Hazardous form

```typescript
function notify(subscribers: readonly ((message: string) => any)[], message: string): void {
  for (const subscriber of subscribers) {
    const receipt = subscriber(message);
    receipt.deliver(); // unchecked use of a callback result
  }
}

notify([message => console.log(message)], 'deployment complete'); // runtime failure: receipt is undefined
```

### 2.4 Why this difference matters

`any` allows the API implementation to accidentally consume the unchecked callback result, whereas `void` prevents that use.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
