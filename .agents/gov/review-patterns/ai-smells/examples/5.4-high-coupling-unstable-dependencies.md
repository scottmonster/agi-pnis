# High coupling / unstable dependencies

## 1. Catalog record

- **Catalog identifier:** 5.4
- **Evidence:** e
- **Definition:** Modules know too much about one another's internals.

## 2. Scenario

### 2.1 Context

The billing module reaches into the private cache fields and database session of the orders module to determine invoice state.

### 2.2 Safer approach

Expose a stable domain operation from orders and pass only the data billing needs.

### 2.3 Failure mode

Have billing read private order fields and duplicate its persistence assumptions for a new invoice rule.

### 2.4 Why this difference matters

An internal orders refactor can silently break billing and makes independent evolution unsafe.

## 3. Boundaries and distinctions

Some module dependencies are necessary. The failure is dependence on internal details rather than a deliberate, stable contract.
