# Consider Temporal for complex date and time-zone logic

## 1. Catalog record

- **Catalog identifier:** 6.1.5
- **Impact:** medium
- **Consensus:** medium
- **Definition:** Where runtime support permits, consider Temporal rather than forcing complex calendar, duration, instant, and time-zone requirements through legacy `Date`.

## 2. Example

### 2.1 Scenario

A booking service must represent a meeting at 09:00 in a named time zone and calculate the following local day.

### 2.2 Preferred form

```javascript
const meeting = Temporal.ZonedDateTime.from({
  timeZone: "America/Chicago",
  year: 2026,
  month: 3,
  day: 8,
  hour: 9,
});

const nextLocalDay = meeting.add({ days: 1 });
console.log(nextLocalDay.toString());
```

### 2.3 Hazardous form

```javascript
const meeting = new Date("2026-03-08T09:00:00-06:00");
const nextLocalDay = new Date(meeting);
nextLocalDay.setDate(nextLocalDay.getDate() + 1);

console.log(nextLocalDay.toString());
```

### 2.4 Why this difference matters

Legacy `Date` combines an instant with host-local operations, making it easy to accidentally apply the wrong calendar or time-zone semantics.

## 3. Boundaries and distinctions

Temporal use depends on runtime availability or an approved polyfill. A simple instant or UTC timestamp may not need Temporal's richer model.
