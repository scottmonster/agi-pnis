# Treat a destination as partially modified after JSON failure

## 1. Catalog record

- **Catalog identifier:** 9.15.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Do not assume an `Unmarshal` error means the destination was left untouched. Prefer decoding into a temporary value when atomic update semantics are needed.

## 2. Example

### 2.1 Scenario

A service reloads live settings and must keep the previously valid configuration if a new JSON file is invalid.

### 2.2 Preferred form

```go
package example

import "encoding/json"

type Settings struct {
	Port int    `json:"port"`
	Mode string `json:"mode"`
}

func reload(current *Settings, data []byte) error {
	var next Settings
	if err := json.Unmarshal(data, &next); err != nil { return err }
	*current = next
	return nil
}
```

### 2.3 Hazardous form

```go
package example

import "encoding/json"

type Settings struct {
	Port int    `json:"port"`
	Mode string `json:"mode"`
}

func reload(current *Settings, data []byte) error {
	return json.Unmarshal(data, current) // Some fields can change before a later error.
}
```

### 2.4 Why this difference matters

An unmarshal failure can leave fields already decoded in the destination. A temporary value makes the assignment an explicit all-or-nothing update.

## 3. Boundaries and distinctions

In-place decoding can be acceptable when partial updates are intentional and documented. Temporary decoding does not itself validate cross-field business rules, which may need separate validation before assignment.
