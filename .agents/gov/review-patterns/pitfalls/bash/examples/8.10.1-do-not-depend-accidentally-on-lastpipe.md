# Do not depend accidentally on `lastpipe`

## 1. Catalog record

- **Catalog identifier:** 8.10.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** With `lastpipe` enabled and job control disabled, Bash can execute the final foreground pipeline component in the current shell rather than a subshell, so code should deliberately configure or avoid that dependency.

## 2. Example

### 2.1 Scenario

A script needs the first line from a producer after a pipeline completes.

### 2.2 Preferred form

```bash
first_line=''
while IFS= read -r line; do
  first_line=$line
  break
done < <(printf 'one\ntwo\n')
printf '%s\n' "$first_line"
```

### 2.3 Hazardous form

```bash
first_line=''
printf 'one\ntwo\n' | while IFS= read -r line; do
  first_line=$line
  break
done
printf '%s\n' "$first_line"
```

### 2.4 Why this difference matters

Normally the hazardous loop runs in a subshell, so its assignment is lost. With `lastpipe` and job control settings it may persist instead, making behavior depend on shell configuration.

## 3. Boundaries and distinctions

Deliberately enabling `lastpipe` can be valid for a controlled Bash environment. Process substitution avoids that option dependency when the producer is suitable for it.
