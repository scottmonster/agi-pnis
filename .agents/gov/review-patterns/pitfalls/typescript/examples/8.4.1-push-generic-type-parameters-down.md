# Push generic type parameters down

## 1. Catalog record

- **Catalog identifier:** 8.4.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Prefer `<T>(arg: T[])` to `<T extends any[]>(arg: T)` when the operation only needs the array element type.

## 2. Example

### 2.1 Scenario

A helper only needs to know an array's element type in order to return its final element.

### 2.2 Preferred form

```typescript
function last<T>(values: readonly T[]): T | undefined {
  return values.at(-1);
}

const lastStatus = last(['draft', 'published']); // string | undefined
```

### 2.3 Hazardous form

```typescript
function last<T extends readonly unknown[]>(values: T): T[number] | undefined {
  return values.at(-1);
}

const lastStatus = last(['draft', 'published']); // unnecessarily preserves array-shape machinery
```

### 2.4 Why this difference matters

Over-constraining the parameter can force property access through the constraint and produce poorer inference, including `any`.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
