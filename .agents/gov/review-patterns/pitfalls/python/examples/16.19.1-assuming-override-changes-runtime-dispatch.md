# Assuming `@override` changes runtime dispatch

## 1. Catalog record

- **Catalog identifier:** 16.19.1
- **Impact:** low
- **Consensus:** high
- **Definition:** Use `@override` to let static checking detect misspelled or nonexistent base methods, not as a runtime override mechanism.

## 2. Example

### 2.1 Scenario

A notifier subtype customizes the delivery method inherited from a base notifier.

### 2.2 Preferred form

```python
from typing import override


class Notifier:
    def deliver(self, message: str) -> str:
        return f"sent: {message}"


class EmailNotifier(Notifier):
    @override
    def deliver(self, message: str) -> str:
        return f"email: {message}"


print(EmailNotifier().deliver("ready"))
```

### 2.3 Hazardous form

```python
from typing import override


class Notifier:
    def deliver(self, message: str) -> str:
        return f"sent: {message}"


class EmailNotifier(Notifier):
    @override
    def delvier(self, message: str) -> str:
        return f"email: {message}"


print(EmailNotifier().deliver("ready"))
```

### 2.4 Why this difference matters

The misspelled hazardous method is not selected by normal runtime lookup, so the inherited implementation runs. `@override` helps a static checker detect this, but it does not alter dispatch.

## 3. Boundaries and distinctions

`@override` requires tooling that understands it to provide diagnostics. Runtime behavior remains ordinary Python method resolution with or without the decorator.
