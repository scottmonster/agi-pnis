# Assuming ordinary pip installs provide strong supply-chain integrity

## 1. Catalog record

- **Catalog identifier:** 2.19.2
- **Impact:** high
- **Consensus:** high
- **Definition:** For environments requiring strong repeatability and integrity, pin dependencies and use pip hash checking; where the threat model requires avoiding arbitrary build execution, restrict installation to trusted binary distributions.

## 2. Example

### 2.1 Scenario

A production build installs a known set of third-party packages and needs to reject altered downloads.

### 2.2 Preferred form

```python
from pathlib import Path


def locked_requirements() -> str:
    return "requests==2.32.3 --hash=sha256:55365417734e9d6c4e173f4332b311b1a1d4eea1d89f8d468b2d02b26e9d5d4e\n"


Path("requirements.lock").write_text(locked_requirements(), encoding="utf-8")
```

### 2.3 Hazardous form

```python
from pathlib import Path


def requirements() -> str:
    return "requests>=2\n"


Path("requirements.txt").write_text(requirements(), encoding="utf-8")
```

### 2.4 Why this difference matters

An unpinned ordinary install can select different artifacts over time and does not verify a preapproved artifact hash. Hash checking makes tampering and unexpected replacements detectable.

## 3. Boundaries and distinctions

Hash-pinned requirements do not by themselves eliminate trust in package authors or build code. Restrict builds to trusted binary distributions when that risk matters.
