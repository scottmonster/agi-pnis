# Unconstrained mocks masking API mistakes

## 1. Catalog record

- **Catalog identifier:** 13.1.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Use `spec`, `spec_set`, or `autospec` when a mock should accurately model a real API, and use `create=True` only deliberately.

## 2. Example

### 2.1 Scenario

A service calls a payment gateway and its unit test should catch misspelled gateway methods.

### 2.2 Preferred form

```python
from unittest.mock import create_autospec


class Gateway:
    def charge(self, cents: int) -> str:
        return "receipt"


def bill(gateway: Gateway, cents: int) -> str:
    return gateway.charge(cents)


gateway = create_autospec(Gateway, instance=True)
gateway.charge.return_value = "receipt"
assert bill(gateway, 500) == "receipt"
gateway.charge.assert_called_once_with(500)
```

### 2.3 Hazardous form

```python
from unittest.mock import Mock


def bill(gateway: object, cents: int) -> object:
    return gateway.chagre(cents)


gateway = Mock()
assert bill(gateway, 500) is gateway.chagre.return_value
```

### 2.4 Why this difference matters

An unconstrained mock manufactures arbitrary attributes, allowing a typo such as `chagre` to pass the test even though the real gateway has no such API.

## 3. Boundaries and distinctions

Loose mocks can be useful for deliberately dynamic interfaces or simple value placeholders. Constrain mocks when the test claims to model a concrete collaborator's contract.
