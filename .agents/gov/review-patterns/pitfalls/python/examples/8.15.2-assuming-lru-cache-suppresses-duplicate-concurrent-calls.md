# Assuming `lru_cache` suppresses duplicate concurrent calls

## 1. Catalog record

- **Catalog identifier:** 8.15.2
- **Impact:** medium
- **Consensus:** high
- **Definition:** Do not use `lru_cache` itself as a single-flight mechanism when duplicate concurrent execution is unacceptable.

## 2. Example

### 2.1 Scenario

Multiple threads request the same expensive initialization, and only one external call may occur.

### 2.2 Preferred form

```python
import threading

class Initializer:
    def __init__(self) -> None:
        self._lock = threading.Lock()
        self._value: str | None = None

    def get(self) -> str:
        with self._lock:
            if self._value is None:
                self._value = "initialized"
            return self._value
```

### 2.3 Hazardous form

```python
from functools import lru_cache

@lru_cache
def initialize(name: str) -> str:
    return f"initialized-{name}"  # Concurrent cache misses can both execute here.
```

### 2.4 Why this difference matters

`lru_cache` protects its internal data structure, but it does not coordinate concurrent misses into one call.

## 3. Boundaries and distinctions

`lru_cache` is suitable when duplicate evaluation is acceptable and caching the completed value is the only requirement.
