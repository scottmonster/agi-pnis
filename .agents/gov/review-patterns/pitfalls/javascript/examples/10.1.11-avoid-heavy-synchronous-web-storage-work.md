# Avoid heavy synchronous Web Storage work

## 1. Catalog record

- **Catalog identifier:** 10.1.11
- **Impact:** medium
- **Consensus:** high
- **Definition:** Avoid large or frequent synchronous storage operations when they can block responsiveness.

## 2. Example

### 2.1 Scenario

A text editor saves a small draft when the user explicitly clicks Save.

### 2.2 Preferred form

```javascript
function saveDraftOnClick(text) {
  const draft = { text, savedAt: new Date().toISOString() };
  localStorage.setItem("draft", JSON.stringify(draft));
}

document.querySelector("#save").addEventListener("click", () => {
  saveDraftOnClick(document.querySelector("#editor").value);
});
```

### 2.3 Hazardous form

```javascript
document.querySelector("#editor").addEventListener("input", (event) => {
  const snapshot = { text: event.target.value, savedAt: new Date().toISOString() };
  localStorage.setItem("draft", JSON.stringify(snapshot));
});
```

### 2.4 Why this difference matters

Web Storage calls are synchronous. Serializing and writing on every keystroke can block the main thread and make input feel sluggish, especially for large drafts.

## 3. Boundaries and distinctions

Small, infrequent storage writes can be appropriate. Batch, debounce, or move substantial client-side data to an asynchronous storage mechanism when responsiveness matters.
