# Do not call `Fatal` from a helper goroutine

## 1. Catalog record

- **Catalog identifier:** 11.15.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** `T.FailNow`, `T.Fatal`, `T.Fatalf`, `SkipNow`, and related termination methods must run in the goroutine executing the test, not an arbitrary spawned goroutine.

## 2. Example

### 2.1 Scenario

A test runs a worker that can return an error and needs the test goroutine to report the failure.

### 2.2 Preferred form

```go
package example

import (
	"errors"
	"testing"
)

func TestWorker(t *testing.T) {
	errCh := make(chan error, 1)
	go func() { errCh <- errors.New("worker failed") }()
	if err := <-errCh; err != nil {
		t.Fatal(err)
	}
}
```

### 2.3 Hazardous form

```go
package example

import "testing"

func TestWorker(t *testing.T) {
	go func() {
		t.Fatal("worker failed") // Fatal must not run in this goroutine
	}()
}
```

### 2.4 Why this difference matters

`Fatal` calls `FailNow`, which terminates only the goroutine that calls it. A helper goroutine can leave the test goroutine running or let the test finish before its failure is reported correctly.

## 3. Boundaries and distinctions

Ordinary `t.Error` is safe from another goroutine, but test-terminating methods are not. Communicate errors to the test goroutine when immediate termination semantics are needed.
