# Keep fuzz targets deterministic and isolated

## 1. Catalog record

- **Catalog identifier:** 11.14.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Fuzz functions should execute quickly and deterministically for a given input and should not depend on state left by previous invocations.

## 2. Example

### 2.1 Scenario

A fuzz target checks that a parser accepts only decimal account numbers.

### 2.2 Preferred form

```go
package example

import (
	"strconv"
	"testing"
)

func FuzzAccountNumber(f *testing.F) {
	f.Add("42")
	f.Fuzz(func(t *testing.T, input string) {
		_, _ = strconv.ParseUint(input, 10, 64)
	})
}
```

### 2.3 Hazardous form

```go
package example

import (
	"math/rand/v2"
	"testing"
)

func FuzzAccountNumber(f *testing.F) {
	f.Fuzz(func(t *testing.T, input string) {
		_ = input
		if rand.IntN(2) == 0 {
			t.Skip("random outcome")
		}
	})
}
```

### 2.4 Why this difference matters

The fuzz engine may run inputs in parallel and in nondeterministic order. Random outcomes or shared mutable state make failures hard to reproduce and can invalidate corpus results.

## 3. Boundaries and distinctions

Tests can use controlled randomness when the seed is part of the input or failure report. A fuzz target itself should produce behavior determined by its current input.
