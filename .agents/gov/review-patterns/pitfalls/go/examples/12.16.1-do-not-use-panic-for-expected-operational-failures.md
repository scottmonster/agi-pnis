# Do not use panic for expected operational failures

## 1. Catalog record

- **Catalog identifier:** 12.16.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Return errors for ordinary invalid input, unavailable resources, failed network calls, and other expected failure paths. Reserve panic for violated invariants or exceptional internal conditions.

## 2. Example

### 2.1 Scenario

A command loads its configuration from a user-provided path. A missing file or an empty path is an ordinary operational failure that the caller may report or recover from.

### 2.2 Preferred form

```go
package example

import (
	"errors"
	"fmt"
	"os"
)

func readConfig(path string) ([]byte, error) {
	if path == "" {
		return nil, errors.New("config path is required")
	}
	contents, err := os.ReadFile(path)
	if err != nil {
		return nil, fmt.Errorf("read config %q: %w", path, err)
	}
	return contents, nil
}
```

### 2.3 Hazardous form

```go
package example

import "os"

func readConfig(path string) []byte {
	if path == "" {
		panic("config path is required")
	}
	contents, err := os.ReadFile(path)
	if err != nil {
		panic(err)
	}
	return contents
}
```

### 2.4 Why this difference matters

Panicking for an unavailable file turns a recoverable input or environment problem into process-wide control flow. Returning an error lets the caller add context, choose a fallback, or terminate cleanly after its deferred cleanup runs.

## 3. Boundaries and distinctions

`panic` remains appropriate for broken internal invariants and impossible states when continuing would be unsafe. It is not a substitute for an error-returning API at ordinary system and user-input boundaries.
