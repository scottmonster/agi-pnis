# `comparable` does not guarantee panic-free equality for interface type arguments

## 1. Catalog record

- **Catalog identifier:** 11.1.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Since Go 1.20, interface types such as `any` may satisfy `comparable`; equality can still panic when the dynamic value placed in that interface is itself non-comparable.

## 2. Example

### 2.1 Scenario

A cache helper accepts values through `any`. Its type parameter satisfies `comparable`, but callers can still place a slice inside that interface.

### 2.2 Preferred form

```go
package example

import "reflect"

func sameDynamicValue[T comparable](a, b T) bool {
	if reflect.TypeOf(a) != reflect.TypeOf(b) {
		return false
	}
	t := reflect.TypeOf(a)
	return t == nil || t.Comparable() && a == b
}

func preferred() bool {
	return !sameDynamicValue[any]([]int{1}, []int{1})
}
```

### 2.3 Hazardous form

```go
package example

func sameDynamicValue[T comparable](a, b T) bool {
	return a == b
}

func hazardous() bool {
	return sameDynamicValue[any]([]int{1}, []int{1}) // panics
}
```

### 2.4 Why this difference matters

The `comparable` constraint permits an interface type, but equality then uses the dynamic values. Comparing dynamic slices or maps panics.

## 3. Boundaries and distinctions

Direct concrete type parameters such as `string` and `int` are safe to compare. This condition matters when an interface type argument can contain values whose dynamic type is not comparable.
