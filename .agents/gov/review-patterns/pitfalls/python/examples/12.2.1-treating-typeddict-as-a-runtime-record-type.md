# Treating `TypedDict` as a runtime record type

## 1. Catalog record

- **Catalog identifier:** 12.2.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Do not expect `TypedDict` construction to validate keys or values at runtime. Add actual validation when external data must satisfy a schema.

## 2. Example

### 2.1 Scenario

An API handler turns a JSON object into a user record before storing it.

### 2.2 Preferred form

```python
from typing import TypedDict


class User(TypedDict):
    id: int
    name: str


def parse_user(value: object) -> User:
    if not isinstance(value, dict):
        raise ValueError("user must be an object")
    user_id = value.get("id")
    name = value.get("name")
    if not isinstance(user_id, int) or not isinstance(name, str):
        raise ValueError("user has an invalid shape")
    return {"id": user_id, "name": name}
```

### 2.3 Hazardous form

```python
from typing import TypedDict


class User(TypedDict):
    id: int
    name: str


payload = {"id": "not-an-integer", "name": 42}
user = User(**payload)
print(user["id"] + 1)
```

### 2.4 Why this difference matters

`TypedDict` informs static analyzers, but its constructor is an ordinary dictionary construction at runtime. Invalid external data can therefore travel far from the boundary before failing.

## 3. Boundaries and distinctions

Static type checking can establish shapes for values created and controlled within typed code. Validate only at runtime boundaries where untrusted or otherwise unchecked data enters.
