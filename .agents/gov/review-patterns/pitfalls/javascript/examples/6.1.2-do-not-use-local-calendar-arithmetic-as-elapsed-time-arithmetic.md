# Do not use local calendar arithmetic as elapsed-time arithmetic

## 1. Catalog record

- **Catalog identifier:** 6.1.2
- **Impact:** high
- **Consensus:** high
- **Definition:** When exact elapsed durations matter, do not assume adding a local day or manipulating local date fields always changes the timestamp by exactly 24 hours. Use UTC or time-zone-aware duration logic appropriate to the requirement.

## 2. Example

### 2.1 Scenario

A cleanup task must expire a token exactly 24 hours after it was issued.

### 2.2 Preferred form

```javascript
function expiresInOneDay(issuedAt) {
  return new Date(issuedAt.getTime() + 24 * 60 * 60 * 1000);
}

const issuedAt = new Date("2026-03-08T06:00:00Z");
console.log(expiresInOneDay(issuedAt).getTime() - issuedAt.getTime()); // 86400000
```

### 2.3 Hazardous form

```javascript
function expiresInOneDay(issuedAt) {
  const expiry = new Date(issuedAt);
  expiry.setDate(expiry.getDate() + 1);
  return expiry;
}

const issuedAt = new Date("2026-03-08T06:00:00Z");
console.log(expiresInOneDay(issuedAt).getTime() - issuedAt.getTime());
```

### 2.4 Why this difference matters

The hazardous calculation preserves a local calendar time. Across a daylight-saving transition, that calendar day can be shorter or longer than 24 elapsed hours.

## 3. Boundaries and distinctions

Local calendar arithmetic is correct for requirements such as "same local time tomorrow." Use elapsed-time arithmetic only when the requirement is an exact duration.
