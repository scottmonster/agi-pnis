# Choose an ASI-safe semicolon policy

## 1. Catalog record

- **Catalog identifier:** 1.1.24
- **Impact:** low
- **Consensus:** medium
- **Definition:** Whether a codebase writes explicit semicolons is largely a style choice, but code relying on automatic semicolon insertion must account for lines beginning with syntax such as `(` or `[` that can continue the previous expression.

## 2. Example

### 2.1 Scenario

A script initializes a list and then starts a new array expression on the following line.

### 2.2 Preferred form

```javascript
const entries = [1, 2];
[3, 4].forEach((entry) => console.log(entry));
```

### 2.3 Hazardous form

```javascript
const entries = [1, 2]
[3, 4].forEach((entry) => console.log(entry));
```

### 2.4 Why this difference matters

Without a safe statement boundary, the second line can continue the first expression, leading to an unintended property access and a runtime failure.

## 3. Boundaries and distinctions

A semicolon-free style can work when it consistently uses safe leading delimiters for continuation-prone lines. Explicit semicolons are a simple alternative.
