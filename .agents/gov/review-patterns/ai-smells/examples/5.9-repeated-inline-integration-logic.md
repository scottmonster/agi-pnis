# Repeated inline integration logic

## 1. Catalog record

- **Catalog identifier:** 5.9
- **Evidence:** e
- **Definition:** External/API interactions are rewritten multiple times once genuine duplication exists.

## 2. Scenario

### 2.1 Context

Several jobs each construct the same payment-provider request, attach credentials, classify errors, and parse the response inline.

### 2.2 Safer approach

Once the shared integration behavior is established, provide one focused client boundary with clear request and error semantics.

### 2.3 Failure mode

Copy the inline HTTP setup into a new refund job and make a local retry change.

### 2.4 Why this difference matters

Credential handling, error behavior, and provider changes drift among call sites.

## 3. Boundaries and distinctions

A single integration call need not gain a wrapper. Centralization becomes useful after genuine repeated interaction logic exists.
