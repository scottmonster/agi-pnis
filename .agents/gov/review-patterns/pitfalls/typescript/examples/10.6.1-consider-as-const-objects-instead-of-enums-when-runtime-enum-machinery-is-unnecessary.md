# Consider `as const` objects instead of enums when runtime enum machinery is unnecessary

## 1. Catalog record

- **Catalog identifier:** 10.6.1
- **Impact:** low
- **Consensus:** medium
- **Definition:** For simple constant sets, a plain object with `as const` plus derived union types can often replace a TypeScript enum; ordinary enums remain valid when their runtime object semantics are useful.

## 2. Example

### 2.1 Scenario

A web client needs a small fixed set of shipment filters to send in requests and display in a menu.

### 2.2 Preferred form

```typescript
export const ShipmentFilter = {
  All: "all",
  InTransit: "in_transit",
  Delivered: "delivered",
} as const;

export type ShipmentFilter = (typeof ShipmentFilter)[keyof typeof ShipmentFilter];

export function isDelivered(filter: ShipmentFilter): boolean {
  return filter === ShipmentFilter.Delivered;
}
```

### 2.3 Hazardous form

```typescript
export enum ShipmentFilter {
  All = "all",
  InTransit = "in_transit",
  Delivered = "delivered",
}

export function isDelivered(filter: ShipmentFilter): boolean {
  return filter === ShipmentFilter.Delivered;
}
```

### 2.4 Why this difference matters

Both forms express the values, but the enum emits TypeScript-specific runtime machinery for a case that only needs plain constants and a derived union. The object form stays transparent to JavaScript consumers and tooling.

## 3. Boundaries and distinctions

Enums remain appropriate when their runtime object semantics, reverse mapping, or an established public API materially helps. This is a simplification choice, not a ban on enums.
