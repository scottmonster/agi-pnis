# Do not compare localized output to hardcoded strings

## 1. Catalog record

- **Catalog identifier:** 6.1.6
- **Impact:** medium
- **Consensus:** high
- **Definition:** Treat `Intl` and `toLocaleString()` output as presentation text rather than a stable machine-readable format.

## 2. Example

### 2.1 Scenario

A checkout service needs a stable currency code for business logic and a localized price for display.

### 2.2 Preferred form

```javascript
const price = { currency: "USD", minorUnits: 1234 };
const amount = price.minorUnits / 100;
const display = new Intl.NumberFormat("en-US", {
  style: "currency",
  currency: price.currency,
}).format(amount);

console.log(price.currency === "USD"); // true
console.log(display); // presentation only
```

### 2.3 Hazardous form

```javascript
const amount = 12.34;
const display = amount.toLocaleString("en-US", {
  style: "currency",
  currency: "USD",
});

console.log(display === "$12.34");
```

### 2.4 Why this difference matters

Localized output can vary by locale and implementation, so equality against a presentation string can fail even when the underlying amount is correct.

## 3. Boundaries and distinctions

Snapshot tests may assert presentation output when they deliberately pin a locale, runtime, and expected formatting policy. Do not use that text as a protocol or business-data representation.
