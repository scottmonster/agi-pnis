# A typed nil inside an interface is not a nil interface

## 1. Catalog record

- **Catalog identifier:** 2.1.1
- **Impact:** high
- **Consensus:** high
- **Definition:** An interface containing a typed nil pointer is non-nil because its dynamic type is present. Avoid returning typed nil pointers as `error` or other interfaces when you intend to return nil.

## 2. Example

### 2.1 Scenario

A lookup function reports an absent account with no error. Its concrete error type is a pointer, so the function must avoid putting a nil pointer into its `error` result.

### 2.2 Preferred form

```go
package example

type lookupError struct{ accountID string }

func (e *lookupError) Error() string { return "account not found: " + e.accountID }

func findAccount(id string) error {
	if id == "missing" {
		return nil
	}
	return nil
}
```

### 2.3 Hazardous form

```go
package example

type lookupError struct{ accountID string }

func (e *lookupError) Error() string { return "account not found: " + e.accountID }

func findAccount(id string) error {
	var problem *lookupError
	if id == "missing" {
		return problem // error has dynamic type *lookupError, so err != nil
	}
	return nil
}
```

### 2.4 Why this difference matters

The hazardous return has a nil pointer value but a non-nil interface type. A caller that checks `err != nil` takes its failure path and may call `Error` on the nil receiver.

## 3. Boundaries and distinctions

This issue applies when a nilable concrete value is converted to an interface. A nil interface is still the correct result when the operation has no error to report.
