# Prefer `testing/synctest` to real sleeps for asynchronous timing tests

## 1. Catalog record

- **Catalog identifier:** 11.17.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Where applicable, use `testing/synctest` rather than long `time.Sleep` calls to coordinate concurrent behavior in tests.

## 2. Example

### 2.1 Scenario

A test verifies that a background timer has not fired before its deadline and does fire after the deadline.

### 2.2 Preferred form

```go
package example

import (
	"testing"
	"testing/synctest"
	"time"
)

func TestDeadline(t *testing.T) {
	synctest.Test(t, func(t *testing.T) {
		fired := make(chan struct{}, 1)
		go func() { time.Sleep(time.Second); fired <- struct{}{} }()
		synctest.Wait()
		select { case <-fired: t.Fatal("fired early"); default: }
		time.Sleep(time.Second) // fake time advances inside the synctest bubble
		<-fired
	})
}
```

### 2.3 Hazardous form

```go
package example

import (
	"testing"
	"time"
)

func TestDeadline(t *testing.T) {
	fired := make(chan struct{}, 1)
	go func() { time.Sleep(time.Second); fired <- struct{}{} }()
	time.Sleep(1100 * time.Millisecond) // slow and scheduler-sensitive
	<-fired
}
```

### 2.4 Why this difference matters

Real-time sleeps make tests slow and vulnerable to scheduler timing and machine load. `synctest` advances controlled time and coordinates goroutines deterministically.

## 3. Boundaries and distinctions

Use `testing/synctest` where its bubble model fits the asynchronous behavior and your supported Go version provides it. Real external I/O and system integration may still require bounded real-time tests.
