# Keep built-in iterator return values strict

## 1. Catalog record

- **Catalog identifier:** 7.11.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Retain `strictBuiltinIteratorReturn`, normally via `strict`, rather than allowing iterator completion values to leak `any`.

## 2. Example

### 2.1 Scenario

A function reads the first tag from a built-in array iterator and must distinguish a yielded value from the iterator's completed state.

### 2.2 Preferred form

```typescript
function firstTag(tags: string[]): string | undefined {
  const step = tags.values().next();

  if (step.done) {
    return undefined;
  }

  return step.value;
}
```

### 2.3 Hazardous form

```typescript
function firstTagUppercase(tags: string[]): string {
  const step = tags.values().next();

  // With strictBuiltinIteratorReturn disabled, this completion value can be any.
  return step.value.toUpperCase();
}
```

### 2.4 Why this difference matters

When `strictBuiltinIteratorReturn` is enabled, the completion value of a built-in iterator is typed as `undefined` rather than `any`. The resulting error forces code to inspect `done` before treating `value` as a yielded element.

## 3. Boundaries and distinctions

This setting affects built-in iterators such as arrays, maps, and sets, and is enabled by `strict`. Custom iterators can declare their own `TReturn` type, so code consuming them must still follow that iterator's contract. If completion is impossible by construction, keep the proof local and explicit rather than disabling the check globally.
