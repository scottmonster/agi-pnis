# Wait on `sync.Cond` in a loop

## 1. Catalog record

- **Catalog identifier:** 6.7.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Recheck the condition after every `Cond.Wait`, normally with `for !condition { c.Wait() }`.

## 2. Example

### 2.1 Scenario

A worker waits until a queue has an item.

### 2.2 Preferred form

```go
package main

import "sync"

type queue struct { mu sync.Mutex; ready *sync.Cond; items []string }
func (q *queue) take() string {
	q.mu.Lock(); defer q.mu.Unlock()
	for len(q.items) == 0 { q.ready.Wait() }
	item := q.items[0]; q.items = q.items[1:]; return item
}
```

### 2.3 Hazardous form

```go
package main

import "sync"

type queue struct { mu sync.Mutex; ready *sync.Cond; items []string }
func (q *queue) take() string {
	q.mu.Lock(); defer q.mu.Unlock()
	if len(q.items) == 0 { q.ready.Wait() }
	item := q.items[0]; q.items = q.items[1:]; return item
}
```

### 2.4 Why this difference matters

Another waiter can consume the item after a signal but before this goroutine obtains the lock. The loop rechecks the predicate.

## 3. Boundaries and distinctions

Maintain the predicate with the condition's lock. Channels are often simpler for one-way work queues.
