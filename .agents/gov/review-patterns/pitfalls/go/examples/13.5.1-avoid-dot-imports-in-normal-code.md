# Avoid dot imports in normal code

## 1. Catalog record

- **Catalog identifier:** 13.5.1
- **Impact:** low
- **Consensus:** high
- **Definition:** Import packages normally and qualify their exported names. Reserve dot imports for exceptional test dependency situations where package cycles make them useful.

## 2. Example

### 2.1 Scenario

A command emits a status message and should make the package providing the output operation obvious.

### 2.2 Preferred form

```go
package example

import "fmt"

func report() {
	fmt.Println("ready")
}
```

### 2.3 Hazardous form

```go
package example

import . "fmt"

func report() {
	Println("ready")
}
```

### 2.4 Why this difference matters

The qualified call identifies its origin and avoids collisions with local names. The dot import hides that information, making a larger package harder to read and refactor.

## 3. Boundaries and distinctions

Dot imports can be appropriate in narrowly constrained tests, especially where they break a test-only import cycle. They are rarely appropriate in ordinary production code.
