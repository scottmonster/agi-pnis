# Treat `sql.DB` as a long-lived connection pool

## 1. Catalog record

- **Catalog identifier:** 9.9.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Open a `*sql.DB` for reuse rather than opening and closing one per request. Configure pool limits when resource constraints require them.

## 2. Example

### 2.1 Scenario

An HTTP service needs a database handle for every incoming request.

### 2.2 Preferred form

```go
package example

import "database/sql"

func openDatabase(dsn string) (*sql.DB, error) {
	db, err := sql.Open("postgres", dsn)
	if err != nil { return nil, err }
	db.SetMaxOpenConns(20)
	db.SetMaxIdleConns(10)
	return db, nil // Reuse for the process lifetime, then close on shutdown.
}
```

### 2.3 Hazardous form

```go
package example

import "database/sql"

func handleRequest(dsn string) error {
	db, err := sql.Open("postgres", dsn)
	if err != nil { return err }
	defer db.Close() // Recreates a pool on every request.
	return db.Ping()
}
```

### 2.4 Why this difference matters

`sql.DB` manages a connection pool, not one connection. Reopening it per request discards pooling and increases connection churn under load.

## 3. Boundaries and distinctions

Create separate pools only for genuinely distinct databases or policies. Tune limits and lifetimes to database capacity, deployment size, and observed workload.
