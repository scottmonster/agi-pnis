# Avoid type-level redundancy that hides widening

## 1. Catalog record

- **Catalog identifier:** 11.6.1
- **Impact:** low
- **Consensus:** medium
- **Definition:** Remove constituents such as `string | "foo"`, `unknown | T`, or `any | T` when the broader type completely absorbs the narrower one unless the redundancy is deliberately documentary.

## 2. Example

### 2.1 Scenario

An API accepts arbitrary text, and a separate value is intentionally unknown until validation.

### 2.2 Preferred form

```typescript
type Tag = string;
type IncomingPayload = unknown;

function report(tag: Tag, payload: IncomingPayload): void {
  console.log(tag, payload);
}

report('urgent', { id: '42' });
```

### 2.3 Hazardous form

```typescript
type Tag = string | 'urgent';
type IncomingPayload = unknown | { id: string };

function report(tag: Tag, payload: IncomingPayload): void {
  console.log(tag, payload);
}

// `Tag` still accepts every string and `IncomingPayload` still needs validation.
```

### 2.4 Why this difference matters

Redundant constituents can make a type appear more constrained than it actually is, particularly when `any` or `unknown` has erased useful information.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
