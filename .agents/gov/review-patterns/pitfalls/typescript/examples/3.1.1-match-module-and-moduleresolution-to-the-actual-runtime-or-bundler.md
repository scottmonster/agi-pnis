# Match `module` and `moduleResolution` to the actual runtime or bundler

## 1. Catalog record

- **Catalog identifier:** 3.1.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Use Node modes for Node, `bundler` for bundler semantics, and otherwise configure TypeScript to model the actual host instead of choosing options solely to silence import errors.

## 2. Example

### 2.1 Scenario

A Node ESM package emits JavaScript that Node resolves directly.

### 2.2 Preferred form

```typescript
// tsconfig.json: { "compilerOptions": { "module": "NodeNext", "moduleResolution": "NodeNext" } }
// src/main.ts
import { format } from './format.js';

console.log(format('ok'));

// src/format.ts
export function format(value: string): string {
  return value.toUpperCase();
}
```

### 2.3 Hazardous form

```typescript
// tsconfig.json: { "compilerOptions": { "module": "ESNext", "moduleResolution": "bundler" } }
// src/main.ts
import { format } from './format';

console.log(format('ok'));

// This may typecheck, but Node ESM cannot resolve the emitted specifier.
```

### 2.4 Why this difference matters

TypeScript uses these options to predict runtime resolution and module behavior; the wrong model can typecheck imports that the runtime cannot load.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
