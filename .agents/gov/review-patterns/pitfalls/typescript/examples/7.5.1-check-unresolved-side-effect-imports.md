# Check unresolved side-effect imports

## 1. Catalog record

- **Catalog identifier:** 7.5.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Keep `noUncheckedSideEffectImports` enabled rather than allowing misspelled or missing side-effect-only modules to disappear silently.

## 2. Example

### 2.1 Scenario

An application startup module loads a file whose only job is to register custom metrics before the server begins handling requests.

### 2.2 Preferred form

```typescript
// tsconfig.json: { "compilerOptions": { "noUncheckedSideEffectImports": true } }

// src/start.ts
import { startServer } from './server.js';
import './register-metrics.js';

startServer();

// src/register-metrics.ts
import { metrics } from './metrics.js';

metrics.registerDefaultCollectors();
```

### 2.3 Hazardous form

```typescript
// tsconfig.json: { "compilerOptions": { "noUncheckedSideEffectImports": false } }

// src/start.ts
import { startServer } from './server.js';
import './register-metric.js'; // Typo: this file does not exist.

startServer();
```

### 2.4 Why this difference matters

Side-effect imports often establish required runtime state. Without this option, TypeScript can overlook an unresolved side-effect-only specifier, leaving the typo to become a missing initializer or a module-not-found failure later. Enabling it makes the compiler validate the import just as it does a named import.

## 3. Boundaries and distinctions

The option checks TypeScript's module resolution, not whether a loaded module actually performs the expected registration. Bundler-provided virtual modules, CSS imports, and generated files may need accurate ambient module declarations or a resolver configuration. Do not disable the option globally merely to accommodate those supported exceptions.
