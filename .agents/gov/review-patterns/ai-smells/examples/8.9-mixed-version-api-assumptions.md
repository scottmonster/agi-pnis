# Mixed-version API assumptions

## 1. Catalog record

- **Catalog identifier:** 8.9
- **Evidence:** e
- **Definition:** Writes code as though features from different releases coexist in one installed version.

## 2. Scenario

### 2.1 Context

A service is pinned to a client library release that supports the `create()` method but not the newer `createStream()` method.

### 2.2 Safer approach

Check the installed release's API reference and use the method available in that release, or upgrade the dependency as a separate compatible change.

```ts
const response = await client.create(request);
for await (const item of response.items) process(item);
```

### 2.3 Failure mode

The agent reads current documentation and writes code for a newer API without changing the pinned dependency.

```ts
const stream = await client.createStream(request);
for await (const item of stream) process(item);
```

### 2.4 Why this difference matters

Type checking or execution fails because the installed package exposes only the older API surface.

## 3. Boundaries and distinctions

Supporting multiple versions can be legitimate when code explicitly detects or abstracts the supported capabilities. The failure is assuming methods from separate releases coexist in one installed version.
