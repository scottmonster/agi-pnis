# Account for local expansion in SSH command strings

## 1. Catalog record

- **Catalog identifier:** 2.3.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Commands sent through `ssh` commonly pass through a local shell and then a remote shell. Quote and structure them with both parsing stages in mind rather than interpolating arbitrary local values into remote shell source.

## 2. Example

### 2.1 Scenario

A release script asks a remote host to write its own hostname to a status file. The hostname must be expanded on the remote machine.

### 2.2 Preferred form

```bash
#!/usr/bin/env bash
set -euo pipefail

remote_host='app.example.test'
ssh -- "$remote_host" 'printf "%s\\n" "$HOSTNAME" > /var/tmp/host-status'
```

### 2.3 Hazardous form

```bash
#!/usr/bin/env bash
set -euo pipefail

remote_host='app.example.test'
ssh -- "$remote_host" "printf '%s\\n' \"$HOSTNAME\" > /var/tmp/host-status"
```

### 2.4 Why this difference matters

The double-quoted remote command expands `$HOSTNAME` locally before `ssh` sends it. Quoting the remote program as shell source keeps that expansion for the remote shell.

## 3. Boundaries and distinctions

When a local value must be sent remotely, pass it through a controlled argument or safely encoded input. Do not concatenate arbitrary data into a remote shell program.
