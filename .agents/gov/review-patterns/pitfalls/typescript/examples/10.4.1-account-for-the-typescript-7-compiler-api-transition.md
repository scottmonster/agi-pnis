# Account for the TypeScript 7 compiler-API transition

## 1. Catalog record

- **Catalog identifier:** 10.4.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** As of TypeScript 7.0, tools requiring the programmatic TypeScript compiler API may still need TypeScript 6 through `@typescript/typescript6` or the documented alias arrangement until the new API arrives.

## 2. Example

### 2.1 Scenario

A build plugin creates a TypeScript program to inspect source files before emitting a report.

### 2.2 Preferred form

```typescript
// package.json installs: "@typescript/typescript6": "^6.0.0"
import ts from "@typescript/typescript6";

export function countSourceFiles(fileNames: readonly string[]): number {
  const program = ts.createProgram([...fileNames], { noEmit: true });
  return program.getSourceFiles().length;
}
```

### 2.3 Hazardous form

```typescript
// package.json installs only: "typescript": "^7.0.0"
import ts from "typescript";

export function countSourceFiles(fileNames: readonly string[]): number {
  const program = ts.createProgram([...fileNames], { noEmit: true });
  return program.getSourceFiles().length;
}
```

### 2.4 Why this difference matters

The TypeScript 7 compiler and language service transition does not yet provide the established programmatic API expected by many build tools. Upgrading the package without a compatibility plan can break the tool before it analyzes any source.

## 3. Boundaries and distinctions

This applies to tools that directly use the compiler API, not ordinary projects that only invoke `tsc`. Follow the current documented migration path and remove the compatibility dependency when the needed TypeScript 7 API is available.
