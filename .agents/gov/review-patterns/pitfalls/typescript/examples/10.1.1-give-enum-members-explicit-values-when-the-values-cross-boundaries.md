# Give enum members explicit values when the values cross boundaries

## 1. Catalog record

- **Catalog identifier:** 10.1.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Explicitly initialize enum members when their numeric/string values are persisted, serialized, stored in databases, sent over APIs, or otherwise externally significant.

## 2. Example

### 2.1 Scenario

An order service stores its status in a database and later sends that same value to another service.

### 2.2 Preferred form

```typescript
enum OrderStatus {
  Pending = "pending",
  Paid = "paid",
  Shipped = "shipped",
}

function serializeStatus(status: OrderStatus): string {
  return status;
}

const databaseValue = serializeStatus(OrderStatus.Paid); // "paid"
```

### 2.3 Hazardous form

```typescript
enum OrderStatus {
  Pending,
  AwaitingFraudReview,
  Paid,
  Shipped,
}

function isPaid(databaseValue: number): boolean {
  return databaseValue === OrderStatus.Paid;
}

isPaid(1); // false, although 1 meant Paid before AwaitingFraudReview was inserted
```

### 2.4 Why this difference matters

Auto-numbered members make the stored representation depend on declaration order. Inserting a new member silently changes the meaning of old data.

## 3. Boundaries and distinctions

Automatic numbering is reasonable for values that never leave a tightly controlled process. Explicit values matter when another stored version, service, or consumer must interpret the value consistently.
