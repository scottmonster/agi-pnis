# Remember JSON struct field matching is case-insensitive

## 1. Catalog record

- **Catalog identifier:** 10.3.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Avoid designing externally exposed schemas whose fields differ only by case, and do not assume Go's decoder requires exact-case matching.

## 2. Example

### 2.1 Scenario

An API publishes a stable user identifier field and needs to understand how incoming field names are resolved by `encoding/json`.

### 2.2 Preferred form

```go
package example

import "encoding/json"

type User struct {
	UserID string `json:"user_id"`
}

func decodeUser(data []byte) (User, error) {
	var user User
	err := json.Unmarshal(data, &user)
	return user, err
}
```

### 2.3 Hazardous form

```go
package example

import "encoding/json"

type Credential struct {
	Token string `json:"token"`
	TOKEN string `json:"TOKEN"`
}

func decodeCredential(data []byte) (Credential, error) {
	var credential Credential
	err := json.Unmarshal(data, &credential)
	return credential, err // "ToKeN" is not an unambiguous external contract
}
```

### 2.4 Why this difference matters

The decoder accepts case-insensitive matches after trying exact names. Fields that differ only by case make clients and future schema changes ambiguous instead of enforcing a strict spelling.

## 3. Boundaries and distinctions

Explicit tags are still useful for a canonical wire spelling. If exact case is a security or protocol requirement, validate raw field names before or alongside decoding.
