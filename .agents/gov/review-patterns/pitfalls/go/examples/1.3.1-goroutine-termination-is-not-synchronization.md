# Goroutine termination is not synchronization

## 1. Catalog record

- **Catalog identifier:** 1.3.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Do not start a goroutine, let it write shared state, and assume its eventual termination makes those writes visible. Synchronize completion explicitly.

## 2. Example

### 2.1 Scenario

A caller needs a computed result before it prints it.

### 2.2 Preferred form

```go
package main

import "fmt"

func main() {
	result := make(chan int, 1)
	go func() { result <- 42 }()
	fmt.Println(<-result)
}
```

### 2.3 Hazardous form

```go
package main

import "fmt"

func main() {
	result := 0
	go func() { result = 42 }()
	fmt.Println(result)
}
```

### 2.4 Why this difference matters

The print can run before the goroutine writes, and the concurrent read and write are a data race. Receiving from the channel waits for and synchronizes with the send.

## 3. Boundaries and distinctions

A `WaitGroup` plus synchronized shared access can also coordinate completion. Sleeping is timing speculation, not synchronization.
