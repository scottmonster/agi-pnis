# Treat double assertions as an escape hatch

## 1. Catalog record

- **Catalog identifier:** 1.6.2
- **Impact:** high
- **Consensus:** high
- **Definition:** Avoid patterns such as `value as unknown as T` except at a deliberately audited unsafe boundary.

## 2. Example

### 2.1 Scenario

An unknown input must become a checked application user.

### 2.2 Preferred form

```typescript
type User = { id: string; active: boolean };

function parseUser(value: unknown): User {
  if (
    typeof value === 'object' && value !== null &&
    'id' in value && typeof value.id === 'string' &&
    'active' in value && typeof value.active === 'boolean'
  ) {
    return { id: value.id, active: value.active };
  }
  throw new Error('Invalid user');
}
```

### 2.3 Hazardous form

```typescript
type User = { id: string; active: boolean };

function parseUser(value: unknown): User {
  return value as unknown as User; // Bypasses assertion compatibility checks.
}
```

### 2.4 Why this difference matters

The intermediate `unknown` exists mainly to bypass TypeScript's assertion compatibility check, so the resulting type has effectively been accepted on trust.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
