# Keep APIs consistently synchronous or asynchronous

## 1. Catalog record

- **Catalog identifier:** 7.1.13
- **Impact:** medium
- **Consensus:** high
- **Definition:** Avoid APIs that invoke a callback synchronously on one path and asynchronously on another. Normalize their scheduling contract.

## 2. Example

### 2.1 Scenario

A lookup reads cached users immediately and otherwise fetches them, while callers need a stable callback ordering guarantee.

### 2.2 Preferred form

```javascript
function getUser(id, cache, callback) {
  const value = cache.get(id);
  if (value) {
    queueMicrotask(() => callback(null, value));
    return;
  }
  Promise.resolve({ id }).then((user) => callback(null, user), (error) => callback(error));
}

getUser("u-1", new Map([["u-1", { id: "u-1" }]]), console.log);
console.log("after getUser");
```

### 2.3 Hazardous form

```javascript
function getUser(id, cache, callback) {
  const value = cache.get(id);
  if (value) {
    callback(null, value);
    return;
  }
  Promise.resolve({ id }).then((user) => callback(null, user));
}

getUser("u-1", new Map([["u-1", { id: "u-1" }]]), console.log);
console.log("after getUser");
```

### 2.4 Why this difference matters

The hazardous cache hit invokes the callback before the following statement, while a miss invokes it later, creating branch-dependent ordering.

## 3. Boundaries and distinctions

Some APIs intentionally offer separate synchronous and asynchronous methods, but one method should not silently alternate its timing contract.
