# Reuse HTTP clients and transports

## 1. Catalog record

- **Catalog identifier:** 9.5.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Keep reusable `http.Client` and `Transport` instances rather than constructing a fresh transport for every request.

## 2. Example

### 2.1 Scenario

A service makes many requests to the same upstream over its lifetime.

### 2.2 Preferred form

```go
package example

import "net/http"

type API struct{ client *http.Client }

func NewAPI() *API {
	return &API{client: &http.Client{Transport: http.DefaultTransport}}
}

func (a *API) Get(url string) (*http.Response, error) { return a.client.Get(url) }
```

### 2.3 Hazardous form

```go
package example

import "net/http"

func get(url string) (*http.Response, error) {
	client := &http.Client{Transport: &http.Transport{}}
	return client.Get(url) // Loses connection pooling for every call.
}
```

### 2.4 Why this difference matters

Reusable transports keep connection pools, reduce connection setup cost, and avoid needless resource churn. A new transport per request defeats that sharing.

## 3. Boundaries and distinctions

Separate clients or transports are appropriate when requests require different proxy, TLS, cookie, or connection policies. Close response bodies in either design.
