# Non-importable multiprocessing targets

## 1. Catalog record

- **Catalog identifier:** 3.5.1
- **Impact:** high
- **Consensus:** high
- **Definition:** With spawn and forkserver, use picklable arguments and ordinarily define worker functions at importable module scope rather than relying on lambdas, REPL definitions, or local functions.

## 2. Example

### 2.1 Scenario

A process pool transforms customer IDs with the spawn start method. The target function and its inputs must cross a serialization boundary.

### 2.2 Preferred form

```python
from multiprocessing import get_context


def normalize_customer_id(customer_id: str) -> str:
    return customer_id.strip().upper()


if __name__ == "__main__":
    context = get_context("spawn")
    with context.Pool() as pool:
        print(pool.map(normalize_customer_id, [" a1 ", "b2"]))
```

### 2.3 Hazardous form

```python
from multiprocessing import get_context


if __name__ == "__main__":
    context = get_context("spawn")
    with context.Pool() as pool:
        print(pool.map(lambda customer_id: customer_id.strip().upper(), [" a1 ", "b2"]))
```

### 2.4 Why this difference matters

Spawned workers need to import and unpickle the target. A lambda or local function normally has no importable module-level name, so worker startup or task submission fails.

## 3. Boundaries and distinctions

Some fork-only environments can appear to accept non-importable targets, but code intended to support spawn or forkserver should use importable functions and picklable data.
