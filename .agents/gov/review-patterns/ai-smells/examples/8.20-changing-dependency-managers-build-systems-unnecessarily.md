# Changing dependency managers/build systems unnecessarily

## 1. Catalog record

- **Catalog identifier:** 8.20
- **Evidence:** se
- **Definition:** Replaces package or build tooling when the existing system can support the requested work.

## 2. Scenario

### 2.1 Context

An agent is asked to add a small API endpoint to a service built and deployed with the repository’s established package manager and build scripts.

### 2.2 Safer approach

It uses the existing package manager, adds the endpoint within the current build layout, and runs the documented build and test commands.

### 2.3 Failure mode

It migrates the repository from npm to another package manager and replaces build configuration while adding the endpoint, even though the current tooling handles the code and deployment unchanged.

### 2.4 Why this difference matters

The endpoint change becomes entangled with a migration that alters contributor workflows, CI, caches, lockfiles, and deployment assumptions, increasing risk and review scope.

## 3. Boundaries and distinctions

A tooling migration can be justified by a supported-platform need, an unsolved limitation, or an explicitly approved modernization project. This failure applies when existing tooling can meet the task and migration is not required.
