# Needless lockfile/build-file churn

## 1. Catalog record

- **Catalog identifier:** 8.17
- **Evidence:** se
- **Definition:** Alters unrelated resolved versions or build metadata, obscuring the intended change and increasing merge risk.

## 2. Scenario

### 2.1 Context

A task asks an agent to change a component label in a web application. The repository uses a committed lockfile and has no dependency change in the requested work.

### 2.2 Safer approach

It edits the component and its focused test, reviews the diff, and leaves `package-lock.json` untouched because no dependency metadata needs to change.

### 2.3 Failure mode

It runs a broad install command before making the label edit and commits hundreds of unrelated lockfile version and integrity changes with the component change.

### 2.4 Why this difference matters

Reviewers cannot easily identify the intended behavior change, and unrelated resolution changes create conflicts, obscure supply-chain review, and can introduce untested updates.

## 3. Boundaries and distinctions

Lockfile or build-file updates are necessary when the task changes a declared dependency, generated build input, or intentionally refreshes resolutions. This failure is the unrelated churn, rather than a required synchronized metadata update.
