# Prefer `unknown` over `any` for unknown values

## 1. Catalog record

- **Catalog identifier:** 1.4.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Use `unknown` when a value can legitimately be anything but must be inspected before use; reserve `any` for deliberate type-checking escape hatches.

## 2. Example

### 2.1 Scenario

A JSON setting has an unknown runtime shape.

### 2.2 Preferred form

```typescript
function readPort(value: unknown): number {
  if (typeof value !== 'number' || !Number.isInteger(value)) {
    throw new Error('Port must be an integer');
  }

  return value;
}
```

### 2.3 Hazardous form

```typescript
const setting: any = JSON.parse('{"port":"not-a-number"}');

// `any` permits an invalid operation without first checking the value.
const port = setting.port.toFixed(0);
```

### 2.4 Why this difference matters

`unknown` forces narrowing before operations, while `any` propagates unchecked assumptions throughout the program.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
