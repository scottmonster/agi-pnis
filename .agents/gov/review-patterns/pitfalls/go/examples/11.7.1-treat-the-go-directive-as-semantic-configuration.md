# Treat the `go` directive as semantic configuration

## 1. Catalog record

- **Catalog identifier:** 11.7.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Update the module's `go` version deliberately rather than treating it as cosmetic metadata.

## 2. Example

### 2.1 Scenario

A package begins using language behavior introduced in Go 1.23. The module declaration must reflect the compatibility decision.

### 2.2 Preferred form

```go
package example

func values(yield func(int) bool) {
	yield(1)
}

func preferred() int {
	// This module has been validated with: go 1.23
	for value := range values {
		return value
	}
	return 0
}
```

### 2.3 Hazardous form

```go
package example

func values(yield func(int) bool) {
	yield(1)
}

func hazardous() int {
	// The module still declares an older go version that rejects this syntax.
	for value := range values {
		return value
	}
	return 0
}
```

### 2.4 Why this difference matters

The `go` directive participates in language-version and module behavior. Changing it without compatibility validation can make a module fail or behave differently for supported consumers.

## 3. Boundaries and distinctions

Updating the directive is appropriate when the project intentionally changes its minimum Go version. The rule is to make and validate that decision explicitly, not to avoid updates forever.
