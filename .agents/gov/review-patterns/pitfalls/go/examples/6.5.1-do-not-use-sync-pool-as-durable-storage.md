# Do not use `sync.Pool` as durable storage

## 1. Catalog record

- **Catalog identifier:** 6.5.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Use `sync.Pool` only for temporary reusable objects whose disappearance is harmless.

## 2. Example

### 2.1 Scenario

A service keeps session records for later requests.

### 2.2 Preferred form

```go
package main

import "sync"

type sessions struct { mu sync.Mutex; data map[string]string }
func (s *sessions) store(id, user string) { s.mu.Lock(); defer s.mu.Unlock(); s.data[id] = user }
```

### 2.3 Hazardous form

```go
package main

import "sync"

var sessions sync.Pool
func store(id, user string) { sessions.Put(map[string]string{id: user}) }
func load() map[string]string { return sessions.Get().(map[string]string) }
```

### 2.4 Why this difference matters

The runtime may discard pool entries, and `Get` can return nil. A pool is a temporary allocation cache, not storage.

## 3. Boundaries and distinctions

Use pools for disposable buffers or encoders, reset them before reuse, and never retain an object after returning it to the pool.
