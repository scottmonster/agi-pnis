# Bound concurrency instead of spawning without limit

## 1. Catalog record

- **Catalog identifier:** 1.5.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Put an explicit limit on simultaneously active work when the input size can grow. Worker pools or `errgroup.SetLimit` are preferable to one unrestricted goroutine per item.

## 2. Example

### 2.1 Scenario

A service must process an input list whose size is controlled by clients.

### 2.2 Preferred form

```go
package main

import "sync"

func process(items []string) {
	jobs := make(chan string)
	var workers sync.WaitGroup
	for range 8 {
		workers.Go(func() {
			for item := range jobs {
				_ = item
			}
		})
	}
	for _, item := range items {
		jobs <- item
	}
	close(jobs)
	workers.Wait()
}
```

### 2.3 Hazardous form

```go
package main

func process(items []string) {
	for _, item := range items {
		go func() { _ = item }()
	}
}
```

### 2.4 Why this difference matters

The hazardous version can create one goroutine per unbounded item, exhausting memory, file descriptors, or downstream capacity. The worker count caps simultaneous work.

## 3. Boundaries and distinctions

Small, trusted, bounded collections can tolerate one goroutine per item. Choose the limit according to CPU, memory, and downstream service capacity.
