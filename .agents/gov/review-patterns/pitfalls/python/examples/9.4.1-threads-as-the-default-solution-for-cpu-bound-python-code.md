# Threads as the default solution for CPU-bound Python code

## 1. Catalog record

- **Catalog identifier:** 9.4.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** On ordinary GIL-enabled CPython, prefer processes, subinterpreters where applicable, native code that releases the GIL, or another suitable strategy for parallel CPU-bound Python bytecode.

## 2. Example

### 2.1 Scenario

A batch job must calculate many independent numeric scores using pure Python code.

### 2.2 Preferred form

```python
from concurrent.futures import ProcessPoolExecutor

def score(value: int) -> int:
    return sum(number * number for number in range(value))

with ProcessPoolExecutor() as executor:
    results = list(executor.map(score, [100_000, 110_000]))

print(results)
```

### 2.3 Hazardous form

```python
from concurrent.futures import ThreadPoolExecutor

def score(value: int) -> int:
    return sum(number * number for number in range(value))

with ThreadPoolExecutor() as executor:
    results = list(executor.map(score, [100_000, 110_000]))

print(results)
```

### 2.4 Why this difference matters

On typical GIL-enabled CPython builds, the thread pool does not run this CPU-bound Python bytecode in parallel, so it may add overhead without improving throughput.

## 3. Boundaries and distinctions

Threads remain an excellent choice for many I/O-bound tasks and for native libraries that release the GIL. The best execution model depends on the interpreter and workload.
