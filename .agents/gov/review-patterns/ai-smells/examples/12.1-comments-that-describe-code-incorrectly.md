# Comments that describe code incorrectly

## 1. Catalog record

- **Catalog identifier:** 12.1
- **Evidence:** e/se
- **Definition:** Documentation adjacent to code states behavior, constraints, or ownership that no longer matches the implementation.

## 2. Scenario

### 2.1 Context

A payment retry helper was changed to make three attempts, but its inline comment still says it makes one retry to avoid duplicate charges.

### 2.2 Safer approach

Update the comment with the implementation change, stating the three-attempt limit and the idempotency protection that makes those attempts safe.

### 2.3 Failure mode

Leave the old comment in place because the retry loop itself is correct and tests pass.

### 2.4 Why this difference matters

The stale comment misleads a future maintainer about the retry behavior and its safety constraints, making an otherwise intentional implementation look unsafe or broken.

## 3. Boundaries and distinctions

This concerns comments that disagree with existing code. It differs from documentation that promises a feature that has never been implemented.
