# Guidance File

This document defines guidance files, explains how they should be used, and sets their boundaries.

A guidance file is a reference that helps people or agents make sound, context-appropriate decisions while performing a type of work. It primarily provides recommended practices, decision factors, examples, cautions, and other advisory guidance. When necessary, it may also define specific requirements for outcomes, actions, processes, procedures, formats, constraints, or other aspects of the work.

Guidance informs judgment. Requirements constrain only what must be constrained.

### How guidance is used

Use a guidance file to identify relevant considerations, select suitable practices, and adapt an approach to the task's scope, risk, domain, constraints, and intended outcome. Apply, adapt, or omit advisory guidance based on its relevance to the work at hand.

A guidance file should preserve judgment and flexibility wherever multiple approaches can appropriately achieve the intended result. It should not impose a fixed procedure, universal scoring system, mandatory output format, identical treatment, or other constraint merely for consistency or convenience.

When a particular outcome, action, process, procedure, format, constraint, or other aspect of the work is necessary, the guidance file may define it as a requirement. Such requirements should be limited to the aspects of the work that actually need to be constrained.

Where an outcome is required but the means of achieving it are not, specify the required outcome and leave the method open. Where a particular action, process, or procedure is itself necessary, the requirement may specify it without unnecessarily constraining unrelated aspects of the work.

### Boundaries

* A guidance file primarily provides recommendations, considerations, preferred practices, cautions, examples, and decision criteria.
* A guidance file may define specific requirements when a constraint is necessary to the work being addressed.
* Requirements should constrain only what must be constrained. A requirement that applies to one aspect of the work should not be interpreted as imposing a fixed approach on other aspects.
* A guidance file should preserve flexibility wherever different approaches can appropriately satisfy the intended outcome.
* A guidance file is not, merely by being a guidance file, a universal standard, policy, contract, or strict rule set.
* Guidance does not replace judgment, task-specific requirements, or higher-authority instructions.
* Not every part of a guidance file applies to every task.
* Advisory guidance should be applied, adapted, or omitted based on its relevance to the task and circumstances.
* Guidance should explain the purpose, reasoning, risks, or tradeoffs of a practice when doing so helps users apply it correctly.
* Requirements should not be introduced merely to enforce consistency, preference, or a single way of working when multiple approaches would satisfy the intended purpose.
* When a guidance file uses normative terms such as _MUST_ or _MUST NOT_, those statements define requirements rather than recommendations. Requirements should be clearly distinguished from advisory content, narrowly scoped to what is necessary, and accompanied by enough explanation to understand why the constraint exists.
* Where a requirement derives from another authority, policy, standard, contract, instruction, or other source, that source should be identified. A guidance file may also define requirements that are intrinsic to the guidance being provided when the stated constraint is necessary to achieve its intended purpose.

### Requirements

Guidance should remain advisory wherever judgment and adaptation are appropriate. A guidance file may define a mandatory requirement when a particular outcome, action, process, procedure, format, constraint, or other condition is necessary to the guidance being provided.

A requirement should be no broader than necessary. If only the outcome must be constrained, require the outcome and leave the means open. If a particular action, process, or procedure is itself necessary, it may also be required. Unrelated aspects of the work should remain open to judgment and adaptation.

When a requirement establishes a meaningful distinction between acceptable and unacceptable execution, the guidance file `MUST` state both sides of that distinction:

* **Required:** What must be done, achieved, included, preserved, or otherwise satisfied, together with an explanation of why the requirement exists.
* **Prohibited:** What must not be done, produced, omitted, allowed, or otherwise occur, together with an explanation of why it would violate the requirement.

The positive and negative statements should describe the actual constraint rather than prescribe unnecessary implementation details.

For example, if a particular outcome is required but several methods can achieve it, the requirement should define the required and prohibited outcomes without mandating one method. If a particular method or procedure is itself necessary, the requirement may define both the required procedure and the procedures or actions that are prohibited.

Normative requirements should be used only where the distinction is necessary. Preferences, recommendations, heuristics, examples, and generally useful practices should remain advisory.
