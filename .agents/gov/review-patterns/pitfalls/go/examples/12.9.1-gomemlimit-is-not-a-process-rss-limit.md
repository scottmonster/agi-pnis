# `GOMEMLIMIT` is not a process RSS limit

## 1. Catalog record

- **Catalog identifier:** 12.9.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Treat `GOMEMLIMIT` or `debug.SetMemoryLimit` as a soft runtime-managed memory target, not a hard cap on total process memory.

## 2. Example

### 2.1 Scenario

A service runs in a container with a 1 GiB memory limit and also uses native libraries. It sets a Go runtime memory target while leaving room for stacks, native allocations, and other process memory.

### 2.2 Preferred form

```go
package example

import "runtime/debug"

func configureMemoryTarget(containerLimit int64) {
	const reserveForNonHeapMemory = 128 << 20
	debug.SetMemoryLimit(containerLimit - reserveForNonHeapMemory)
}
```

### 2.3 Hazardous form

```go
package example

import "runtime/debug"

func configureMemoryTarget(containerLimit int64) {
	// This does not prevent the process RSS from exceeding containerLimit.
	debug.SetMemoryLimit(containerLimit)
}
```

### 2.4 Why this difference matters

The runtime target influences garbage collection and the Go runtime's memory management. It does not include every source of resident memory, so using the full container limit as though it were a hard process cap can still lead to an out-of-memory kill.

## 3. Boundaries and distinctions

`GOMEMLIMIT` is useful for controlling Go heap pressure and should normally leave a deployment-specific margin. Use container or operating-system limits when a hard process memory boundary is required.
