# Prefer consumer-defined interfaces and producer-returned concrete types

## 1. Catalog record

- **Catalog identifier:** 10.4.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Define small interfaces where behavior is consumed, and generally let constructors return concrete implementation types rather than speculative producer-side interfaces.

## 2. Example

### 2.1 Scenario

A report service needs only to write bytes, while its own buffer constructor should expose useful buffer-specific operations.

### 2.2 Preferred form

```go
package example

import (
	"bytes"
	"io"
)

func writeReport(dst io.Writer, body []byte) error {
	_, err := dst.Write(body)
	return err
}

func NewReportBuffer() *bytes.Buffer {
	return new(bytes.Buffer)
}
```

### 2.3 Hazardous form

```go
package example

import (
	"bytes"
	"io"
)

type ReportBuffer interface {
	io.Writer
	Bytes() []byte
}

func NewReportBuffer() ReportBuffer {
	return new(bytes.Buffer)
}
```

### 2.4 Why this difference matters

The producer-side interface fixes an incomplete abstraction too early and hides concrete capabilities from callers. The consumer can instead declare the smallest behavior it actually needs.

## 3. Boundaries and distinctions

Return an interface when the interface itself is the intentional stable abstraction, such as a plugin boundary. Keep consumer interfaces narrow and tailored to the consuming operation.
