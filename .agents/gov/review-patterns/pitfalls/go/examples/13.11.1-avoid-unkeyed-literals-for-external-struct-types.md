# Avoid unkeyed literals for external struct types

## 1. Catalog record

- **Catalog identifier:** 13.11.1
- **Impact:** low
- **Consensus:** high
- **Definition:** Initialize structs from other packages with field names rather than positional literals.

## 2. Example

### 2.1 Scenario

A client builds a TCP address from a standard-library type owned by another package.

### 2.2 Preferred form

```go
package example

import "net"

func loopback() net.TCPAddr {
	return net.TCPAddr{IP: net.IPv4(127, 0, 0, 1), Port: 8080}
}
```

### 2.3 Hazardous form

```go
package example

import "net"

func loopback() net.TCPAddr {
	return net.TCPAddr{net.IPv4(127, 0, 0, 1), 8080, ""}
}
```

### 2.4 Why this difference matters

The keyed form documents which fields are being set and tolerates later added fields. The positional form depends on field order and can break when the external type evolves.

## 3. Boundaries and distinctions

Unkeyed literals remain reasonable for types you own and control together. Avoid them at package boundaries where another maintainer controls the struct definition.
