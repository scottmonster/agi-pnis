# Reject unknown JSON fields when the schema must be strict

## 1. Catalog record

- **Catalog identifier:** 9.12.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Use `Decoder.DisallowUnknownFields` when unexpected object fields should cause failure rather than being silently ignored.

## 2. Example

### 2.1 Scenario

An administrative endpoint accepts a versioned configuration schema and should reject typoed fields.

### 2.2 Preferred form

```go
package example

import (
	"encoding/json"
	"io"
)

type Config struct { Enabled bool `json:"enabled"` }

func decodeConfig(r io.Reader) (Config, error) {
	decoder := json.NewDecoder(r)
	decoder.DisallowUnknownFields()
	var config Config
	err := decoder.Decode(&config)
	return config, err
}
```

### 2.3 Hazardous form

```go
package example

import (
	"encoding/json"
	"io"
)

type Config struct { Enabled bool `json:"enabled"` }

func decodeConfig(r io.Reader) (Config, error) {
	var config Config
	err := json.NewDecoder(r).Decode(&config) // {"enabeld":true} is silently ignored.
	return config, err
}
```

### 2.4 Why this difference matters

Rejecting unknown fields catches misspellings and incompatible clients at the boundary instead of applying an unintended zero value.

## 3. Boundaries and distinctions

Permissive decoding can be the right compatibility strategy for extensible public payloads. Use strict mode only where unexpected fields must be rejected.
