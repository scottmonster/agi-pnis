# Treat HTML string insertion as an injection sink

## 1. Catalog record

- **Catalog identifier:** 11.1.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Do not pass untrusted strings to HTML-parsing sinks; use text insertion or appropriate trusted sanitization.

## 2. Example

### 2.1 Scenario

A profile page displays a display name supplied by a user. The page should show the supplied text without allowing it to become markup.

### 2.2 Preferred form

```javascript
const greeting = document.querySelector("#greeting");
const displayName = "<img src=x onerror=alert('injected')>";

greeting.textContent = `Welcome, ${displayName}`;
```

### 2.3 Hazardous form

```javascript
const greeting = document.querySelector("#greeting");
const displayName = "<img src=x onerror=alert('injected')>";

greeting.innerHTML = `Welcome, ${displayName}`;
```

### 2.4 Why this difference matters

`textContent` creates a text node, so the display name is shown literally. `innerHTML` parses the untrusted value as HTML, allowing an attacker-controlled element or script-capable attribute to enter the document.

## 3. Boundaries and distinctions

HTML insertion is appropriate only for markup that is fully trusted or has been sanitized for the precise output context by a maintained sanitizer. Escaping text for an HTML context does not automatically make it safe for other contexts such as URLs or JavaScript.
