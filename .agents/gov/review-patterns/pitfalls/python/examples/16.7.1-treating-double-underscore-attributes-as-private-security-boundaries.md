# Treating double-underscore attributes as private security boundaries

## 1. Catalog record

- **Catalog identifier:** 16.7.1
- **Impact:** low
- **Consensus:** high
- **Definition:** Use double-leading-underscore name mangling primarily to avoid accidental subclass name collisions, not to enforce privacy.

## 2. Example

### 2.1 Scenario

A base class keeps an internal counter that subclasses should not accidentally shadow, while access control is enforced by a separate method.

### 2.2 Preferred form

```python
class BaseCounter:
    def __init__(self) -> None:
        self.__count = 0

    def increment(self) -> None:
        self.__count += 1

    def count_for_authorized_user(self, authorized: bool) -> int:
        if not authorized:
            raise PermissionError("not authorized")
        return self.__count
```

### 2.3 Hazardous form

```python
class SecretCounter:
    def __init__(self) -> None:
        self.__count = 0

    def public_dump(self) -> int:
        return self._SecretCounter__count
```

### 2.4 Why this difference matters

Double underscores mangle an attribute name but do not make it inaccessible. Code can still access `_SecretCounter__count`, so name mangling cannot protect secrets or enforce authorization.

## 3. Boundaries and distinctions

Name mangling is useful to reduce accidental clashes in subclass hierarchies. Enforce security with access controls, process boundaries, encryption, and other real security mechanisms.
