# Bash function locals use dynamic scope

## 1. Catalog record

- **Catalog identifier:** 7.10.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** A local variable in a Bash function is visible to functions called from that function unless they shadow it. Do not assume lexical-scope behavior from languages such as Python or JavaScript.

## 2. Example

### 2.1 Scenario

A deployment function delegates name normalization to a helper. The helper should make its input dependency explicit.

### 2.2 Preferred form

```bash
normalize_environment() {
  local input=$1
  printf '%s\n' "${input,,}"
}

deploy() {
  local environment=PRODUCTION
  local normalized
  normalized=$(normalize_environment "$environment")
  printf 'Deploying to %s\n' "$normalized"
}

deploy
```

### 2.3 Hazardous form

```bash
normalize_environment() {
  printf '%s\n' "${environment,,}"
}

deploy() {
  local environment=PRODUCTION
  normalize_environment
}

deploy
```

### 2.4 Why this difference matters

The hazardous helper reads its caller's local `environment` through Bash dynamic scope. A later caller with a same-named local can change the helper's behavior without changing its arguments or contract.

## 3. Boundaries and distinctions

Dynamic scope can be intentionally used by tightly coupled shell helpers, but it creates hidden dependencies. Prefer explicit arguments and local names when functions need reusable, predictable interfaces.
