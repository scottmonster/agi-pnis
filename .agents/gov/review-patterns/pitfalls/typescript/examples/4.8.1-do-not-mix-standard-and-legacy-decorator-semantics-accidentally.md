# Do not mix standard and legacy decorator semantics accidentally

## 1. Catalog record

- **Catalog identifier:** 4.8.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Know whether a framework expects modern decorators or legacy `experimentalDecorators`; existing legacy decorators are not automatically compatible with the standard decorator model.

## 2. Example

### 2.1 Scenario

A class uses decorators under the modern standard decorator configuration.

### 2.2 Preferred form

```typescript
function logged<This, Args extends unknown[], Return>(
  method: (this: This, ...args: Args) => Return,
  context: ClassMethodDecoratorContext<This, (this: This, ...args: Args) => Return>,
) {
  return function (this: This, ...args: Args): Return {
    console.log(`Calling ${String(context.name)}`);
    return method.call(this, ...args);
  };
}

class Service {
  @logged
  format(value: string): string {
    return value.toUpperCase();
  }
}
```

### 2.3 Hazardous form

```typescript
// Legacy decorator signature, requiring `experimentalDecorators`.
function logged(target: object, key: string, descriptor: PropertyDescriptor): void {
  const original = descriptor.value as (value: string) => string;
  descriptor.value = (value: string) => original(value);
}

class Service {
  @logged
  format(value: string): string {
    return value.toUpperCase();
  }
}
```

### 2.4 Why this difference matters

Their invocation, typing, emit, parameter-decorator support, and metadata behavior differ materially.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
