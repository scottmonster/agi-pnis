# Do not blindly cast `Object.keys` to `keyof T`

## 1. Catalog record

- **Catalog identifier:** 6.7.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Assume runtime objects may contain keys beyond their static type; use `Object.entries`, targeted validation, or a `keyof` cast only when exact keys are genuinely guaranteed.

## 2. Example

### 2.1 Scenario

A diagnostics helper lists every setting supplied at runtime.

### 2.2 Preferred form

```typescript
function describeSettings(settings: Record<string, unknown>): string[] {
  return Object.entries(settings).map(([key, value]) => `${key}=${String(value)}`);
}

console.log(describeSettings({ theme: 'dark', retries: 3 }));
```

### 2.3 Hazardous form

```typescript
function typedEntries<T extends object>(value: T): Array<[keyof T, T[keyof T]]> {
  return Object.keys(value).map((key): [keyof T, T[keyof T]] => [
    key as keyof T,
    value[key as keyof T],
  ]);
}

const settings: { theme: string } = { theme: 'dark' };
Object.defineProperty(settings, 'retries', { enumerable: true, value: 3 });

const entries = typedEntries(settings);
// TypeScript claims every key is 'theme', but runtime output also contains ['retries', 3].
```

### 2.4 Why this difference matters

Structural typing intentionally allows extra properties, which is why `Object.keys` cannot generally return `(keyof T)[]` safely.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
