# Prefer an ordinary map plus locking unless `sync.Map` fits its specialized cases

## 1. Catalog record

- **Catalog identifier:** 6.6.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Do not treat `sync.Map` as the default concurrent-map replacement. Most code is clearer and maintains stronger invariants with a typed map protected by a mutex.

## 2. Example

### 2.1 Scenario

An inventory update must never make stock negative.

### 2.2 Preferred form

```go
package main

import "sync"

type inventory struct { mu sync.Mutex; stock map[string]int }
func (i *inventory) remove(sku string, count int) bool {
	i.mu.Lock(); defer i.mu.Unlock()
	if i.stock[sku] < count { return false }
	i.stock[sku] -= count; return true
}
```

### 2.3 Hazardous form

```go
package main

import "sync"

type inventory struct { stock sync.Map }
func (i *inventory) remove(sku string, count int) bool {
	value, _ := i.stock.Load(sku); next := value.(int) - count
	if next < 0 { return false }; i.stock.Store(sku, next); return true
}
```

### 2.4 Why this difference matters

The `Load` and `Store` do not form one invariant-preserving operation, so concurrent removals can oversell stock.

## 3. Boundaries and distinctions

`sync.Map` suits specialized independently keyed workloads. Use `CompareAndSwap` only if its precise semantics protect the needed invariant.
