# `threading.local()` for asyncio-local state

## 1. Catalog record

- **Catalog identifier:** 3.14.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Use `ContextVar` for logical context that must remain isolated across concurrent asynchronous tasks rather than storing such state in `threading.local()`.

## 2. Example

### 2.1 Scenario

Two request handlers run concurrently on one event-loop thread and each must retain its own request identifier.

### 2.2 Preferred form

```python
import asyncio
from contextvars import ContextVar


request_id: ContextVar[str] = ContextVar("request_id")


async def handle(identifier: str) -> str:
    token = request_id.set(identifier)
    try:
        await asyncio.sleep(0)
        return request_id.get()
    finally:
        request_id.reset(token)


async def main() -> list[str]:
    return await asyncio.gather(handle("a"), handle("b"))


assert asyncio.run(main()) == ["a", "b"]
```

### 2.3 Hazardous form

```python
import asyncio
import threading


request_state = threading.local()


async def handle(identifier: str) -> str:
    request_state.identifier = identifier
    await asyncio.sleep(0)
    return request_state.identifier


async def main() -> list[str]:
    return await asyncio.gather(handle("a"), handle("b"))


assert asyncio.run(main()) == ["b", "b"]
```

### 2.4 Why this difference matters

Asyncio tasks can share a single OS thread. `threading.local()` therefore stores one value for both tasks, allowing one request to overwrite another request's state.

## 3. Boundaries and distinctions

`threading.local()` remains suitable for state that is truly isolated by OS thread. `ContextVar` is designed to follow logical asynchronous context.
