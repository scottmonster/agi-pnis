# N+1 query/API behavior

## 1. Catalog record

- **Catalog identifier:** 7.9
- **Evidence:** se
- **Definition:** Fetches a collection once, then makes an additional query or request for each item in that collection.

## 2. Scenario

### 2.1 Context

An agent implements a page listing projects and each project's owner name.

### 2.2 Safer approach

It loads owners with a join, eager load, or one bulk request keyed by the project owner IDs.

### 2.3 Failure mode

It queries all projects, then issues one owner query for every listed project.

### 2.4 Why this difference matters

One collection query becomes N additional remote operations, so page latency and database load scale poorly with the list.

## 3. Boundaries and distinctions

This is a specific collection-plus-per-item access pattern, not every repeated query; individual requests can be valid when each item needs distinct data unavailable in bulk.
