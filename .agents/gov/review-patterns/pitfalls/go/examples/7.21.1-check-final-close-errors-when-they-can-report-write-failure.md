# Check final close errors when they can report write failure

## 1. Catalog record

- **Catalog identifier:** 7.21.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** For output resources whose `Close` finalizes or flushes content, do not automatically discard the close error when no earlier error occurred.

## 2. Example

### 2.1 Scenario

A CSV exporter writes to an output file that can report a delayed error while closing.

### 2.2 Preferred form

```go
package export

import "io"

func write(destination io.WriteCloser, data []byte) (err error) {
	defer func() {
		if closeErr := destination.Close(); err == nil { err = closeErr }
	}()
	_, err = destination.Write(data)
	return err
}
```

### 2.3 Hazardous form

```go
package export

import "io"

func write(destination io.WriteCloser, data []byte) error {
	defer destination.Close() // A final write or finalization error is lost.
	_, err := destination.Write(data)
	return err
}
```

### 2.4 Why this difference matters

Some output formats and filesystems report finalization failures only from `Close`, so success could be reported for incomplete data.

## 3. Boundaries and distinctions

If an earlier operation has already failed, preserve that primary error unless the API requires a combined error report.
