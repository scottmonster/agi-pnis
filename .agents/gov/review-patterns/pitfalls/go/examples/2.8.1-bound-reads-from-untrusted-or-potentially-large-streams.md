# Bound reads from untrusted or potentially large streams

## 1. Catalog record

- **Catalog identifier:** 2.8.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Do not use `io.ReadAll` on an unbounded attacker-controlled or arbitrarily large source. Apply an appropriate limit or stream the content.

## 2. Example

### 2.1 Scenario

An upload endpoint accepts a small JSON settings document from an untrusted request body and rejects input above its documented size limit.

### 2.2 Preferred form

```go
package example

import (
	"fmt"
	"io"
)

const maxSettingsSize = 1 << 20

func readSettings(body io.Reader) ([]byte, error) {
	limited := io.LimitReader(body, maxSettingsSize+1)
	data, err := io.ReadAll(limited)
	if err != nil {
		return nil, err
	}
	if len(data) > maxSettingsSize {
		return nil, fmt.Errorf("settings body exceeds %d bytes", maxSettingsSize)
	}
	return data, nil
}
```

### 2.3 Hazardous form

```go
package example

import "io"

func readSettings(body io.Reader) ([]byte, error) {
	return io.ReadAll(body) // an untrusted body can force unbounded allocation
}
```

### 2.4 Why this difference matters

`io.ReadAll` grows memory until the source ends. An attacker or broken peer can keep sending data, exhausting memory and denying service before the application can validate the content.

## 3. Boundaries and distinctions

`io.ReadAll` is appropriate for known, bounded data such as an in-memory reader or a size-checked file. For large legitimate streams, process incrementally instead of selecting an arbitrarily large whole-body limit.
