# Avoid async Promise executors

## 1. Catalog record

- **Catalog identifier:** 7.1.3
- **Impact:** high
- **Consensus:** high
- **Definition:** Do not write `new Promise(async (resolve, reject) => ...)`. Prefer an ordinary executor or, usually, make the surrounding function `async` and return its result directly.

## 2. Example

### 2.1 Scenario

A service loads a settings document from an asynchronous storage API.

### 2.2 Preferred form

```javascript
async function readSettings(storage) {
  const text = await storage.read("settings.json");
  return JSON.parse(text);
}

const storage = { read: async () => '{"theme":"dark"}' };
readSettings(storage).then(console.log, console.error);
```

### 2.3 Hazardous form

```javascript
function readSettings(storage) {
  return new Promise(async (resolve, reject) => {
    const text = await storage.read("settings.json");
    resolve(JSON.parse(text));
  });
}

const storage = { read: async () => '{"theme":"dark"}' };
readSettings(storage).then(console.log, console.error);
```

### 2.4 Why this difference matters

If the async executor throws after an await, its returned promise rejects separately and the constructed promise can remain pending.

## 3. Boundaries and distinctions

An ordinary Promise executor is appropriate when adapting a callback API, but it must settle through `resolve` or `reject`.
