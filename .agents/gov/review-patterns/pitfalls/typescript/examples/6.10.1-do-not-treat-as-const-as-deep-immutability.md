# Do not treat `as const` as deep immutability

## 1. Catalog record

- **Catalog identifier:** 6.10.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Use `as const` for literal preservation and readonly tuple/property inference, not as a guarantee that every referenced nested object can never mutate.

## 2. Example

### 2.1 Scenario

A client configuration must keep its retry policy unchanged at runtime.

### 2.2 Preferred form

```typescript
const clientConfig = Object.freeze({
  endpoint: 'https://api.example',
  retry: Object.freeze({ attempts: 3 }),
});

console.log(clientConfig.retry.attempts);
```

### 2.3 Hazardous form

```typescript
const retry = { attempts: 3 };
const clientConfig = { endpoint: 'https://api.example', retry } as const;

retry.attempts = 0;
console.log(clientConfig.retry.attempts); // `as const` did not freeze the referenced object.
```

### 2.4 Why this difference matters

A const assertion changes static inference but does not freeze the runtime object graph.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
