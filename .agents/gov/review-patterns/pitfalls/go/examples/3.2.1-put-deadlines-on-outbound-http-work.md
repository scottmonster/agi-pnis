# Put deadlines on outbound HTTP work

## 1. Catalog record

- **Catalog identifier:** 3.2.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Use request contexts, `Client.Timeout`, or appropriately configured transport deadlines for calls that must not wait indefinitely.

## 2. Example

### 2.1 Scenario

An API handler calls an upstream profile service while the caller is waiting for the answer. The upstream call needs a bounded share of the request budget.

### 2.2 Preferred form

```go
package example

import (
	"context"
	"net/http"
	"time"
)

func fetchProfile(parent context.Context, client *http.Client, url string) error {
	ctx, cancel := context.WithTimeout(parent, 2*time.Second)
	defer cancel()

	req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
	if err != nil {
		return err
	}
	resp, err := client.Do(req)
	if err != nil {
		return err
	}
	defer resp.Body.Close()
	return nil
}
```

### 2.3 Hazardous form

```go
package example

import "net/http"

func fetchProfile(client *http.Client, url string) error {
	resp, err := client.Get(url) // Can wait forever for a broken upstream.
	if err != nil {
		return err
	}
	defer resp.Body.Close()
	return nil
}
```

### 2.4 Why this difference matters

The context deadline stops this operation when its budget expires, including during body reading. Without a deadline, stuck connections or servers can tie up goroutines and request capacity indefinitely.

## 3. Boundaries and distinctions

Choose limits from the operation's latency budget and retry behavior. A shared `Client.Timeout` or transport-level timeouts can be suitable, but a request context is usually needed when the caller's cancellation must propagate.
