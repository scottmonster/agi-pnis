# Do not assume `rootDir` controls what enters the program

## 1. Catalog record

- **Catalog identifier:** 10.12.1
- **Impact:** low
- **Consensus:** high
- **Definition:** Use `include`, `files`, references, and import structure to control program membership; use `rootDir` primarily to define source/output layout expectations.

## 2. Example

### 2.1 Scenario

A service package should compile only production sources, while test fixtures remain in a separate test project.

### 2.2 Preferred form

```typescript
// tsconfig.json: { "compilerOptions": { "rootDir": "./src" }, "include": ["src/**/*.ts"] }
// src/index.ts
export function formatOrderId(id: number): string {
  return `order-${id}`;
}

// test/tsconfig.json references the service project and owns test fixtures.
```

### 2.3 Hazardous form

```typescript
// tsconfig.json: { "compilerOptions": { "rootDir": "./src" } }
// src/index.ts
import { fixtureOrderId } from "../test/fixture.js";

export function formatFixtureOrder(): string {
  return `order-${fixtureOrderId}`;
}

// The imported test/fixture.ts enters the program despite rootDir being ./src.
```

### 2.4 Why this difference matters

`rootDir` defines an expected source and output layout. It does not exclude imported files or otherwise select the program's roots, so relying on it for membership can pull test code into a production compile or cause layout diagnostics.

## 3. Boundaries and distinctions

Use `rootDir` to validate and shape emit layout. Use `files`, `include`, project references, and import boundaries to determine which files belong to a compilation.
