# Use `skipLibCheck` deliberately, not as a universal fix

## 1. Catalog record

- **Catalog identifier:** 7.12.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Treat `skipLibCheck` as a performance or migration tradeoff and fix duplicate or incompatible dependency declarations when practical.

## 2. Example

### 2.1 Scenario

A library upgrade introduces two incompatible declaration packages. The team wants fast local checks, but still needs CI to reveal the dependency conflict.

### 2.2 Preferred form

```typescript
// tsconfig.json
// { "compilerOptions": { "strict": true, "skipLibCheck": false } }

// package.json
// { "overrides": { "@types/node": "22.10.0" } }

// Resolve the conflicting transitive @types/node versions, then keep library
// declaration checking enabled in CI.
```

### 2.3 Hazardous form

```typescript
// tsconfig.json
// { "compilerOptions": { "strict": true, "skipLibCheck": true } }

// The duplicate declarations no longer report errors, but TypeScript now trusts
// whichever incompatible declarations happen to be consumed by the program.
```

### 2.4 Why this difference matters

`skipLibCheck` skips checking `.d.ts` files, including declarations supplied by dependencies. It can substantially reduce check time and help a migration move forward, but it can also hide duplicate globals, incompatible overloads, and a library compiled against different assumptions. Pinning or deduplicating the offending packages preserves a more reliable type boundary.

## 3. Boundaries and distinctions

Keeping `skipLibCheck` enabled can be a reasonable temporary migration decision or a deliberate performance tradeoff for a large application. Record the reason, check declarations in at least one CI configuration when feasible, and do not expect the option to repair runtime incompatibilities or errors in application source files.
