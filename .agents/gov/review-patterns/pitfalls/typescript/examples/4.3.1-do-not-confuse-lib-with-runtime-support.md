# Do not confuse `lib` with runtime support

## 1. Catalog record

- **Catalog identifier:** 4.3.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Configure `lib` to describe APIs actually supplied by the target runtime or by intentional polyfills, rather than enabling newer libraries merely to eliminate type errors.

## 2. Example

### 2.1 Scenario

An application supports a runtime that may not implement the newest built-in APIs.

### 2.2 Preferred form

```typescript
// `Array.prototype.at` is used only after the required polyfill is installed.
function last<T>(items: readonly T[]): T | undefined {
  return items.at(-1);
}

console.log(last(['first', 'last']));
```

### 2.3 Hazardous form

```typescript
// Including ES2022 in `lib` makes this compile, but does not add `at` to an old runtime.
const last = ['first', 'last'].at(-1);
```

### 2.4 Why this difference matters

Adding a library declaration tells TypeScript that an API exists but does not install or polyfill that API.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
