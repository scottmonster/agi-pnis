# Use an interface instead of a type parameter when only methods matter

## 1. Catalog record

- **Catalog identifier:** 10.11.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** If generic code only invokes methods defined by the constraint and gains nothing from retaining the concrete type, a normal interface parameter is usually simpler.

## 2. Example

### 2.1 Scenario

A notifier only calls `Send` and does not need to return, store, or otherwise preserve the notifier's concrete type.

### 2.2 Preferred form

```go
package example

type Sender interface {
	Send(string) error
}

func notify(sender Sender, message string) error {
	return sender.Send(message)
}
```

### 2.3 Hazardous form

```go
package example

type Sender interface {
	Send(string) error
}

func notify[T Sender](sender T, message string) error {
	return sender.Send(message) // T is never used as a concrete type
}
```

### 2.4 Why this difference matters

The type parameter adds syntax and inference behavior without providing type-preserving value flow or operations unavailable through the interface. The interface directly states the needed capability.

## 3. Boundaries and distinctions

Use a type parameter when the algorithm must preserve or relate concrete types, operate on their underlying values, or return a value of the same type. Interface dispatch is not a universal replacement for generics.
