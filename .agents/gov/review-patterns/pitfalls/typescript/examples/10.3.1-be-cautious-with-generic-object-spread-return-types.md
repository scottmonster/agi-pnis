# Be cautious with generic object spread return types

## 1. Catalog record

- **Catalog identifier:** 10.3.1
- **Impact:** medium
- **Consensus:** medium
- **Definition:** Avoid treating a generic object spread as though its type-level intersection precisely models runtime overwrite behavior, especially in reusable generic helpers.

## 2. Example

### 2.1 Scenario

A connection editor changes only a known subset of a connection configuration.

### 2.2 Preferred form

```typescript
interface ConnectionOptions {
  retries: number;
  mode: "safe" | "fast";
}

function changeMode(
  current: ConnectionOptions,
  mode: ConnectionOptions["mode"],
): ConnectionOptions {
  return { ...current, mode };
}

const updated = changeMode({ retries: 3, mode: "safe" }, "fast");
```

### 2.3 Hazardous form

```typescript
function combine<Left extends object, Right extends object>(
  left: Left,
  right: Right,
): Left & Right {
  return { ...left, ...right } as Left & Right;
}

const options = combine({ retries: 3, mode: "safe" as const }, { mode: "fast" as const });

JSON.stringify(options.mode); // Runtime value: "fast". Type: never.
```

### 2.4 Why this difference matters

JavaScript spread overwrites an earlier property with a later one. An intersection instead says the property satisfies both types, which becomes misleading or impossible when generic inputs have conflicting keys.

## 3. Boundaries and distinctions

Object spread is useful for compatible, known shapes. A reusable merge API needs an explicit overwrite model, constraints that prevent key conflicts, or a return type designed around its real contract.
