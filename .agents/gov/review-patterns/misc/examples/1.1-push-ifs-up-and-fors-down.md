# Push Ifs Up and Fors Down

## 1. Catalog record

- **Catalog identifier:** 1.1
- **Definition:** Centralize shared control flow at an orchestration boundary, and place repeated work in batch-oriented operations when that makes the work clearer or more efficient.

## 2. Scenario

### 2.1 Context

A nightly billing job receives eligible and ineligible accounts. Eligible accounts must have their invoices generated and emailed. The job can decide eligibility once for the run, while invoice rendering benefits from receiving a batch of accounts.

### 2.2 Safer approach

```ts
if (run.isBillingDay) {
  const eligibleAccounts = accounts.filter(isEligibleForBilling);
  await generateAndSendInvoices(eligibleAccounts);
}
```

`generateAndSendInvoices` receives accounts that satisfy its precondition and can render, queue, and send them in batches.

### 2.3 Less suitable approach

```ts
for (const account of accounts) {
  if (run.isBillingDay && isEligibleForBilling(account)) {
    await generateAndSendInvoice(account);
  }
}
```

The shared calendar decision is re-evaluated for every account, and the one-account API prevents batching or reordering work.

### 2.4 Why this difference matters

The first form puts the business decision where it is visible and keeps the processing routine focused on its valid input. It also gives the implementation one place to amortize setup and use batch-friendly execution.

## 3. Boundaries and distinctions

Do not move a condition upward when each item has a distinct decision, when the callee must defend a public or untrusted boundary, or when a small scalar operation is clearer and there is no meaningful batching benefit. This is a heuristic for shared control flow and repeated work, not a rule to remove all checks or loops.
