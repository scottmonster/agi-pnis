# Distinguish invalid regex from no regex match

## 1. Catalog record

- **Catalog identifier:** 4.9.2
- **Impact:** medium
- **Consensus:** high
- **Definition:** Handle status 2 from `=~` as an invalid regex rather than an ordinary nonmatch.

## 2. Example

### 2.1 Scenario

A validator receives a dynamically configured regex and must report malformed patterns separately from ordinary nonmatches.

### 2.2 Preferred form

```bash
#!/usr/bin/env bash

value=${1:?provide a value}
pattern=${2:?provide a regex}

if [[ $value =~ $pattern ]]; then
  printf 'matched\n'
else
  status=$?
  if (( status == 2 )); then
    printf 'invalid regex: %s\n' "$pattern" >&2
    exit 2
  fi
  printf 'did not match\n'
fi
```

### 2.3 Hazardous form

```bash
#!/usr/bin/env bash

value=${1:?provide a value}
pattern=${2:?provide a regex}
if [[ $value =~ $pattern ]]; then
  printf 'matched\n'
else
  printf 'did not match\n'
fi
```

### 2.4 Why this difference matters

Regex matching returns 1 for a valid nonmatch and 2 for an invalid expression. Treating both statuses as a nonmatch hides configuration errors.

## 3. Boundaries and distinctions

For a fixed, tested regex, status 2 is unlikely. Check it whenever a pattern is generated, configured, or otherwise variable.
