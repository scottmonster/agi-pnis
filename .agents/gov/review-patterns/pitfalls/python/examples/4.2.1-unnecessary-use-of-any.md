# Unnecessary use of `Any`

## 1. Catalog record

- **Catalog identifier:** 4.2.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Use `Any` deliberately when type checking truly must be bypassed. Prefer `object`, protocols, unions, generics, or `unknown`-style narrowing patterns when operations should remain checked.

## 2. Example

### 2.1 Scenario

A helper receives a value from a heterogeneous data source and handles only text values.

### 2.2 Preferred form

```python
def normalized_label(value: object) -> str:
    if not isinstance(value, str):
        raise TypeError("label must be text")
    return value.strip().lower()


label = normalized_label("  Ready ")
```

### 2.3 Hazardous form

```python
from typing import Any


def normalized_label(value: Any) -> str:
    return value.strip().lower()


label = normalized_label(42)
```

### 2.4 Why this difference matters

`Any` permits every operation at type-check time, so an invalid `.strip()` call can reach production unchecked.

## 3. Boundaries and distinctions

`Any` can be necessary at untyped integration boundaries, but it should be narrowed or wrapped promptly rather than propagated through application logic.
