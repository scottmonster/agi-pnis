# Do not use variance annotations as a way to force structural variance

## 1. Catalog record

- **Catalog identifier:** 10.11.1
- **Impact:** low
- **Consensus:** high
- **Definition:** Normally let TypeScript infer variance; add `in`/`out` annotations only for accurately understood recursive types, diagnostics, or measured performance cases.

## 2. Example

### 2.1 Scenario

A cache reads and replaces values of one generic type.

### 2.2 Preferred form

```typescript
interface Cache<Value> {
  read(): Value;
  write: (value: Value) => void;
}

function replaceFrom<Value>(target: Cache<Value>, source: Cache<Value>): void {
  target.write(source.read());
}
```

### 2.3 Hazardous form

```typescript
// @ts-expect-error Value is consumed by write, so this cannot be declared `out`.
interface Cache<out Value> {
  read(): Value;
  write: (value: Value) => void;
}

// The `out` annotation conflicts with Value being consumed by write.
// It does not force Cache<Value> to become a safely covariant type.
```

### 2.4 Why this difference matters

Variance annotations describe a type parameter's actual usage and can help TypeScript check certain complex type relationships. They do not override structural assignability, and an inaccurate annotation creates an error or misleading maintenance signal.

## 3. Boundaries and distinctions

Let TypeScript infer variance for ordinary APIs. Add an accurate annotation only after understanding a recursive type's variance, diagnosing a relevant error, or measuring a performance benefit.
