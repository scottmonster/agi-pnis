# Excessive generated documentation for trivial internals

## 1. Catalog record

- **Catalog identifier:** 12.6
- **Evidence:** se
- **Definition:** Adds verbose reference material for obvious private details, obscuring the small amount of guidance readers need.

## 2. Scenario

### 2.1 Context

A change generates pages of prose for every private field in a small internal data class, while the only non-obvious behavior is one lifecycle invariant.

### 2.2 Safer approach

Document the lifecycle invariant and other decisions readers need to use or maintain the component, while leaving obvious private implementation details in the code.

### 2.3 Failure mode

Generate lengthy reference text for every getter, field, and trivial helper merely because tooling can produce it.

### 2.4 Why this difference matters

The operationally useful guidance becomes difficult to find and the generated material creates unnecessary maintenance surface.

## 3. Boundaries and distinctions

Detailed documentation remains appropriate for complex or externally used interfaces. The problem is verbosity for obvious private internals, not documentation itself.
