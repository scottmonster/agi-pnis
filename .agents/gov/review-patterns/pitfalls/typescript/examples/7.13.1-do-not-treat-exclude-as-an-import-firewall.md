# Do not treat `exclude` as an import firewall

## 1. Catalog record

- **Catalog identifier:** 7.13.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Remember that `exclude` only changes what `include` discovers; imported or explicitly referenced files can still become part of the program.

## 2. Example

### 2.1 Scenario

An application intends to compile only `src`, while one source file imports a helper from an excluded `scripts` directory.

### 2.2 Preferred form

```typescript
// src/report.ts
import { makeManifest } from './lib/make-manifest.js';

export function report(): string {
  return makeManifest('production');
}

// tsconfig.json
// { "include": ["src/**/*.ts"], "exclude": ["scripts"] }

// scripts/generate.ts may import src/lib/make-manifest.ts, but application
// source does not import scripts. Give scripts a separate tsconfig if needed.
// src/lib/make-manifest.ts
export function makeManifest(environment: string): string {
  return `manifest:${environment}`;
}
```

### 2.3 Hazardous form

```typescript
// src/report.ts
import { makeManifest } from '../scripts/make-manifest.js';

export const report = () => makeManifest('production');

// tsconfig.json
// { "include": ["src/**/*.ts"], "exclude": ["scripts"] }

// The import causes scripts/make-manifest.ts to enter the TypeScript program.
```

### 2.4 Why this difference matters

`exclude` filters files found through `include`; it does not prohibit module resolution. Once `src/report.ts` imports the helper, TypeScript follows that import and may typecheck or emit the excluded file. This can pull in unwanted environment assumptions, declarations, or generated-code dependencies.

## 3. Boundaries and distinctions

Use project boundaries, package boundaries, or lint rules when code must not depend on a directory. `files` and `include` determine program roots, but they also are not import firewalls. JavaScript bundlers may have separate inclusion rules, so verify both the TypeScript program and the production build.
