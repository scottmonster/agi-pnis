# Distinguish absent optional properties from explicit `undefined`

## 1. Catalog record

- **Catalog identifier:** 6.1.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Enable `exactOptionalPropertyTypes` when property presence itself has meaning, rather than automatically treating `foo?: T` as permitting `foo: undefined`.

## 2. Example

### 2.1 Scenario

A patch API treats an omitted field differently from a field supplied with a value.

### 2.2 Preferred form

```typescript
// `exactOptionalPropertyTypes: true`
type UserPatch = { displayName?: string };

function clearName(): UserPatch {
  return {}; // Absence means leave the current name unchanged.
}
```

### 2.3 Hazardous form

```typescript
type UserPatch = { displayName?: string };

function clearName(): UserPatch {
  return { displayName: undefined }; // Presence may overwrite a stored value.
}
```

### 2.4 Why this difference matters

JavaScript operations such as `in`, spreading, defaults, and serialization can distinguish an absent property from a present property containing `undefined`.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
