# A clean race-detector run is not proof of race freedom

## 1. Catalog record

- **Catalog identifier:** 11.12.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Run `go test -race` and realistic race-enabled workloads, but continue reasoning about synchronization even when no race is reported.

## 2. Example

### 2.1 Scenario

An order processor updates a counter only on a rare timeout path that a small unit test does not execute.

### 2.2 Preferred form

```go
package example

import "sync"

type counter struct {
	mu sync.Mutex
	n  int
}

func (c *counter) add() {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.n++
}
```

### 2.3 Hazardous form

```go
package example

type counter struct{ n int }

func (c *counter) add() {
	c.n++ // a test that misses concurrent calls reports no race
}
```

### 2.4 Why this difference matters

The race detector reports races that execute during the observed run. A clean run does not establish a synchronization relationship for unexercised interleavings.

## 3. Boundaries and distinctions

Run race-enabled unit, integration, and realistic workload tests whenever possible. Their diagnostic value is high, but correctness still requires deliberate synchronization design.
