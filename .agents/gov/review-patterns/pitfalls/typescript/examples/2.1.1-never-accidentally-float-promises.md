# Never accidentally float Promises

## 1. Catalog record

- **Catalog identifier:** 2.1.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Await, return, aggregate, or explicitly handle every Promise rather than letting it become an unused expression.

## 2. Example

### 2.1 Scenario

A request handler must persist an order before reporting success.

### 2.2 Preferred form

```typescript
async function saveOrder(): Promise<void> {
  await Promise.resolve(); // Represents a database write.
}

async function handle(): Promise<void> {
  await saveOrder();
  console.log('Order saved');
}
```

### 2.3 Hazardous form

```typescript
async function saveOrder(): Promise<void> {
  await Promise.resolve(); // Represents a database write.
}

function handle(): void {
  saveOrder(); // The rejection and completion are both ignored.
  console.log('Order saved');
}
```

### 2.4 Why this difference matters

Floating Promises cause lost errors, incorrect sequencing, and work that callers assume has completed when it has not.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
