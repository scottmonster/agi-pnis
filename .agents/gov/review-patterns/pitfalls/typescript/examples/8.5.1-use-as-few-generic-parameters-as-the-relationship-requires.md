# Use as few generic parameters as the relationship requires

## 1. Catalog record

- **Catalog identifier:** 8.5.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Remove type parameters that do not meaningfully relate two or more positions or otherwise contribute information.

## 2. Example

### 2.1 Scenario

A formatter always returns a generic status label, so no type relationship needs to be preserved.

### 2.2 Preferred form

```typescript
function statusLabel(status: string): string {
  return `status:${status}`;
}

console.log(statusLabel('published'));
```

### 2.3 Hazardous form

```typescript
function statusLabel<T extends string>(status: T): string {
  return `status:${status}`;
}

console.log(statusLabel<'published'>('published')); // T contributes nothing to the result
```

### 2.4 Why this difference matters

Unnecessary type parameters complicate inference and can make APIs appear more type-safe or flexible than they really are.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
