# Do not return, throw, break, or continue from finally

## 1. Catalog record

- **Catalog identifier:** 1.1.16
- **Impact:** high
- **Consensus:** high
- **Definition:** Avoid control-flow statements inside `finally` that override an earlier return, throw, break, or continue. Use `finally` for cleanup without replacing the pending completion.

## 2. Example

### 2.1 Scenario

A transaction helper must release a lock while preserving an error from the transaction.

### 2.2 Preferred form

```javascript
function completeTransaction(lock) {
  try {
    throw new Error("database rejected the update");
  } finally {
    lock.release();
  }
}

const lock = { release() { console.log("released"); } };
completeTransaction(lock);
```

### 2.3 Hazardous form

```javascript
function completeTransaction(lock) {
  try {
    throw new Error("database rejected the update");
  } finally {
    lock.release();
    return "completed";
  }
}

const lock = { release() { console.log("released"); } };
console.log(completeTransaction(lock));
```

### 2.4 Why this difference matters

The `return` in `finally` suppresses the transaction error, making the failed update appear successful.

## 3. Boundaries and distinctions

Use `finally` for cleanup that must run regardless of outcome. Replacing a pending completion should be an exceptional, explicit design decision.
