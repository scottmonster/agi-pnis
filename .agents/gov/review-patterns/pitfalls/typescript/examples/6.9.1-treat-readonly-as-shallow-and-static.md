# Treat `readonly` as shallow and static

## 1. Catalog record

- **Catalog identifier:** 6.9.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Do not interpret TypeScript `readonly` as deep runtime immutability.

## 2. Example

### 2.1 Scenario

A project summary must not be able to change any part of the project it reads.

### 2.2 Preferred form

```typescript
type ProjectView = {
  readonly name: string;
  readonly tags: readonly string[];
};

function summarize(project: ProjectView): string {
  return `${project.name}: ${project.tags.join(', ')}`;
}

console.log(summarize({ name: 'docs', tags: ['guide'] }));
```

### 2.3 Hazardous form

```typescript
type ProjectView = { readonly name: string; readonly tags: string[] };

function summarize(project: ProjectView): string {
  project.tags.push('reviewed');
  return `${project.name}: ${project.tags.join(', ')}`;
}

console.log(summarize({ name: 'docs', tags: ['guide'] }));
// `readonly` protects only the property reference, not the nested array.
```

### 2.4 Why this difference matters

Nested values may remain mutable, and aliases with mutable types can still modify the same runtime object.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
