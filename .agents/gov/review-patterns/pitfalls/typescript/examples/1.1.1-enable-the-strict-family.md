# Enable the `strict` family

## 1. Catalog record

- **Catalog identifier:** 1.1.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Use `strict: true` as the normal baseline rather than selectively opting into type safety after problems appear.

## 2. Example

### 2.1 Scenario

A service reads optional profile data supplied by another module.

### 2.2 Preferred form

```typescript
// tsconfig.json: { "compilerOptions": { "strict": true } }
type Profile = { nickname?: string };

export function greeting(profile: Profile): string {
  return `Hello, ${profile.nickname ?? 'guest'}`;
}
```

### 2.3 Hazardous form

```typescript
// tsconfig.json: { "compilerOptions": { "strict": false } }
// `profile` becomes implicit `any`, so misspellings pass unchecked.
export function greeting(profile) {
  return `Hello, ${profile.nicknmae.toUpperCase()}`;
}
```

### 2.4 Why this difference matters

It enables the core strictness checks that eliminate large classes of unsound inference, nullability, function compatibility, initialization, and other errors.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
