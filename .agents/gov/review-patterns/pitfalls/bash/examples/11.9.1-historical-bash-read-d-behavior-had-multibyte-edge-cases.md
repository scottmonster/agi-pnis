# Historical Bash `read -d` behavior had multibyte edge cases

## 1. Catalog record

- **Catalog identifier:** 11.9.1
- **Impact:** low
- **Consensus:** low
- **Definition:** Some Bash 5.0 through pre-release 5.3 versions had a multibyte-locale issue involving `read -d` delimiter handling that was corrected in final Bash 5.3. Treat reports involving those versions as version-specific rather than assuming current Bash shares the bug.

## 2. Example

### 2.1 Scenario

A tool processes UTF-8 records separated by a custom delimiter and supports a documented set of Bash versions.

### 2.2 Preferred form

```bash
#!/usr/bin/env bash

if (( BASH_VERSINFO[0] < 5 || (BASH_VERSINFO[0] == 5 && BASH_VERSINFO[1] < 3) )); then
  echo 'Bash 5.3 or later is required for this multibyte read -d workflow.' >&2
  exit 1
fi

input=$'café|naïve|'
while IFS= read -r -d '|' record; do
  echo "record: $record"
done <<<"$input"
```

### 2.3 Hazardous form

```bash
#!/usr/bin/env bash

input=$'café|naïve|'
while IFS= read -r -d '|' record; do
  echo "record: $record"
done <<<"$input"
```

### 2.4 Why this difference matters

On affected historical Bash versions in multibyte locales, `read -d` could handle delimiters incorrectly, so unqualified compatibility claims can produce corrupted or unexpectedly split records.

## 3. Boundaries and distinctions

This is a version-specific historical issue, corrected in final Bash 5.3. Current Bash should not be treated as affected solely because older reports describe the behavior.
