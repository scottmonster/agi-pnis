# `eval()` and `exec()` on untrusted input

## 1. Catalog record

- **Catalog identifier:** 2.2.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Never pass untrusted strings or code objects to `eval()` or `exec()`. Prefer parsing, explicit dispatch, or purpose-specific data formats.

## 2. Example

### 2.1 Scenario

A reporting endpoint accepts a requested aggregate operation.

### 2.2 Preferred form

```python
def aggregate(operation: str, values: list[int]) -> int:
    operations = {"sum": sum, "maximum": max}
    try:
        return operations[operation](values)
    except KeyError as error:
        raise ValueError("unsupported operation") from error


print(aggregate("sum", [2, 3, 5]))
```

### 2.3 Hazardous form

```python
def aggregate(expression: str, values: list[int]) -> object:
    return eval(expression, {"values": values})


print(aggregate("sum(values)", [2, 3, 5]))
```

### 2.4 Why this difference matters

An attacker can supply an expression that accesses builtins or performs actions beyond the intended aggregate operation.

## 3. Boundaries and distinctions

Dynamic execution can be appropriate for fully trusted developer-controlled code, but input from users, files, or network peers needs parsing or constrained dispatch.
