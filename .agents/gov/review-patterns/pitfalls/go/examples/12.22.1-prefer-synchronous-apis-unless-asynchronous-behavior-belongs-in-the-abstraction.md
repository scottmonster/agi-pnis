# Prefer synchronous APIs unless asynchronous behavior belongs in the abstraction

## 1. Catalog record

- **Catalog identifier:** 12.22.1
- **Impact:** medium
- **Consensus:** medium
- **Definition:** Prefer functions that finish their work before returning when callers can trivially add concurrency themselves.

## 2. Example

### 2.1 Scenario

A service records an audit event and must let the HTTP handler decide whether to wait, retry, or run work concurrently.

### 2.2 Preferred form

```go
package audit

import "context"

type Event struct {
	Action string
}

type Sink interface {
	Save(context.Context, Event) error
}

type Service struct {
	sink Sink
}

func (s Service) Record(ctx context.Context, event Event) error {
	return s.sink.Save(ctx, event)
}
```

### 2.3 Hazardous form

```go
package audit

import "context"

type Event struct {
	Action string
}

type Sink interface {
	Save(context.Context, Event) error
}

type Service struct {
	sink Sink
}

func (s Service) Record(event Event) {
	go func() {
		_ = s.sink.Save(context.Background(), event)
	}()
}
```

### 2.4 Why this difference matters

The asynchronous method returns before the caller can learn whether the event was saved, and it discards cancellation and errors. A synchronous contract lets each caller add a goroutine, timeout, queue, or retry policy that fits its request.

## 3. Boundaries and distinctions

Asynchronous behavior is appropriate when queuing, scheduling, or eventual delivery is the API's explicit purpose. Such APIs should expose ownership, cancellation, completion, backpressure, and error reporting rather than merely starting a hidden goroutine.
