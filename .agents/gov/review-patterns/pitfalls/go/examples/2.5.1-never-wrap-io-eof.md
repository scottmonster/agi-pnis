# Never wrap `io.EOF`

## 1. Catalog record

- **Catalog identifier:** 2.5.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Readers that signal end of input should return `io.EOF` itself rather than a wrapped form.

## 2. Example

### 2.1 Scenario

A custom reader exposes a fixed byte payload to code that ends its loop by comparing the returned error with `io.EOF`.

### 2.2 Preferred form

```go
package example

import "io"

type payloadReader struct{ data []byte }

func (r *payloadReader) Read(p []byte) (int, error) {
	if len(r.data) == 0 {
		return 0, io.EOF
	}
	n := copy(p, r.data)
	r.data = r.data[n:]
	return n, nil
}
```

### 2.3 Hazardous form

```go
package example

import (
	"fmt"
	"io"
)

type payloadReader struct{ data []byte }

func (r *payloadReader) Read(p []byte) (int, error) {
	if len(r.data) == 0 {
		return 0, fmt.Errorf("payload complete: %w", io.EOF)
	}
	n := copy(p, r.data)
	r.data = r.data[n:]
	return n, nil
}
```

### 2.4 Why this difference matters

`io.Reader` consumers are allowed to test `err == io.EOF`. Wrapping EOF changes that identity and can make a normal end-of-input condition look like an unexpected failure.

## 3. Boundaries and distinctions

Adding context to other operational errors can be appropriate when the API permits wrapping. This rule is specific to EOF returned by reader implementations.
