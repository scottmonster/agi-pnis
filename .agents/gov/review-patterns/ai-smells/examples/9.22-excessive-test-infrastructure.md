# Excessive test infrastructure

## 1. Catalog record

- **Catalog identifier:** 9.22
- **Evidence:** se
- **Definition:** Builds factories, DSLs, and helper frameworks for a handful of straightforward tests.

## 2. Scenario

### 2.1 Context

A new validation rule needs three small unit tests with plainly readable input objects.

### 2.2 Safer approach

Construct the small objects directly in each test, extracting only a simple shared helper if repeated setup becomes stable and noisy.

### 2.3 Failure mode

Create a fluent test-data DSL, generic factory hierarchy, and custom matcher package before writing the three tests.

### 2.4 Why this difference matters

The tests gain extra indirection and maintenance burden while the behavior under test becomes harder to read.

## 3. Boundaries and distinctions

Reusable test infrastructure is justified when repeated setup is genuinely complex and stable across many tests, not merely to make a small initial suite look extensible.
