# Do not rely on newly inserted map entries appearing during range

## 1. Catalog record

- **Catalog identifier:** 7.8.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** If a map is modified during iteration, do not rely on new entries being visited. Deletions of not-yet-reached entries prevent those entries from being produced.

## 2. Example

### 2.1 Scenario

A graph traversal expands discovered work items stored in a map.

### 2.2 Preferred form

```go
package graph

func expand(initial []string) []string {
	queue := append([]string(nil), initial...)
	visited := make([]string, 0, len(queue))
	for len(queue) > 0 {
		name := queue[0]
		queue = queue[1:]
		visited = append(visited, name)
		if name == "root" { queue = append(queue, "child") }
	}
	return visited
}
```

### 2.3 Hazardous form

```go
package graph

func expand(todo map[string]bool) {
	for name := range todo {
		todo[name+".next"] = true // This new key might not be ranged over.
	}
}
```

### 2.4 Why this difference matters

The language permits inserted keys to be skipped, so range is not a reliable work queue.

## 3. Boundaries and distinctions

Deleting a key not yet reached prevents it from being produced. Map mutation is permitted, but iteration results must not depend on it.
