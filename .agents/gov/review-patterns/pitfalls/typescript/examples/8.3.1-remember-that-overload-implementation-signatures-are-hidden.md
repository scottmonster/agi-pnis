# Remember that overload implementation signatures are hidden

## 1. Catalog record

- **Catalog identifier:** 8.3.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Do not assume callers can use a parameter combination merely because the implementation signature accepts it; expose every supported call shape through overload signatures.

## 2. Example

### 2.1 Scenario

A decoder supports both text and binary payloads, so each supported form must appear in its public overloads.

### 2.2 Preferred form

```typescript
function decode(payload: string): string;
function decode(payload: Uint8Array): string;
function decode(payload: string | Uint8Array): string {
  return typeof payload === 'string' ? payload : new TextDecoder().decode(payload);
}

console.log(decode(new Uint8Array([79, 75])));
```

### 2.3 Hazardous form

```typescript
function decode(payload: string): string;
function decode(payload: string | Uint8Array): string {
  return typeof payload === 'string' ? payload : new TextDecoder().decode(payload);
}

decode(new Uint8Array([79, 75])); // Error: the binary call shape is not public
```

### 2.4 Why this difference matters

TypeScript resolves calls against the public overload list, not the implementation signature.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
