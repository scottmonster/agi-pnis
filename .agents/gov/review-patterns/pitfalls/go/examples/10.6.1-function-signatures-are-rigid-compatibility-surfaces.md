# Function signatures are rigid compatibility surfaces

## 1. Catalog record

- **Catalog identifier:** 10.6.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Prefer adding another function or method over changing an existing exported function signature, even when a change such as adding a variadic parameter appears source-compatible at call sites.

## 2. Example

### 2.1 Scenario

A package needs configurable retry behavior after users have already assigned its exported function to callbacks with the original signature.

### 2.2 Preferred form

```go
package example

type Options struct{ Retries int }

func Fetch(url string) error {
	return FetchWithOptions(url, Options{})
}

func FetchWithOptions(url string, options Options) error {
	return nil
}

var callback func(string) error = Fetch
```

### 2.3 Hazardous form

```go
package example

type Options struct{ Retries int }

func Fetch(url string, options ...Options) error { return nil }

// var callback func(string) error = Fetch // no longer compiles after the signature change
```

### 2.4 Why this difference matters

Adding a variadic argument may preserve direct calls such as `Fetch(url)`, but it changes the function type. Existing callbacks, interfaces, and method expressions relying on the old signature break.

## 3. Boundaries and distinctions

Changing an unexported function is usually safe after updating its callers. For a public API, add a new name or a new method unless a deliberate breaking release is intended.
