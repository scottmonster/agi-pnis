# Follow cgo pointer retention rules

## 1. Catalog record

- **Catalog identifier:** 4.11.1
- **Impact:** high
- **Consensus:** high
- **Definition:** C code must not retain ordinary Go pointers after a cgo call unless the referenced memory is pinned under the documented rules. Use `runtime.Pinner` or `runtime/cgo.Handle` where appropriate.

## 2. Example

### 2.1 Scenario

A C callback registry needs a stable value that Go can look up after the registration call returns.

### 2.2 Preferred form

```go
package example

/*
#include <stdint.h>
static uintptr_t saved;
static void remember(uintptr_t value) { saved = value; }
*/
import "C"

import "runtime/cgo"

type callbackState struct {
	name string
}

func register(state *callbackState) cgo.Handle {
	handle := cgo.NewHandle(state)
	C.remember(C.uintptr_t(handle))
	return handle
}
```

### 2.3 Hazardous form

```go
package example

/*
static void *saved;
static void remember(void *value) { saved = value; }
*/
import "C"

import "unsafe"

type callbackState struct {
	name string
}

func register(state *callbackState) {
	C.remember(unsafe.Pointer(state))
}
```

### 2.4 Why this difference matters

The handle is an integer token that C can retain without retaining a Go pointer. The hazardous form gives C a pointer into Go-managed memory after the call returns, violating cgo's lifetime rules and risking invalid memory access.

## 3. Boundaries and distinctions

Delete the returned `cgo.Handle` after C no longer needs it. `runtime.Pinner` can be appropriate when C must retain eligible Go memory temporarily, but its lifetime and pointer contents must satisfy the documented cgo rules.
