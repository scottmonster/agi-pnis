# Narrow instead of asserting

## 1. Catalog record

- **Catalog identifier:** 1.6.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Prefer control-flow narrowing, validation, type guards, or checked construction over `as T`, especially assertions that narrow to a more specific type.

## 2. Example

### 2.1 Scenario

A function receives an untrusted value that may represent an invoice.

### 2.2 Preferred form

```typescript
type Invoice = { total: number };

function invoiceTotal(value: unknown): number {
  if (
    typeof value === 'object' && value !== null &&
    'total' in value && typeof value.total === 'number'
  ) {
    return value.total;
  }
  throw new Error('Invalid invoice');
}
```

### 2.3 Hazardous form

```typescript
type Invoice = { total: number };

function invoiceTotal(value: unknown): number {
  return (value as Invoice).total; // The assertion proves nothing at runtime.
}
```

### 2.4 Why this difference matters

Assertions tell the compiler to accept an assumption without proving it and do not change or validate the runtime value.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
