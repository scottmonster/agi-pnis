# Startup/import-time side effects

## 1. Catalog record

- **Catalog identifier:** 12.12
- **Evidence:** se
- **Definition:** Performs I/O, mutation, registration, network access, or other work merely by loading a module or starting a process.

## 2. Scenario

### 2.1 Context

Importing a Python module immediately connects to a production database and creates a missing table before any application entry point runs.

### 2.2 Safer approach

Keep import behavior declarative and invoke database setup from an explicit startup command with clear configuration, error handling, and test control.

### 2.3 Failure mode

Place the database connection and schema mutation at module scope so all consumers receive setup automatically.

### 2.4 Why this difference matters

Tests, tooling, and unrelated imports trigger network access and mutation unexpectedly, making failures and lifecycle behavior hard to control.

## 3. Boundaries and distinctions

Some explicit startup initialization is necessary. This failure is work caused merely by module loading or process start without an intentional, controllable boundary.
