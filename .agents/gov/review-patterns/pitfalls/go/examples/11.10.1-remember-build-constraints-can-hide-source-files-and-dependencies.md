# Remember build constraints can hide source files and dependencies

## 1. Catalog record

- **Catalog identifier:** 11.10.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Test relevant GOOS, GOARCH, and build-tag combinations rather than assuming the source set used on one development machine represents every build.

## 2. Example

### 2.1 Scenario

A service has Unix-only file-descriptor code. A developer on Linux must still confirm that the Windows configuration builds.

### 2.2 Preferred form

```go
package example

import "os/exec"

func verifyWindowsBuild() error {
	cmd := exec.Command("go", "test", "./...")
	cmd.Env = append(cmd.Environ(), "GOOS=windows", "GOARCH=amd64")
	return cmd.Run()
}
```

### 2.3 Hazardous form

```go
//go:build unix

package example

import "golang.org/x/sys/unix"

func closeFD(fd int) error {
	return unix.Close(fd) // invisible in a Windows build
}
```

### 2.4 Why this difference matters

Filename suffixes and `//go:build` expressions change which files, declarations, and dependencies exist. A successful local build can leave another supported configuration broken.

## 3. Boundaries and distinctions

Test materially supported operating systems, architectures, and tags, not every theoretical combination. Cross-compilation may require additional integration tests when native behavior matters.
