# Do not copy a nonzero `strings.Builder`

## 1. Catalog record

- **Catalog identifier:** 12.14.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Pass a `strings.Builder` by pointer or keep it local rather than copying it after it has been used.

## 2. Example

### 2.1 Scenario

A renderer starts a response in one function and lets a helper append the final greeting. The helper must operate on the same builder rather than receive a copy of its current state.

### 2.2 Preferred form

```go
package example

import (
	"fmt"
	"strings"
)

func appendGreeting(dst *strings.Builder, name string) {
	fmt.Fprintf(dst, "Hello, %s!", name)
}

func greeting(name string) string {
	var builder strings.Builder
	builder.WriteString("Message: ")
	appendGreeting(&builder, name)
	return builder.String()
}
```

### 2.3 Hazardous form

```go
package example

import (
	"fmt"
	"strings"
)

func appendGreeting(dst strings.Builder, name string) {
	// Writing this copied nonzero builder panics at runtime.
	fmt.Fprintf(&dst, "Hello, %s!", name)
}

func greeting(name string) string {
	var builder strings.Builder
	builder.WriteString("Message: ")
	appendGreeting(builder, name)
	return builder.String()
}
```

### 2.4 Why this difference matters

`strings.Builder` detects copies after its first use and panics when a copied builder is written. Passing a pointer also makes it clear that the helper intentionally extends the caller's output.

## 3. Boundaries and distinctions

Copying a zero-value builder before either copy is used is not the same problem, but avoiding builder value parameters generally keeps ownership clear. A completed string returned by `String` is the appropriate value to pass onward.
