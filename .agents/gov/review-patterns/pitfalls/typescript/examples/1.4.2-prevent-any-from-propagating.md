# Prevent `any` from propagating

## 1. Catalog record

- **Catalog identifier:** 1.4.2
- **Impact:** high
- **Consensus:** high
- **Definition:** Use type-aware lint rules such as `no-unsafe-assignment`, `no-unsafe-argument`, `no-unsafe-call`, `no-unsafe-member-access`, and `no-unsafe-return` to contain unavoidable `any` values.

## 2. Example

### 2.1 Scenario

A legacy JavaScript library returns `any`.

### 2.2 Preferred form

```typescript
declare function legacyReadSetting(): any;

function requireString(value: unknown): string {
  if (typeof value !== 'string') throw new Error('Expected a string');
  return value;
}

const raw: unknown = legacyReadSetting();
const theme = requireString(raw);
```

### 2.3 Hazardous form

```typescript
declare function legacyReadSetting(): any;

type Theme = { name: string };

function loadTheme(): Theme {
  return legacyReadSetting(); // `any` crosses an otherwise typed boundary.
}
```

### 2.4 Why this difference matters

A single `any` can silently infect otherwise strongly typed code through assignments, calls, returns, and property access.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
