# Synchronize concurrent map access

## 1. Catalog record

- **Catalog identifier:** 1.13.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Do not concurrently modify an ordinary map while another goroutine reads or modifies it. Protect it with synchronization or use an appropriate specialized structure.

## 2. Example

### 2.1 Scenario

Workers record completed jobs in a shared lookup table.

### 2.2 Preferred form

```go
package main

import "sync"

type completed struct {
	mu   sync.RWMutex
	jobs map[string]bool
}

func newCompleted() *completed {
	return &completed{jobs: make(map[string]bool)}
}

func (c *completed) mark(id string) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.jobs[id] = true
}

func (c *completed) has(id string) bool {
	c.mu.RLock()
	defer c.mu.RUnlock()
	return c.jobs[id]
}
```

### 2.3 Hazardous form

```go
package main

type completed struct{ jobs map[string]bool }

func newCompleted() *completed {
	return &completed{jobs: make(map[string]bool)}
}

func (c *completed) mark(id string) { c.jobs[id] = true }
func (c *completed) has(id string) bool { return c.jobs[id] }
```

### 2.4 Why this difference matters

Concurrent reads and writes to the hazardous map can race and may trigger a runtime fatal error. The lock protects the map and the associated invariant.

## 3. Boundaries and distinctions

`sync.Map` can suit specialized read-mostly or independently keyed workloads. A regular map with a mutex is usually clearer when operations span multiple keys.
