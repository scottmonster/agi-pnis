# Prefer useful got/want test failures

## 1. Catalog record

- **Catalog identifier:** 13.13.2
- **Impact:** low
- **Consensus:** high
- **Definition:** Report the input, actual value, and expected value when a comparison fails.

## 2. Example

### 2.1 Scenario

A table-driven parser test needs to expose enough context to diagnose a failing case.

### 2.2 Preferred form

```go
package example

import "testing"

func length(s string) int { return len(s) }

func TestLength(t *testing.T) {
	input, want := "gopher", 6
	if got := length(input); got != want {
		t.Fatalf("length(%q): got %d, want %d", input, got, want)
	}
}
```

### 2.3 Hazardous form

```go
package example

import "testing"

func length(s string) int { return len(s) }

func TestLength(t *testing.T) {
	if length("gopher") != 6 {
		t.Fatal("length failed")
	}
}
```

### 2.4 Why this difference matters

The preferred failure identifies the input and both values, which makes a table failure actionable. The vague message forces the reader to reconstruct the comparison from the test.

## 3. Boundaries and distinctions

Keep diagnostics proportionate to the test. For complex values, use a focused diff or summarize the relevant fields rather than dumping unrelated data.
