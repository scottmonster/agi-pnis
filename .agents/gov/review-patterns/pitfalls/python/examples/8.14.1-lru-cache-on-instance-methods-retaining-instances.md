# `lru_cache` on instance methods retaining instances

## 1. Catalog record

- **Catalog identifier:** 8.14.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Be cautious caching instance methods on large or short-lived object populations. Bound method calls include `self` in the cache key.

## 2. Example

### 2.1 Scenario

Short-lived request objects calculate a value that is only useful during one request.

### 2.2 Preferred form

```python
class Request:
    def __init__(self, customer_id: int) -> None:
        self.customer_id = customer_id

    def label(self) -> str:
        return f"customer-{self.customer_id}"

assert Request(7).label() == "customer-7"
```

### 2.3 Hazardous form

```python
from functools import lru_cache

class Request:
    def __init__(self, customer_id: int) -> None:
        self.customer_id = customer_id

    @lru_cache
    def label(self) -> str:
        return f"customer-{self.customer_id}"
```

### 2.4 Why this difference matters

The method cache key includes `self`, so cached calls can keep many otherwise short-lived instances reachable.

## 3. Boundaries and distinctions

A bounded cache can be useful for long-lived instances with a deliberate cache lifetime and `cache_clear()` policy.
