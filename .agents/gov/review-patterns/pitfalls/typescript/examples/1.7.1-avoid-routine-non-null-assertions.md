# Avoid routine non-null assertions

## 1. Catalog record

- **Catalog identifier:** 1.7.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Prefer proving that a value is non-nullish rather than silencing the checker with `value!`.

## 2. Example

### 2.1 Scenario

A lookup may not find the requested user.

### 2.2 Preferred form

```typescript
type User = { email: string };
const users = new Map<string, User>();

function recipientFor(id: string): string {
  const user = users.get(id);
  if (user === undefined) throw new Error(`Unknown user: ${id}`);
  return user.email;
}
```

### 2.3 Hazardous form

```typescript
type User = { email: string };
const users = new Map<string, User>();

function recipientFor(id: string): string {
  return users.get(id)!.email;
}
```

### 2.4 Why this difference matters

The non-null assertion is erased at runtime and can convert a legitimate `undefined` or `null` path into an unchecked runtime failure.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
