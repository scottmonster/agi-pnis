# Prefer interface extension over large object intersections when composition is equivalent

## 1. Catalog record

- **Catalog identifier:** 11.1.1
- **Impact:** low
- **Consensus:** high
- **Definition:** In heavily composed object hierarchies, prefer `interface Foo extends A, B` over repeatedly constructing `A & B & {...}` when either representation meets the semantic need.

## 2. Example

### 2.1 Scenario

A telemetry event combines common properties and has several event-specific fields.

### 2.2 Preferred form

```typescript
interface Timestamped {
  occurredAt: Date;
}

interface Traceable {
  traceId: string;
}

interface PurchaseEvent extends Timestamped, Traceable {
  orderId: string;
  totalCents: number;
}

function recordPurchase(event: PurchaseEvent): void {
  console.log(event.traceId, event.orderId, event.totalCents);
}
```

### 2.3 Hazardous form

```typescript
type Timestamped = { occurredAt: Date };
type Traceable = { traceId: string };

type PurchaseEvent = Timestamped & Traceable & {
  orderId: string;
  totalCents: number;
};

type RefundEvent = Timestamped & Traceable & {
  refundId: string;
  totalCents: number;
};

function recordPurchase(event: PurchaseEvent): void {
  console.log(event.traceId, event.orderId, event.totalCents);
}

function recordRefund(event: RefundEvent): void {
  console.log(event.traceId, event.refundId, event.totalCents);
}
```

### 2.4 Why this difference matters

Interfaces flatten relationships, report property conflicts more directly, and are generally easier for the checker to cache and compare.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
