# “Future-proof” indirection

## 1. Catalog record

- **Catalog identifier:** 3.30
- **Evidence:** se
- **Definition:** Adds layers whose only justification is that requirements might change.

## 2. Scenario

### 2.1 Context

A notifier has one supported delivery channel and one current caller.

### 2.2 Safer approach

Implement the direct notification path and evolve it when a concrete requirement arrives.

### 2.3 Failure mode

Add several forwarding layers and extension types only because the notifier might someday support other channels.

### 2.4 Why this difference matters

Speculative layers make the present code harder to understand while future requirements remain unknown.

## 3. Boundaries and distinctions

Designing for known, likely variation differs from indirection justified only by an unspecified possible future.
