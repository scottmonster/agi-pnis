# Unsynchronized shared SQLite connections

## 1. Catalog record

- **Catalog identifier:** 2.16.1
- **Impact:** high
- **Consensus:** high
- **Definition:** If SQLite's `check_same_thread=False` is used, serialize writes yourself rather than treating the connection as automatically safe for unrestricted concurrent access.

## 2. Example

### 2.1 Scenario

Two worker threads share a SQLite connection to append audit events.

### 2.2 Preferred form

```python
import sqlite3
import threading


connection = sqlite3.connect("audit.db", check_same_thread=False)
write_lock = threading.Lock()


def record_event(message: str) -> None:
    with write_lock:
        connection.execute("INSERT INTO audit_events(message) VALUES (?)", (message,))
        connection.commit()
```

### 2.3 Hazardous form

```python
import sqlite3


connection = sqlite3.connect("audit.db", check_same_thread=False)


def record_event(message: str) -> None:
    connection.execute("INSERT INTO audit_events(message) VALUES (?)", (message,))
    connection.commit()
```

### 2.4 Why this difference matters

Allowing cross-thread connection use does not make unrestricted concurrent writes safe. Serialize write operations to protect the connection and transaction behavior.

## 3. Boundaries and distinctions

Separate per-thread connections or a dedicated database worker can be preferable designs, depending on the workload and transaction model.
