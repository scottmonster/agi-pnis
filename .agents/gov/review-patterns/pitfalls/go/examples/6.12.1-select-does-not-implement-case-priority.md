# `select` does not implement case priority

## 1. Catalog record

- **Catalog identifier:** 6.12.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** When multiple communication cases are ready, `select` chooses among them pseudo-randomly rather than selecting the first case.

## 2. Example

### 2.1 Scenario

A worker should prefer shutdown over a queued job.

### 2.2 Preferred form

```go
package main

func next(stop <-chan struct{}, jobs <-chan string) (string, bool) {
	select {
	case <-stop:
		return "", false
	default:
	}
	select {
	case <-stop:
		return "", false
	case job := <-jobs:
		return job, true
	}
}
```

### 2.3 Hazardous form

```go
package main

func next(stop <-chan struct{}, jobs <-chan string) (string, bool) {
	select {
	case <-stop:
		return "", false
	case job := <-jobs:
		return job, true
	}
}
```

### 2.4 Why this difference matters

When both cases are ready, the hazardous select can choose the job although shutdown appears first.

## 3. Boundaries and distinctions

The preferred pattern is best effort because shutdown can arrive after its first check. Use stronger coordination if any in-flight job is unacceptable.
