# Prefer ES modules over TypeScript namespaces in modern code

## 1. Catalog record

- **Catalog identifier:** 7.17.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Use standard ES modules for normal application and library organization; reserve namespaces primarily for declaration or legacy scenarios where they are actually required.

## 2. Example

### 2.1 Scenario

A browser application shares geometry helpers across feature modules and needs explicit runtime dependencies.

### 2.2 Preferred form

```typescript
// geometry.ts
export function area(radius: number): number {
  return Math.PI * radius ** 2;
}

// dashboard.ts
import { area } from './geometry.js';

const label = `Area: ${area(2).toFixed(1)}`;
document.body.textContent = label;
```

### 2.3 Hazardous form

```typescript
// geometry.ts, a script with no import or export
namespace Geometry {
  export function area(radius: number): number {
    return Math.PI * radius ** 2;
  }
}

// dashboard.ts, a separate script
const label = `Area: ${Geometry.area(2).toFixed(1)}`;
document.body.textContent = label;

// Both files must be loaded in the right order, and another script can merge
// into the global Geometry namespace.
```

### 2.4 Why this difference matters

ES modules give each file a private scope and declare its dependencies in syntax that browsers, Node, bundlers, and test runners understand. TypeScript namespaces usually compile to global-object or IIFE-style code, making load order and accidental declaration merging part of the program's runtime contract.

## 3. Boundaries and distinctions

Namespaces remain useful for describing an intentional global API in `.d.ts` files, augmenting a legacy global library, or maintaining an existing non-module script application. They are not inherently invalid, but new application and package code should use ES modules unless it must participate in one of those global contracts.
