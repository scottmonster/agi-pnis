# Using `IntEnum` when integer interoperability is unnecessary

## 1. Catalog record

- **Catalog identifier:** 14.3.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Prefer `Enum` or `Flag` for new APIs unless compatibility with integer APIs is actually required.

## 2. Example

### 2.1 Scenario

A new order-status API needs distinct symbolic states but does not communicate with an integer-only external protocol.

### 2.2 Preferred form

```python
from enum import Enum


class Status(Enum):
    PENDING = 1
    PAID = 2


def is_paid(status: Status) -> bool:
    return status is Status.PAID


print(is_paid(Status.PAID))
```

### 2.3 Hazardous form

```python
from enum import IntEnum


class Status(IntEnum):
    PENDING = 1
    PAID = 2


def is_paid(status: Status) -> bool:
    return status == 2


print(is_paid(Status.PAID))
```

### 2.4 Why this difference matters

`IntEnum` members behave like integers, which makes accidental comparisons and substitutions with raw integer values easier. The API loses some protection against mixing unrelated concepts.

## 3. Boundaries and distinctions

Use `IntEnum` when an integer-based protocol, C API, serialization format, or legacy interface actually requires it. Prefer regular `Enum` when values should remain distinct domain objects.
