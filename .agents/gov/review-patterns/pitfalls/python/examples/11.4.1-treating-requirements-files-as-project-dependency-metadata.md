# Treating requirements files as project dependency metadata

## 1. Catalog record

- **Catalog identifier:** 11.4.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Declare the dependencies needed by the distributable project in project metadata and use requirements-style files for describing particular environments or deployment sets.

## 2. Example

### 2.1 Scenario

A library needs to declare its runtime dependency while an application deployment pins a specific environment.

### 2.2 Preferred form

```python
# pyproject.toml
# [project]
# dependencies = ["httpx>=0.27"]

# requirements-prod.txt
# httpx==0.27.2

runtime_dependency = "httpx>=0.27"
print(runtime_dependency)
```

### 2.3 Hazardous form

```python
# requirements.txt
# httpx>=0.27

project_metadata_file = "requirements.txt"
print(project_metadata_file)
```

### 2.4 Why this difference matters

Installers and package consumers read distribution metadata, not an arbitrary requirements file, so a library can be installed without its needed dependency being declared.

## 3. Boundaries and distinctions

Requirements files are useful for application environments, test sets, and deployment constraints. They serve a different purpose from the dependency metadata of a distributable project.
