# Do not store contexts in structs by default

## 1. Catalog record

- **Catalog identifier:** 9.1.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Pass `context.Context` as the first parameter to operations that need it instead of putting it into a long-lived struct.

## 2. Example

### 2.1 Scenario

A repository instance serves many requests, each with its own cancellation and deadline.

### 2.2 Preferred form

```go
package example

import "context"

type Repository struct{}

func (Repository) Find(ctx context.Context, id string) error {
	return ctx.Err()
}
```

### 2.3 Hazardous form

```go
package example

import "context"

type Repository struct{ ctx context.Context }

func (r Repository) Find(id string) error {
	return r.ctx.Err() // Uses whichever request last configured the repository.
}
```

### 2.4 Why this difference matters

Passing context makes cancellation ownership visible and prevents a long-lived object from retaining an expired, unrelated request context.

## 3. Boundaries and distinctions

Some short-lived request objects may deliberately hold a context, but operation APIs should still accept it explicitly when they can be called in multiple request lifecycles.
