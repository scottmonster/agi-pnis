# Do not disable TLS verification with `InsecureSkipVerify`

## 1. Catalog record

- **Catalog identifier:** 4.1.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Leave certificate and hostname verification enabled unless you are implementing equivalent verification through the documented custom verification hooks.

## 2. Example

### 2.1 Scenario

A service calls its payments API over HTTPS and must authenticate the server it reaches.

### 2.2 Preferred form

```go
package example

import (
	"crypto/tls"
	"net/http"
)

func paymentsClient() *http.Client {
	return &http.Client{Transport: &http.Transport{
		TLSClientConfig: &tls.Config{MinVersion: tls.VersionTLS12},
	}}
}
```

### 2.3 Hazardous form

```go
package example

import (
	"crypto/tls"
	"net/http"
)

func paymentsClient() *http.Client {
	return &http.Client{Transport: &http.Transport{
		TLSClientConfig: &tls.Config{InsecureSkipVerify: true},
	}}
}
```

### 2.4 Why this difference matters

The preferred client rejects certificates and hostnames it cannot verify. Disabling verification allows an attacker able to intercept traffic to impersonate the API.

## 3. Boundaries and distinctions

Custom verification hooks are appropriate only when they implement an equivalent, reviewed verification policy. A private test client may use a controlled test certificate instead of weakening production verification.
