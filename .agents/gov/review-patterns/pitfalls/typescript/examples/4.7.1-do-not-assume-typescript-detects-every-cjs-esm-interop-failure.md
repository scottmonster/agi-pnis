# Do not assume TypeScript detects every CJS/ESM interop failure

## 1. Catalog record

- **Catalog identifier:** 4.7.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Test actual Node interop behavior, particularly `require()` of ESM and CommonJS named imports, rather than treating successful type checking as a complete runtime compatibility test.

## 2. Example

### 2.1 Scenario

A CommonJS consumer must load an ESM dependency under the Node version it supports.

### 2.2 Preferred form

```typescript
// cjs-consumer.cjs
async function loadFormatter(): Promise<(value: string) => string> {
  const module = await import('./formatter.mjs');
  return module.format;
}
```

### 2.3 Hazardous form

```typescript
// cjs-consumer.cjs
// TypeScript declarations can make this look valid, but older Node versions reject it.
const { format } = require('./formatter.mjs');
console.log(format('ok'));
```

### 2.4 Why this difference matters

TypeScript intentionally cannot detect some runtime cases, including certain top-level-await and synthetic-named-export situations.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
