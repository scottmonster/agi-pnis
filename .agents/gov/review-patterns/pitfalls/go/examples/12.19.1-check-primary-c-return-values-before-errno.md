# Check primary C return values before `errno`

## 1. Catalog record

- **Catalog identifier:** 12.19.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** When using cgo's two-result form that captures `errno`, determine whether the C call failed according to its documented return value before interpreting `errno`.

## 2. Example

### 2.1 Scenario

A cgo wrapper calls a C function whose documented success result is zero. The function leaves `errno` set from earlier work even when it succeeds.

### 2.2 Preferred form

```go
package native

/*
#include <errno.h>
static int refresh_cache(void) {
	errno = EINTR;
	return 0;
}
*/
import "C"

import "fmt"

func RefreshCache() error {
	result, errno := C.refresh_cache()
	if result != 0 {
		return fmt.Errorf("refresh cache: %w", errno)
	}
	return nil
}
```

### 2.3 Hazardous form

```go
package native

/*
#include <errno.h>
static int refresh_cache(void) {
	errno = EINTR;
	return 0;
}
*/
import "C"

import "fmt"

func RefreshCache() error {
	_, errno := C.refresh_cache()
	if errno != nil {
		return fmt.Errorf("refresh cache: %w", errno)
	}
	return nil
}
```

### 2.4 Why this difference matters

`errno` is meaningful only after the C API has indicated failure by its specified return value. Treating a non-nil captured errno as failure can report an error after a successful operation.

## 3. Boundaries and distinctions

Use the failure indicator documented for the particular C function, such as `NULL`, `-1`, or a positive error code. Some C APIs return errors directly and do not use `errno` at all.
