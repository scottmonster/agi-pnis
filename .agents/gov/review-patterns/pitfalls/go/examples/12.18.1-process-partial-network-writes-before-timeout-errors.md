# Process partial network writes before timeout errors

## 1. Catalog record

- **Catalog identifier:** 12.18.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** When an I/O method returns both `n > 0` and an error, account for the successfully transferred portion before handling the error.

## 2. Example

### 2.1 Scenario

A replication client writes a record to a `net.Conn` that can time out after the peer has accepted part of the record.

### 2.2 Preferred form

```go
package replication

import (
	"io"
	"net"
)

func writeRecord(conn net.Conn, record []byte) (int, error) {
	written := 0
	for written < len(record) {
		n, err := conn.Write(record[written:])
		written += n
		if err != nil {
			return written, err
		}
		if n == 0 {
			return written, io.ErrShortWrite
		}
	}
	return written, nil
}
```

### 2.3 Hazardous form

```go
package replication

import "net"

func writeRecord(conn net.Conn, record []byte) (int, error) {
	n, err := conn.Write(record)
	if err != nil {
		return 0, err // Discards bytes the peer may already have received.
	}
	return n, nil
}
```

### 2.4 Why this difference matters

Returning zero on a partial write loses the progress information needed to resume, account for, or safely retry the transfer. A retry that resends the whole record can duplicate data at the peer.

## 3. Boundaries and distinctions

Whether to retry depends on the protocol's framing and idempotency guarantees. The requirement to account for `n` applies even when the returned error is a timeout or another terminal failure.
