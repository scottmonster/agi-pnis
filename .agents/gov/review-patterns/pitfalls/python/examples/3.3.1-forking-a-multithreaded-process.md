# Forking a multithreaded process

## 1. Catalog record

- **Catalog identifier:** 3.3.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Avoid `os.fork()` from a multithreaded Python process and do not assume the historical `fork` multiprocessing behavior is safe.

## 2. Example

### 2.1 Scenario

A service with worker threads needs to launch an isolated child job. The child should start without inheriting thread-owned process state.

### 2.2 Preferred form

```python
import multiprocessing as mp
from threading import Thread


def child_job() -> None:
    print("child started")


def background_worker() -> None:
    print("worker started")


if __name__ == "__main__":
    mp.set_start_method("spawn")
    Thread(target=background_worker).start()
    process = mp.Process(target=child_job)
    process.start()
    process.join()
```

### 2.3 Hazardous form

```python
import os
from threading import Lock, Thread


lock = Lock()


def background_worker() -> None:
    with lock:
        input("hold the lock while another thread forks: ")


Thread(target=background_worker).start()
child_pid = os.fork()
if child_pid == 0:
    with lock:
        print("this child can deadlock")
    os._exit(0)
```

### 2.4 Why this difference matters

After a multithreaded fork, only the calling thread exists in the child, but locks and other state may reflect threads that no longer exist. The child can deadlock or behave inconsistently.

## 3. Boundaries and distinctions

Fork remains a specialized primitive and can be appropriate in carefully controlled process states. It is unsafe as a general process-start strategy after threads have begun running.
