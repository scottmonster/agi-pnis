# Avoid assertion mini-languages when ordinary Go comparisons are clearer

## 1. Catalog record

- **Catalog identifier:** 13.20.1
- **Impact:** low
- **Consensus:** low
- **Definition:** Go-maintained testing guidance generally favors explicit comparisons and useful failure messages over large assertion DSLs, although third-party assertion libraries remain widely used and many teams reasonably prefer them.

## 2. Example

### 2.1 Scenario

A small unit test checks the status returned for a missing resource.

### 2.2 Preferred form

```go
package example

import "testing"

func status(found bool) int { if found { return 200 }; return 404 }

func TestMissingStatus(t *testing.T) {
	const want = 404
	if got := status(false); got != want {
		t.Fatalf("status for missing resource: got %d, want %d", got, want)
	}
}
```

### 2.3 Hazardous form

```go
package example

import "testing"

func status(found bool) int { if found { return 200 }; return 404 }

func assert(t *testing.T, description string, ok bool) {
	if !ok { t.Fatal(description) }
}

func TestMissingStatus(t *testing.T) {
	assert(t, "status is expected", status(false) == 404)
}
```

### 2.4 Why this difference matters

The direct comparison exposes the tested values and gives a useful failure message. A generic assertion phrase hides both the operation and the values that failed.

## 3. Boundaries and distinctions

Third-party assertion libraries can be a reasonable team choice, especially for complex domain checks. Prefer them only when their added vocabulary is clearer than ordinary Go comparisons.
