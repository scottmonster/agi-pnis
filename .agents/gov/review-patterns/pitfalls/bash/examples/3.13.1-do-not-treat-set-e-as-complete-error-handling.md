# Do not treat `set -e` as complete error handling

## 1. Catalog record

- **Catalog identifier:** 3.13.1
- **Impact:** high
- **Consensus:** medium
- **Definition:** Use explicit checks for essential operations rather than assuming `set -e` exits after every failure.

## 2. Example

### 2.1 Scenario

A deployment function must stop when uploading the release artifact fails.

### 2.2 Preferred form

```bash
upload_release() {
  return 1
}

if ! upload_release; then
  printf 'upload failed\n' >&2
  exit 1
fi

printf 'publishing release\n'
```

### 2.3 Hazardous form

```bash
set -e

upload_release() {
  return 1
}

deploy() {
  upload_release
  printf 'marked artifact ready\n'
}

if deploy; then
  printf 'publishing release\n'
fi
```

### 2.4 Why this difference matters

`errexit` has exceptions in tested contexts such as an `if` condition, so a failure can be handled differently than an unguarded command and refactoring can change control flow.

## 3. Boundaries and distinctions

`set -e` can still be a useful guardrail, but it cannot replace explicit status handling where success is required.
