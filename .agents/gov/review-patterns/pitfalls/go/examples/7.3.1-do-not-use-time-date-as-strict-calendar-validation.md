# Do not use `time.Date` as strict calendar validation

## 1. Catalog record

- **Catalog identifier:** 7.3.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Validate calendar fields separately when invalid input should be rejected. `time.Date` normalizes out-of-range components such as October 32, and DST gaps or repetitions are inherently ambiguous.

## 2. Example

### 2.1 Scenario

A booking endpoint accepts a date-only value that must reject impossible calendar dates.

### 2.2 Preferred form

```go
package booking

import "time"

func validDate(year int, month time.Month, day int) bool {
	date := time.Date(year, month, day, 0, 0, 0, 0, time.UTC)
	return date.Year() == year && date.Month() == month && date.Day() == day
}
```

### 2.3 Hazardous form

```go
package booking

import "time"

func validDate(year int, month time.Month, day int) bool {
	_ = time.Date(year, month, day, 0, 0, 0, 0, time.UTC)
	return true
}
```

### 2.4 Why this difference matters

`time.Date(2026, time.October, 32, ...)` normalizes to a November date instead of rejecting the input.

## 3. Boundaries and distinctions

Normalization is useful when carrying calendar arithmetic intentionally. Local wall times also require a policy for DST gaps and repetitions.
