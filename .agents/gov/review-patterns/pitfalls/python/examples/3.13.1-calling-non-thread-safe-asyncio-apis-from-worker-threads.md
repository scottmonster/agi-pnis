# Calling non-thread-safe asyncio APIs from worker threads

## 1. Catalog record

- **Catalog identifier:** 3.13.1
- **Impact:** high
- **Consensus:** high
- **Definition:** From another OS thread, use `loop.call_soon_threadsafe()` or `asyncio.run_coroutine_threadsafe()` rather than ordinary event-loop methods.

## 2. Example

### 2.1 Scenario

A worker thread receives a completed result and must notify an asyncio event loop that runs on another thread.

### 2.2 Preferred form

```python
import asyncio


def record_result(result: str) -> None:
    print(result)


def worker(loop: asyncio.AbstractEventLoop) -> None:
    loop.call_soon_threadsafe(record_result, "finished")
```

### 2.3 Hazardous form

```python
import asyncio


def record_result(result: str) -> None:
    print(result)


def worker(loop: asyncio.AbstractEventLoop) -> None:
    loop.call_soon(record_result, "finished")
```

### 2.4 Why this difference matters

Most asyncio objects are not thread-safe. The thread-safe scheduling API wakes and coordinates with the event loop correctly, while ordinary loop methods can race with it.

## 3. Boundaries and distinctions

Ordinary event-loop methods are appropriate when called from the thread that owns the running loop. Coroutine submission from another thread should use `asyncio.run_coroutine_threadsafe()`.
