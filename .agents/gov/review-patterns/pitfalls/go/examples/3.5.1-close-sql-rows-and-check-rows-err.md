# Close SQL rows and check `Rows.Err`

## 1. Catalog record

- **Catalog identifier:** 3.5.1
- **Impact:** high
- **Consensus:** high
- **Definition:** Close `*sql.Rows`, normally with `defer`, and after the iteration loop check `rows.Err()`.

## 2. Example

### 2.1 Scenario

A repository reads every active account name from a query. Iteration can encounter a late driver or network error after earlier rows were delivered.

### 2.2 Preferred form

```go
package example

import (
	"context"
	"database/sql"
)

func activeNames(ctx context.Context, db *sql.DB) ([]string, error) {
	rows, err := db.QueryContext(ctx, "SELECT name FROM accounts WHERE active = true")
	if err != nil {
		return nil, err
	}
	defer rows.Close()

	var names []string
	for rows.Next() {
		var name string
		if err := rows.Scan(&name); err != nil {
			return nil, err
		}
		names = append(names, name)
	}
	if err := rows.Err(); err != nil {
		return nil, err
	}
	return names, nil
}
```

### 2.3 Hazardous form

```go
package example

import (
	"context"
	"database/sql"
)

func activeNames(ctx context.Context, db *sql.DB) ([]string, error) {
	rows, err := db.QueryContext(ctx, "SELECT name FROM accounts WHERE active = true")
	if err != nil {
		return nil, err
	}

	var names []string
	for rows.Next() {
		var name string
		_ = rows.Scan(&name)
		names = append(names, name)
	}
	return names, nil // rows is leaked and a late iteration error is hidden.
}
```

### 2.4 Why this difference matters

`Rows.Close` releases database resources promptly. `Rows.Err` reports errors that end iteration, so omitting it can make a partial result look complete.

## 3. Boundaries and distinctions

`rows.Close` may be redundant after a fully exhausted successful loop, but deferring it is the clear safe default and handles early returns. Always check scan errors separately from the final iteration error.
