# Do not accidentally destroy exported struct comparability

## 1. Catalog record

- **Catalog identifier:** 10.7.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Before adding a slice, map, function, or other non-comparable field to an exported value struct, consider whether callers may compare the struct or use it as a map key.

## 2. Example

### 2.1 Scenario

A package exposes a `Coordinate` value that callers use as a key when grouping map tiles.

### 2.2 Preferred form

```go
package example

type Coordinate struct {
	X int
	Y int
}

func visitsByCoordinate() map[Coordinate]int {
	return map[Coordinate]int{{X: 1, Y: 2}: 1}
}
```

### 2.3 Hazardous form

```go
package example

type Coordinate struct {
	X      int
	Y      int
	Labels []string // adding this makes Coordinate non-comparable
}

func example() Coordinate {
	coordinate := Coordinate{X: 1, Y: 2}
	// _ = map[Coordinate]int{coordinate: 1} // no longer compiles
	return coordinate
}
```

### 2.4 Why this difference matters

Adding a slice silently changes an exported value type from comparable to non-comparable. Downstream code using `==` or `map[Coordinate]` fails to compile after the release.

## 3. Boundaries and distinctions

Non-comparable fields are fine when callers should not compare or key by the value. Document that choice, or keep mutable metadata in a separate associated type.
