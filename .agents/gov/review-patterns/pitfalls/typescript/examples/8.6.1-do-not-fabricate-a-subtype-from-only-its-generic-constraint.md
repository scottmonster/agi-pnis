# Do not fabricate a subtype from only its generic constraint

## 1. Catalog record

- **Catalog identifier:** 8.6.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** If a function promises to return `T extends Base`, do not construct and return merely a `Base` value as though it were an arbitrary caller-provided `T`.

## 2. Example

### 2.1 Scenario

A function changes a known property of the caller's object while preserving the rest of that caller-provided subtype.

### 2.2 Preferred form

```typescript
interface Named {
  name: string;
}

function rename<T extends Named>(person: T, name: string): T {
  return { ...person, name };
}

const member = rename({ name: 'Ana', loyaltyPoints: 40 }, 'Anika');
console.log(member.loyaltyPoints);
```

### 2.3 Hazardous form

```typescript
interface Named {
  name: string;
}

function makeNamed<T extends Named>(name: string): T {
  return { name } as T;
}

const member = makeNamed<{ name: string; loyaltyPoints: number }>('Anika');
console.log(member.loyaltyPoints); // undefined at runtime
```

### 2.4 Why this difference matters

The caller's subtype may contain additional required invariants or properties that the generic implementation cannot know how to create.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
