# Do not upgrade or recursively acquire `RWMutex` read locks

## 1. Catalog record

- **Catalog identifier:** 6.4.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** `RWMutex` cannot be upgraded from read to write or downgraded from write to read. Recursive read locking is unsafe when a writer may be pending.

## 2. Example

### 2.1 Scenario

A cache loads a missing value while protecting a map.

### 2.2 Preferred form

```go
package main

import "sync"

type cache struct { mu sync.RWMutex; m map[string]string }
func (c *cache) getOrLoad(key string) string {
	c.mu.RLock(); value, ok := c.m[key]; c.mu.RUnlock()
	if ok { return value }
	c.mu.Lock(); defer c.mu.Unlock()
	if value, ok = c.m[key]; !ok { value = "loaded"; c.m[key] = value }
	return value
}
```

### 2.3 Hazardous form

```go
package main

import "sync"

type cache struct { mu sync.RWMutex; m map[string]string }
func (c *cache) getOrLoad(key string) string {
	c.mu.RLock(); defer c.mu.RUnlock()
	if value, ok := c.m[key]; ok { return value }
	c.mu.Lock(); defer c.mu.Unlock()
	c.m[key] = "loaded"; return c.m[key]
}
```

### 2.4 Why this difference matters

Acquiring a write lock while holding the read lock can deadlock. Release, then recheck while holding the write lock.

## 3. Boundaries and distinctions

The recheck handles another goroutine populating the value first. Use a plain mutex when read parallelism is not worthwhile.
