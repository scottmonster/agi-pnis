# Outdated dependency

## 1. Catalog record

- **Catalog identifier:** 8.6
- **Evidence:** e
- **Definition:** Pins or selects an old version that lacks required fixes, support, or compatibility.

## 2. Scenario

### 2.1 Context

A Node service must support a current cloud SDK API that requires a bug fix added after version 3.410.0.

### 2.2 Safer approach

Check the project runtime, the SDK compatibility notes, and the needed API before selecting a maintained version. Record the compatible version range and update the lockfile through the normal package workflow.

```json
{
  "dependencies": {
    "@acme/cloud-sdk": "^3.455.0"
  }
}
```

### 2.3 Failure mode

The agent copies an old version from a legacy service because it appears familiar.

```json
{
  "dependencies": {
    "@acme/cloud-sdk": "3.410.0"
  }
}
```

### 2.4 Why this difference matters

The older SDK lacks the required fix, so the new integration can fail despite passing local compilation.

## 3. Boundaries and distinctions

An older version can be deliberate when a supported runtime or documented compatibility constraint requires it. This failure is selecting an old version without verifying whether it still meets the task's support, fix, and compatibility needs.
