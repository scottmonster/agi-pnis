# Project dependency conflict

## 1. Catalog record

- **Catalog identifier:** 2.10
- **Evidence:** e
- **Definition:** Relies on a dependency, import, object, module, or initialization path unavailable in the actual project.

## 2. Scenario

### 2.1 Context

An agent adds image resizing to a service with a small, fixed dependency manifest.

### 2.2 Safer approach

It checks available dependencies and either uses a supported one or explicitly adds the required package through the project's normal process.

### 2.3 Failure mode

It imports `sharp` because it expects the package to be present, although it is not declared or installed.

### 2.4 Why this difference matters

The implementation cannot run in a clean project environment and creates a hidden setup requirement.

## 3. Boundaries and distinctions

Adding a dependency can be appropriate when approved and declared; the failure is relying on one unavailable in the project.
