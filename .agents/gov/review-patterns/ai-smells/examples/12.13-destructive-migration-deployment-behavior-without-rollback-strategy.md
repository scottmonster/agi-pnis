# Destructive migration/deployment behavior without rollback strategy

## 1. Catalog record

- **Catalog identifier:** 12.13
- **Evidence:** se
- **Definition:** Irreversibly changes data or infrastructure without a tested recovery path if the deployment fails.

## 2. Scenario

### 2.1 Context

A deployment drops a populated database column before the replacement application version has completed its rollout, and no backup restoration or compatible rollback has been tested.

### 2.2 Safer approach

Stage the schema change with backward compatibility, preserve recovery data, and exercise the rollback path before relying on the destructive step.

### 2.3 Failure mode

Drop the column as part of the release because the new code no longer reads it, without planning for a partial deployment failure.

### 2.4 Why this difference matters

If rollout fails, restoring the prior version may not restore the lost data or a working infrastructure state.

## 3. Boundaries and distinctions

Destructive changes can be appropriate when a tested recovery strategy fits the system. The issue is irreversible deployment behavior without a validated way back.
