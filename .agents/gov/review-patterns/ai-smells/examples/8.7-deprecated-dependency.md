# Deprecated dependency

## 1. Catalog record

- **Catalog identifier:** 8.7
- **Evidence:** e
- **Definition:** Uses a package or feature its maintainer has marked for replacement or end of support.

## 2. Scenario

### 2.1 Context

A maintenance change needs to add request validation to a TypeScript API. The existing project uses a deprecated validation package whose maintainer directs new users to its replacement.

### 2.2 Safer approach

Use the supported replacement, adapt the validation boundary, and update the import and tests together.

```ts
import { object, string } from "supported-validator";

const createUser = object({ email: string().email() });
```

### 2.3 Failure mode

The agent adds new code with the deprecated package because its API appears in older project files.

```ts
import legacyValidator from "legacy-validator";

const createUser = legacyValidator.object({ email: legacyValidator.email() });
```

### 2.4 Why this difference matters

New work deepens reliance on an unsupported component, increasing future migration, security, and compatibility risk.

## 3. Boundaries and distinctions

An existing deprecated dependency may require a staged migration when replacement is not compatible or safe to complete in the current change. The failure is introducing or extending its use without considering the maintainer's replacement or support status.
