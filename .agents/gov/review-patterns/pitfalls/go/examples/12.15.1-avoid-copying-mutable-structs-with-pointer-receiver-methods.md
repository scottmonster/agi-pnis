# Avoid copying mutable structs with pointer receiver methods

## 1. Catalog record

- **Catalog identifier:** 12.15.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Do not casually copy types such as `bytes.Buffer` whose internal slices or other state can alias after copying.

## 2. Example

### 2.1 Scenario

A response builder has prepared an HTTP header and needs to create a separate response body. The new buffer should receive copied bytes, not a copied `bytes.Buffer` value.

### 2.2 Preferred form

```go
package example

import "bytes"

func response() string {
	var header bytes.Buffer
	header.WriteString("Content-Type: text/plain\\r\\n\\r\\n")

	var full bytes.Buffer
	full.Write(header.Bytes())
	full.WriteString("hello")
	return full.String()
}
```

### 2.3 Hazardous form

```go
package example

import "bytes"

func response() string {
	var header bytes.Buffer
	header.Grow(128)
	header.WriteString("Content-Type: text/plain\\r\\n\\r\\n")

	full := header // Copies mutable state and may share its backing array.
	full.WriteString("hello")
	return header.String()
}
```

### 2.4 Why this difference matters

A copied `bytes.Buffer` can share its backing bytes with the original while maintaining separate length and offset fields. Later writes can therefore create surprising output, corrupt assumptions about ownership, or race when used concurrently.

## 3. Boundaries and distinctions

Small immutable structs are normally safe to copy. For mutable library types, follow their documentation and copy the logical contents into a new value when independent ownership is needed.
