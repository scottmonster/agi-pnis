# Require explicit `override` markers

## 1. Catalog record

- **Catalog identifier:** 7.8.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Enable `noImplicitOverride` so an overriding member must explicitly say `override`.

## 2. Example

### 2.1 Scenario

A base class exposes a lifecycle hook that a subclass customizes. Later, the base class is renamed during a refactor.

### 2.2 Preferred form

```typescript
class Job {
  run(): void {
    console.log('running');
  }
}

class TimedJob extends Job {
  override run(): void {
    console.time('job');
    super.run();
    console.timeEnd('job');
  }
}
```

### 2.3 Hazardous form

```typescript
class Job {
  execute(): void {
    console.log('running');
  }
}

class TimedJob extends Job {
  // This used to override Job.run. It is now an unrelated method.
  run(): void {
    console.time('job');
    console.timeEnd('job');
  }
}

new TimedJob().execute(); // timing is silently skipped
```

### 2.4 Why this difference matters

With `noImplicitOverride`, the preferred member must state its intent. If `Job.run` is renamed or removed, TypeScript reports that `TimedJob.run` no longer overrides anything instead of accepting an unrelated member.

## 3. Boundaries and distinctions

This check applies to members that override a declared base-class member. It does not require `override` for new subclass APIs, and it does not alter JavaScript runtime dispatch. Enable it in projects where superclass refactors should fail at compile time rather than silently change subclass behavior.
