# Assuming `cached_property` computes exactly once under concurrency

## 1. Catalog record

- **Catalog identifier:** 8.15.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** If duplicate execution would be unsafe, explicitly synchronize a `cached_property` computation rather than relying on the descriptor to provide once-only execution.

## 2. Example

### 2.1 Scenario

Concurrent callers lazily initialize a resource whose creation has an external side effect.

### 2.2 Preferred form

```python
import threading

class Connection:
    def __init__(self) -> None:
        self._client: object | None = None
        self._lock = threading.Lock()

    def client(self) -> object:
        with self._lock:
            if self._client is None:
                self._client = object()
            return self._client
```

### 2.3 Hazardous form

```python
from functools import cached_property

class Connection:
    @cached_property
    def client(self) -> object:
        return object()  # Concurrent access can invoke this getter more than once.
```

### 2.4 Why this difference matters

Modern `cached_property` does not supply a once-only concurrency guarantee, so racing calls can duplicate work or side effects.

## 3. Boundaries and distinctions

Duplicate computation is harmless for many pure, idempotent getters, where the descriptor remains convenient.
