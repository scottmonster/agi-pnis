# Keep context values request-scoped and collision-resistant

## 1. Catalog record

- **Catalog identifier:** 9.3.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Use context values only for request-scoped data crossing API boundaries, not as an optional-parameter bag. Define private comparable key types rather than raw strings.

## 2. Example

### 2.1 Scenario

Middleware attaches a tracing request ID that downstream logging code must read without adding it to every API signature.

### 2.2 Preferred form

```go
package example

import "context"

type requestIDKey struct{}

func withRequestID(ctx context.Context, id string) context.Context {
	return context.WithValue(ctx, requestIDKey{}, id)
}

func requestID(ctx context.Context) (string, bool) {
	id, ok := ctx.Value(requestIDKey{}).(string)
	return id, ok
}
```

### 2.3 Hazardous form

```go
package example

import "context"

func withOptions(ctx context.Context, retries int, region string) context.Context {
	ctx = context.WithValue(ctx, "retries", retries)
	return context.WithValue(ctx, "region", region) // String keys can collide.
}
```

### 2.4 Why this difference matters

Private key types avoid collisions with other packages, while explicit parameters keep ordinary configuration visible and type checked.

## 3. Boundaries and distinctions

Context values are appropriate for request-scoped metadata crossing API boundaries, such as tracing data. They are not a replacement for required business inputs or service configuration.
