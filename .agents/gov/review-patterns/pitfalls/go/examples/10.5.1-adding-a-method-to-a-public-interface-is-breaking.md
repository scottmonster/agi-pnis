# Adding a method to a public interface is breaking

## 1. Catalog record

- **Catalog identifier:** 10.5.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Add a new interface or feature-detect a secondary interface rather than casually adding a method to an exported interface implemented by users.

## 2. Example

### 2.1 Scenario

A library wants to optionally flush custom writers supplied by its users without breaking existing `Writer` implementations.

### 2.2 Preferred form

```go
package example

type Writer interface {
	Write([]byte) error
}

type Flusher interface {
	Flush() error
}

func finish(w Writer) error {
	if f, ok := w.(Flusher); ok {
		return f.Flush()
	}
	return nil
}
```

### 2.3 Hazardous form

```go
package example

type Writer interface {
	Write([]byte) error
	Flush() error // every downstream Writer implementation now fails to compile
}

type userWriter struct{}

func (userWriter) Write([]byte) error { return nil }

// var _ Writer = userWriter{} // this existing user implementation no longer compiles
```

### 2.4 Why this difference matters

External types that previously satisfied the public interface no longer do after a method is added. A secondary interface lets old implementations continue working and new ones opt into flushing.

## 3. Boundaries and distinctions

Adding a method is safe only for interfaces not implemented outside the controlled codebase. A major-version release can intentionally make this breaking change when migration is worthwhile.
