# Prefer `@ts-expect-error` over `@ts-ignore`

## 1. Catalog record

- **Catalog identifier:** 7.19.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** When a type error genuinely must be suppressed, use `@ts-expect-error`, ideally with an explanation, rather than an indefinite `@ts-ignore`.

## 2. Example

### 2.1 Scenario

A type test deliberately passes an invalid value to verify that an API rejects it.

### 2.2 Preferred form

```typescript
declare function setRetryCount(count: number): void;

// @ts-expect-error: retry counts must be numbers
setRetryCount('many');
```

### 2.3 Hazardous form

```typescript
declare function setRetryCount(count: number): void;

// @ts-ignore
setRetryCount('many');
```

### 2.4 Why this difference matters

`@ts-expect-error` becomes a compiler error when the following line no longer has a type error. If `setRetryCount` is widened or the test is accidentally changed, the stale directive is caught. `@ts-ignore` keeps suppressing diagnostics indefinitely, so it can conceal that the expected error disappeared or that a different error replaced it.

## 3. Boundaries and distinctions

Use a suppression only at a narrow, documented boundary, such as a negative type test or an unavoidable third-party typing defect. `@ts-ignore` may be necessary for generated code or a temporary migration where no stable expected error can be named, but it should carry an issue reference and removal plan. Neither directive validates untyped runtime data.
