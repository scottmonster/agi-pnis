# Add explicit exported return types when profiling shows inference cost

## 1. Catalog record

- **Catalog identifier:** 11.1.3
- **Impact:** low
- **Consensus:** high
- **Definition:** Do not annotate every trivial expression, but consider explicit return and public API types in declaration-heavy or very large projects where compiler profiling identifies inference/serialization cost.

## 2. Example

### 2.1 Scenario

A declaration-heavy package exposes a normalized route table after profiling identifies declaration serialization work.

### 2.2 Preferred form

```typescript
export interface Route {
  method: 'GET' | 'POST';
  path: string;
}

export type RouteTable = Readonly<Record<string, Route>>;

export function createRoutes(): RouteTable {
  return {
    health: { method: 'GET', path: '/health' },
    submit: { method: 'POST', path: '/submit' },
  };
}
```

### 2.3 Hazardous form

```typescript
export function createRoutes() {
  return {
    health: { method: 'GET' as const, path: '/health' },
    submit: { method: 'POST' as const, path: '/submit' },
  };
}
```

### 2.4 Why this difference matters

Named explicit types can reduce work and produce smaller, more stable declaration representations.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
