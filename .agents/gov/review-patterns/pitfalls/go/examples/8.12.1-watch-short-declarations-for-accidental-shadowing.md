# Watch short declarations for accidental shadowing

## 1. Catalog record

- **Catalog identifier:** 8.12.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Be especially careful with `:=` inside nested blocks when names such as `err` already exist. Use assignment when the outer variable is intended.

## 2. Example

### 2.1 Scenario

A request handler performs a required audit write after it validates a request.

### 2.2 Preferred form

```go
package handler

import "errors"

func process(valid bool, audit func() error) error {
	if !valid {
		return errors.New("invalid request")
	}
	if err := audit(); err != nil {
		return err
	}
	return nil
}
```

### 2.3 Hazardous form

```go
package handler

import "errors"

func process(valid bool, audit func() error) (err error) {
	if !valid {
		err = errors.New("invalid request")
	}
	if err := audit(); err != nil {
		return err
	}
	return nil
}
```

### 2.4 Why this difference matters

The `err` declared in the `if` initializer is scoped only to that conditional. Even more seriously, the final `return nil` overwrites the outer validation error, allowing an invalid request to appear successful.

## 3. Boundaries and distinctions

Short declarations are idiomatic when their scope is deliberately local, including `if err := call(); err != nil`. Use `=` when assigning a previously declared variable is required, and favor early returns to avoid retaining error state across blocks.
