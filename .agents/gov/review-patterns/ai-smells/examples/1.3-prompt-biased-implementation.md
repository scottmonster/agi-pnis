# Prompt-biased implementation

## 1. Catalog record

- **Catalog identifier:** 1.3
- **Evidence:** e
- **Definition:** Overfits wording, examples, variable names, or incidental details in the prompt instead of the underlying requirement.

## 2. Scenario

### 2.1 Context

A bug report says the sample user `alice@example.test` cannot reset a password because expired reset tokens are accepted. The requirement is to reject expired tokens for every account.

### 2.2 Safer approach

Trace token validation, add a time-based expiry check in the shared reset flow, and test both expired and unexpired tokens for multiple users.

### 2.3 Failure mode

The agent adds a special condition for `alice@example.test` because it treats the report's example account as the requirement.

### 2.4 Why this difference matters

The reported example may pass while the general security defect remains for all other accounts.

## 3. Boundaries and distinctions

Concrete examples can clarify expected behavior. They should not narrow a general requirement unless the task expressly makes them the scope.
