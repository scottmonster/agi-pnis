# Avoid heterogeneous enums

## 1. Catalog record

- **Catalog identifier:** 10.7.1
- **Impact:** low
- **Consensus:** high
- **Definition:** Do not mix numeric and string members in one enum without a strong interoperability reason.

## 2. Example

### 2.1 Scenario

A job runner records a terminal result and exposes it to a metrics pipeline.

### 2.2 Preferred form

```typescript
enum JobResult {
  Succeeded = "succeeded",
  Failed = "failed",
  Cancelled = "cancelled",
}

function metricValue(result: JobResult): string {
  return result;
}
```

### 2.3 Hazardous form

```typescript
enum JobResult {
  Succeeded = 0,
  Failed = "failed",
  Cancelled = 2,
}

function metricValue(result: JobResult): string {
  return String(result);
}
```

### 2.4 Why this difference matters

The hazardous enum produces values such as `"0"`, `"failed"`, and `"2"` for one conceptual field. Callers, logs, and external consumers must now account for two incompatible representations.

## 3. Boundaries and distinctions

A heterogeneous enum can be justified when a fixed external protocol truly requires the mixed values. Otherwise choose one representation, or model the protocol translation at its boundary.
