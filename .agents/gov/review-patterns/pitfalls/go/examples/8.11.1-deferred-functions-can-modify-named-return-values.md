# Deferred functions can modify named return values

## 1. Catalog record

- **Catalog identifier:** 8.11.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Be cautious when combining named result variables with defers. A deferred closure can read or change those result values after the return statement has set them.

## 2. Example

### 2.1 Scenario

A function validates a request and returns the validation error to its caller.

### 2.2 Preferred form

```go
package validate

import "errors"

func check(valid bool) error {
	defer func() {
		// Metrics or cleanup can run here without changing the result.
	}()
	if !valid {
		return errors.New("invalid request")
	}
	return nil
}
```

### 2.3 Hazardous form

```go
package validate

import "errors"

func check(valid bool) (err error) {
	defer func() {
		err = nil
	}()
	if !valid {
		return errors.New("invalid request")
	}
	return nil
}
```

### 2.4 Why this difference matters

Before a deferred function runs, `return errors.New(...)` assigns that error to the named result. The deferred closure then overwrites it with nil, hiding validation failure from the caller.

## 3. Boundaries and distinctions

Named results and deferred modification can be appropriate for a tightly controlled pattern, such as adding a cleanup error only when no earlier error exists. Keep that behavior brief and explicit because it changes the function's return contract.
