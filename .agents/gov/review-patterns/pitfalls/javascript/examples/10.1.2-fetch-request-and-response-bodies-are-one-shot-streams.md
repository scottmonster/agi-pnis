# Fetch request and response bodies are one-shot streams

## 1. Catalog record

- **Catalog identifier:** 10.1.2
- **Impact:** medium
- **Consensus:** high
- **Definition:** Treat fetch bodies as one-shot streams and clone before first consumption only when a valid second read is needed.

## 2. Example

### 2.1 Scenario

A support tool needs to parse an API response and retain its original text for a diagnostic record.

### 2.2 Preferred form

```javascript
async function readResponse(response) {
  const diagnosticCopy = response.clone();
  const payload = await response.json();
  const diagnosticText = await diagnosticCopy.text();
  return { payload, diagnosticText };
}

fetch("/api/orders/42").then(readResponse).then(console.log);
```

### 2.3 Hazardous form

```javascript
async function readResponse(response) {
  const payload = await response.json();
  const diagnosticText = await response.text();
  return { payload, diagnosticText };
}

fetch("/api/orders/42").then(readResponse).then(console.log);
```

### 2.4 Why this difference matters

After `json()` consumes the response body, the subsequent `text()` call rejects because the body stream is already used.

## 3. Boundaries and distinctions

Clone only when two independent readers are truly required. A clone tees the underlying stream and can add memory pressure for large or unevenly consumed bodies.
