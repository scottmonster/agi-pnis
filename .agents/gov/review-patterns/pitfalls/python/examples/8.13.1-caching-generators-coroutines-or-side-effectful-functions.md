# Caching generators, coroutines, or side-effectful functions

## 1. Catalog record

- **Catalog identifier:** 8.13.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Use `lru_cache` and `cache` for reusable computed values, not calls whose identity, side effects, freshness, generator iteration state, or coroutine execution matters.

## 2. Example

### 2.1 Scenario

A loader is called repeatedly for the same customer and callers need reusable results.

### 2.2 Preferred form

```python
from functools import cache

@cache
def load_codes(customer_id: int) -> tuple[str, ...]:
    return (f"C-{customer_id}-A", f"C-{customer_id}-B")

assert load_codes(7) == ("C-7-A", "C-7-B")
```

### 2.3 Hazardous form

```python
from functools import cache

@cache
def load_codes(customer_id: int):
    yield f"C-{customer_id}-A"

assert list(load_codes(7)) == ["C-7-A"]
assert list(load_codes(7)) == []  # The cached generator was exhausted.
```

### 2.4 Why this difference matters

Caching returns the same generator or coroutine object, not a newly executable computation, and can also suppress needed side effects or freshness.

## 3. Boundaries and distinctions

Caching is appropriate for deterministic, reusable values with a suitable invalidation and memory policy.
