# Catch errors you can handle and rethrow unexpected ones

## 1. Catalog record

- **Catalog identifier:** 7.1.7
- **Impact:** medium
- **Consensus:** high
- **Definition:** Avoid broad catch blocks that silently turn every exception into the same fallback. Handle expected failures and rethrow exceptions the layer cannot meaningfully resolve.

## 2. Example

### 2.1 Scenario

A cache lookup may legitimately miss, but a programming or transport error must reach the caller.

### 2.2 Preferred form

```javascript
class CacheMissError extends Error {}

async function readCache(key) {
  if (key === "missing") throw new CacheMissError("not cached");
  throw new TypeError("corrupt cache client");
}

async function getCachedOrDefault(key) {
  try {
    return await readCache(key);
  } catch (error) {
    if (error instanceof CacheMissError) return "default value";
    throw error;
  }
}

getCachedOrDefault("missing").then(console.log, console.error);
```

### 2.3 Hazardous form

```javascript
async function readCache() {
  throw new TypeError("corrupt cache client");
}

async function getCachedOrDefault(key) {
  try {
    return await readCache(key);
  } catch {
    return "default value";
  }
}

getCachedOrDefault("theme").then(console.log, console.error);
```

### 2.4 Why this difference matters

The broad catch disguises an unexpected defect as a routine cache miss, delaying detection and diagnosis.

## 3. Boundaries and distinctions

A broad fallback can be valid at a deliberate application boundary, provided the error is logged or otherwise observed and the fallback is safe.
