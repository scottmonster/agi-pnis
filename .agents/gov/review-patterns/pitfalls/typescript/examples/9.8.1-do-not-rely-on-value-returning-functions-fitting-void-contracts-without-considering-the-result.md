# Do not rely on value-returning functions fitting `void` contracts without considering the result

## 1. Catalog record

- **Catalog identifier:** 9.8.1
- **Impact:** medium
- **Consensus:** medium
- **Definition:** TypeScript intentionally permits a value-returning function where `() => void` is expected; use `strict-void-return` when your architecture treats ignored return values as suspicious.

## 2. Example

### 2.1 Scenario

A batch runner must await every save before it reports completion.

### 2.2 Preferred form

```typescript
async function saveInvoice(id: string): Promise<void> {
  await Promise.resolve(id);
}

async function runAll(jobs: readonly (() => Promise<void>)[]): Promise<void> {
  await Promise.all(jobs.map((job) => job()));
}

await runAll([() => saveInvoice('inv-42')]);
```

### 2.3 Hazardous form

```typescript
async function saveInvoice(id: string): Promise<void> {
  await Promise.resolve(id);
}

function runAll(jobs: readonly (() => void)[]): void {
  jobs.forEach((job) => job());
}

runAll([() => saveInvoice('inv-42')]); // Promise is accepted and silently ignored
```

### 2.4 Why this difference matters

The rule can expose ignored Promises, generators, accidental `.map`/`.forEach` confusion, and mismatches between static `void` and runtime return values.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
