# Use branded types when structurally identical primitives represent different domains

## 1. Catalog record

- **Catalog identifier:** 6.11.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** For values such as validated strings, IDs, currencies, or tokens that share an underlying primitive but must not be interchangeable, introduce a brand or `unique symbol` marker where the distinction is valuable.

## 2. Example

### 2.1 Scenario

A function receives a user identifier and a product identifier, both serialized as strings.

### 2.2 Preferred form

```typescript
declare const userIdBrand: unique symbol;
declare const productIdBrand: unique symbol;

type UserId = string & { readonly [userIdBrand]: true };
type ProductId = string & { readonly [productIdBrand]: true };

function userId(value: string): UserId {
  if (!value.startsWith('user_')) throw new Error('Invalid user ID');
  return value as UserId;
}

function productId(value: string): ProductId {
  if (!value.startsWith('product_')) throw new Error('Invalid product ID');
  return value as ProductId;
}

function loadProduct(userId: UserId, productId: ProductId): string {
  return `${userId}:${productId}`;
}

const owner = userId('user_1');
const product = productId('product_1');
loadProduct(owner, product);
```

### 2.3 Hazardous form

```typescript
type UserId = string;
type ProductId = string;

function loadProduct(userId: UserId, productId: ProductId): string {
  return `${userId}:${productId}`;
}

loadProduct('product_1', 'user_1'); // The arguments can be silently swapped.
```

### 2.4 Why this difference matters

Plain aliases such as `type UserId = string` and `type ProductId = string` remain structurally interchangeable.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
