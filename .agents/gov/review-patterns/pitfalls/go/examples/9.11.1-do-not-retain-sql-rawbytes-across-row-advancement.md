# Do not retain `sql.RawBytes` across row advancement

## 1. Catalog record

- **Catalog identifier:** 9.11.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Copy `RawBytes` if data must survive the next `Rows.Next`, `Scan`, or close operation.

## 2. Example

### 2.1 Scenario

A report collects binary identifiers from every row before emitting them after iteration.

### 2.2 Preferred form

```go
package example

import "database/sql"

func collect(rows *sql.Rows) ([][]byte, error) {
	var values [][]byte
	for rows.Next() {
		var raw sql.RawBytes
		if err := rows.Scan(&raw); err != nil { return nil, err }
		values = append(values, append([]byte(nil), raw...))
	}
	return values, rows.Err()
}
```

### 2.3 Hazardous form

```go
package example

import "database/sql"

func collect(rows *sql.Rows) ([][]byte, error) {
	var values [][]byte
	for rows.Next() {
		var raw sql.RawBytes
		if err := rows.Scan(&raw); err != nil { return nil, err }
		values = append(values, raw) // Driver storage can change on the next iteration.
	}
	return values, rows.Err()
}
```

### 2.4 Why this difference matters

`RawBytes` may reference driver-owned memory that is reused on row advancement. Copying provides stable ownership for data retained after the scan.

## 3. Boundaries and distinctions

Do not copy when the bytes are consumed immediately before the next `Next`, `Scan`, or close operation. Prefer scanning into a string or ordinary `[]byte` when that better fits the data contract.
