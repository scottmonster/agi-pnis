# Signal uncertain index-signature properties with bracket access

## 1. Catalog record

- **Catalog identifier:** 7.10.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Consider `noPropertyAccessFromIndexSignature` when dictionary-like objects mix declared properties and arbitrary keys.

## 2. Example

### 2.1 Scenario

An HTTP response has a declared content type and an open-ended collection of headers, whose presence is determined at runtime.

### 2.2 Preferred form

```typescript
interface ResponseHeaders {
  contentType: string;
  [headerName: string]: string;
}

function traceRequestId(headers: ResponseHeaders): void {
  console.log(headers.contentType); // declared property
  console.log(headers['x-request-id']); // arbitrary header may be absent
}
```

### 2.3 Hazardous form

```typescript
interface ResponseHeaders {
  contentType: string;
  [headerName: string]: string;
}

function traceRequestId(headers: ResponseHeaders): void {
  console.log(headers.contentType);
  console.log(headers.xRequestId); // looks like a declared, guaranteed property
}
```

### 2.4 Why this difference matters

With `noPropertyAccessFromIndexSignature`, TypeScript requires bracket access for `xRequestId` because the index signature, not the interface, supplies its type. The syntax makes the uncertain dictionary lookup visible in review and encourages a presence check where one is needed.

## 3. Boundaries and distinctions

Use this option for mixed shapes that have both stable fields and arbitrary keys, such as headers, feature flags, and metadata maps. It does not make an indexed lookup non-nullable. Pair it with `noUncheckedIndexedAccess` or an explicit validation when missing keys must be handled safely.
