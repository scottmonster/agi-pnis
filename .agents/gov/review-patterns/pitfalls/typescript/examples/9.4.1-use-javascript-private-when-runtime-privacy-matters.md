# Use JavaScript `#private` when runtime privacy matters

## 1. Catalog record

- **Catalog identifier:** 9.4.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** Use ECMAScript private fields for hard runtime privacy rather than assuming the TypeScript `private` modifier creates an inaccessible runtime slot.

## 2. Example

### 2.1 Scenario

An account's balance must be inaccessible to runtime callers outside the class.

### 2.2 Preferred form

```typescript
class Account {
  #balance = 0;

  deposit(amount: number): void {
    this.#balance += amount;
  }
}

const account = new Account();
account.deposit(25);
console.log((account as unknown as { balance: number }).balance); // undefined
```

### 2.3 Hazardous form

```typescript
class Account {
  private balance = 0;

  deposit(amount: number): void {
    this.balance += amount;
  }
}

const account = new Account();
account.deposit(25);
console.log((account as unknown as { balance: number }).balance); // 25
```

### 2.4 Why this difference matters

TypeScript `private` is primarily a static restriction, while `#private` is enforced by JavaScript itself.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
