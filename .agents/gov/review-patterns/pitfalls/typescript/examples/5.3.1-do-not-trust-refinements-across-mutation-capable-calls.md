# Do not trust refinements across mutation-capable calls

## 1. Catalog record

- **Catalog identifier:** 5.3.1
- **Impact:** high
- **Consensus:** medium
- **Definition:** If a callback or function call can mutate an object that has been narrowed, capture the narrowed primitive locally or expose a readonly view before the call.

## 2. Example

### 2.1 Scenario

A callback can clear an optional value after it has been narrowed.

### 2.2 Preferred form

```typescript
type Session = { token?: string };

function send(session: Session, beforeSend: () => void): string {
  const token = session.token;
  if (token === undefined) throw new Error('Not authenticated');
  beforeSend();
  return token.toUpperCase();
}
```

### 2.3 Hazardous form

```typescript
type Session = { token?: string };

function send(session: Session, beforeSend: () => void): string {
  if (session.token === undefined) throw new Error('Not authenticated');
  beforeSend();
  return session.token.toUpperCase(); // The callback may have deleted `token`.
}
```

### 2.4 Why this difference matters

TypeScript generally does not invalidate refinements after arbitrary function calls even though the called code can mutate the refined property.

## 3. Boundaries and distinctions

Apply this guidance in the conditions described by the catalog record. Deliberate exceptions need a documented runtime guarantee, compatible toolchain behavior, or an explicit local unsafe boundary.
