# Late-bound closures in loops

## 1. Catalog record

- **Catalog identifier:** 6.6.1
- **Impact:** medium
- **Consensus:** high
- **Definition:** When callbacks created in a loop should capture the current loop value, bind it explicitly, such as through a default parameter or helper scope.

## 2. Example

### 2.1 Scenario

A menu builder creates callbacks that must retain the identifier for their own menu item.

### 2.2 Preferred form

```python
item_ids = ["open", "save", "close"]
callbacks = [lambda item_id=item_id: item_id for item_id in item_ids]

assert [callback() for callback in callbacks] == ["open", "save", "close"]
```

### 2.3 Hazardous form

```python
item_ids = ["open", "save", "close"]
callbacks = [lambda: item_id for item_id in item_ids]

assert [callback() for callback in callbacks] == ["close", "close", "close"]
```

### 2.4 Why this difference matters

Closures refer to the variable, not a snapshot of its value at creation time. Once the loop finishes, every callback observes the final binding.

## 3. Boundaries and distinctions

Late binding is useful when callbacks should observe a changing shared variable. Bind explicitly only when each callback needs a distinct current value.
